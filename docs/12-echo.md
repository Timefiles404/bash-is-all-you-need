# 阶段 12：回声

最便宜的工具调用，是你没发出去的那一次。模型要一条命令，Agent 之前已经
跑过，而这条命令读过的东西从那以后没有一样变过——那你就把答案递回去，不
必再起一个进程。

整个想法就这么多，写出来大概八十行。这一章大半篇幅花在另外两个问题上，
它们比看上去难，而且再多的代码也替你答不了：**两条命令什么时候算同一条
命令**，以及**那个答案现在还成立吗**。然后它会问第三个，而这个问题几乎
没人在缓存上线之前问过——**这东西本来帮得上忙吗？**——结果这里的答案是
*勉强*，而这恰恰是全章最有用的东西。

缓存你还是要做。不是因为这个数字好看，而是因为查出一个数字很难看，只花
你一个下午；等它上线之后才查出来，代价大得多。

**动手之前。**你需要阶段 07 的子 Agent，因为这个缓存明显划算的地方只有
一处，就是几个子 Agent 同时读同一个文件；需要阶段 08 那个论证——一条
shell 命令干什么，光读它是读不出来的——因为这一章要把同一个事实反过来
用；还需要阶段 02 的事件 trace，因为正是 trace 让你能拿已经发生过的会话
去评估缓存，不用 API key，也不用真跑任何东西。

**你会做出什么。**一个结果缓存：键按内容寻址；一份白名单，凡是它没有完
全看懂的命令一律拒绝；一套失效检查，用的是文件哈希，不是时间戳；两条互
相独立的体积上限；四个计数器，是零也照样打印；外加一个 `--cache-audit`
模式，把旧 trace 在一个冷缓存上重放一遍，告诉你它本来会怎么做。一个新文
件，一种新事件，一个 flag——默认关着，理由这一章会讲。

---

## 起点在哪里

阶段 11 结束时，派发循环会先校验一次工具调用，再把它跑起来。bash 那一半
是六行：

```go
func (a *agent) runCommand(ctx context.Context, turn int, callID, command string) string {
    a.bus.Emit(Event{Kind: KindCommandStart, Turn: turn, ToolID: callID, Command: command})
    r := runBash(ctx, a.cfg.shell, command, a.cfg.timeout)
    rendered, truncated := r.render(a.cfg.maxOutput)
    a.bus.Emit(Event{Kind: KindCommandEnd, Truncated: truncated /* ... */})
    return rendered
}
```

每条命令都真跑。二十个回合之前模型要过的命令，它再要一次，就再跑一次。
三个子 Agent 都要看同一个文件，这个文件就被打开三次。

这里面没有哪一条是明摆着错的。值不值得修，取决于几个数字，而这一章接下
来就是去把这些数字取回来。

---

## 先该问的那个问题

要不要做缓存，通常是靠讲道理决定的。这道理讲起来总是很有说服力：命令会
重复，进程很贵，所以要缓存。每一步都站得住，结论照样可以一文不值——因为
"命令会重复"是一句关于工作负载的断言，而没有人去查过。

有更好的办法，而这个仓库从阶段 02 起就一直在往那个方向铺路。**trace 逐
条记下了每一次工具调用的确切命令、它们的先后顺序，以及各自花了多少。**
缓存决策要依赖的东西，全都在里面了。所以在写缓存之前，你可以先写评估
器，把它对准你录下来的每一个会话，然后拿到你本来会有的命中率——用的是你
自己干过的活，不要 API key，什么也不用跑。

`--cache-audit` 就是这个东西：

```sh
./agent12 --cache-audit .work/*.jsonl
```

它读每一份 trace，按顺序把 `command_end` 事件挑出来，再把每条命令推过一
个冷缓存。这个仓库里录下来的 16 个会话，107 条命令：

```text
trace                      cmds    hit   miss  stale  refus      saved
esc.jsonl                     1      0      0      0      1         0s
m-delegate.jsonl              4      0      3      0      1         0s
m-inline.jsonl                4      0      3      0      1         0s
mem1.jsonl                    3      0      2      0      1         0s
mem2.jsonl                    0      0      0      0      0         0s
p-pipe.jsonl                  1      0      0      0      1         0s
p-steps.jsonl                 1      0      0      0      1         0s
p-strict.jsonl               23      0     21      0      2         0s
s05-compact.jsonl            17      2     15      0      0      217ms
s05-nocompact.jsonl           6      0      6      0      0         0s
s05-roomy.jsonl               6      0      6      0      0         0s
sb.jsonl                      3      0      2      0      1         0s
x-none.jsonl                  8      0      8      0      0         0s
x-roomy.jsonl                 8      0      8      0      0         0s
x-tight.jsonl                11      1     10      0      0       88ms
x-tight2.jsonl               11      1     10      0      0       96ms
TOTAL                       107      4     94      0      9      401ms

hit rate 3.7% of 107 commands · 21.0kB of output not re-read · 401ms of command
time not re-run
```

**107 条命令，4 次命中，省下 401 毫秒。**

记住这个数。后面写的每一句，要么是在解释它为什么这么小，要么是在论证这
东西还是该做。

这次审计有两处局限，两处都值得点名，因为它们都不会自报家门。

trace 记的是 Agent 跑了什么，不是它底下的磁盘干了什么，所以审计没法知道
某个文件是不是在会话中途变过、本来会让一条记录失效。于是它数出来的命中
是个上界。在这份样本上这不影响什么——没有任何东西写过任何东西——但换成
一个会改文件的会话，它就有影响了。

第二处很快就咬到了这个工具自己。**拿一份录制时就已经开着缓存的 trace 去
审计，报出来的命中是零。** 命中不发 `command_end`（理由在本章后面论），
所以审计只看得见真跑过的那些命令，而那些命令按定义就两两不同。同一个
任务跑两遍量到的：没开缓存那一遍录下的 trace，审计出 47 条命令里命中 9
次；开了缓存那一遍——它真的服务了 12 个结果——审计出 44 条里命中 0 次。

两边都没错。审计真正在问的是“一个冷缓存对这些命令会做什么”，两个数
都是这个问题的正确答案；只不过第二个答案是*做不了多少，因为有意思的那几
条已经不在了*。去审没开缓存的 trace，否则你量的是一份已经被拿掉重复的
会话。

## 一条命令到底值多少

401 毫秒是个毫无意义的数——但要看出这一点，你得先知道拿它跟什么比。
还是那 16 份 trace：

| | |
|---|---|
| 跑过的命令 | 107 |
| 命令总耗时 | 10,041 ms |
| 命令耗时中位数 | 92 ms |
| 最慢的一条命令 | 182 ms |
| 写进上下文的命令输出 | 401,783 B |
| 模型调用 | 173 |
| 模型总耗时 | 864,374 ms |

**十秒的 shell，对十四分钟的模型。**两者加起来，命令占 1.2%。
一个能把*每一条命令*都消掉的缓存，也只能让它们快 1.2%；而你真做得出来的
那个，消掉的是这 1.2% 里的 3.7%，也就是万分之四。

这不是关于缓存的事实。这是关于 Agent 的时间都花在哪儿的事实，而在给这样
一个循环做任何优化之前，值得先把它装进脑子里。工具是 bash，命令是
`sed`、`wc`、`cat`、`ls`、`grep`，对着几十 kB 的文件跑。这份清单里没有慢
的东西。慢的东西是网络另一头的那个语言模型，而且慢三个数量级。

要是你的命令是 `npm install`、一整套测试，或者一次打到另一个地区的数据库
查询，这一章里每个数字都会变，缓存也就明摆着值得做。仪器本身才是重点：
它告诉你，这两个世界里你身处的是哪一个。

## 那四次重复是从哪来的

四次命中，少到可以一次一次拿出来看，而这么看比那个比率本身更说明问题。

其中两次在 `s05-compact.jsonl` 里。按顺序排出来，把压缩事件也留在里面：

```text
turn   2   sed -n '1,150p' wire-notes.md
turn   4   sed -n '151,300p' wire-notes.md
turn   6   sed -n '301,450p' wire-notes.md
           << 压缩 >>
回合  7-10  又读了四次，没一次是重复
turn  11   sed -n '601,731p' wire-notes.md
           << 压缩 >>
turn  12   sed -n '1,150p' wire-notes.md        <- 回合 2 的重复
turn  13   sed -n '151,300p' wire-notes.md      <- 回合 4 的重复
```

模型读了一个文件的头三百行，摘要器把那几个回合换成了一段讲它们的话，然
后模型把同样这三百行又读了一遍。另外两次重复在 `x-tight.jsonl` 和
`x-tight2.jsonl` 里，形状一样，起因不同：用户发来第二条消息，模型把它在
第一条消息下读过的文件重新读了一遍。

所以 Agent 产生的重复，不是那种随手多做一遍、缓存客客气气替它吸收掉的冗
余。**那是模型在把自己弄丢的东西找回来**，而它弄丢东西的方式只有两种：
压缩，以及回合一个接一个地过去。这件事对设计是有后果的，而且它是这一章
里唯一一处，一旦想错就错得很有意思的地方。

诱人的优化是：拿一个指针、而不是那堆字节去回答一次重复——"你在回合 2 跑过
这条，输出就在上面"——这样省下的除了进程还有上下文窗口。在这里行不通。模型
之所以把这条命令重跑一遍，*正是因为先前那份结果已经不在它眼前了*。指向
一条被压缩掉的消息的指针，就是指向空无一物的指针，而它恰恰在产生这次重
复的那种情形里失效。

于是就只剩下一种缓存：把同样的字节还回去。它省下了进程，在上下文窗口上
一个字节也没省——那 5,447 个字节反正都要进对话记录。**结果缓存是挂钟时间
上的特性，不是 token 上的特性。**谁跟你说不是这样，那就是没去看这些字节
最后落在哪儿。

## 两条命令什么时候是同一条命令

键是个哈希，凡是能改变答案的东西，都得待在里面。

```go
func keyOf(shell, wd, command string, maxOutput int, env []string) string
```

命令本身不用解释。另外四个，每一个值一句话。

**工作目录**，因为 `cat notes.md` 在两个目录里问的是两个不同的问题；而
Agent 只要有可能在不止一个地方跑命令，不把它放进去，就会拿这个目录的答案
去回答那个目录。

**shell**，因为 `bash` 和 `dash` 在足够多的地方意见不合，而你拿到的是哪
一个，由 `findBash()` 说了算，它又取决于这台机器。

**输出预算**，因为存下来的不是命令打印了什么——是那份*渲染过*的结果，已
经按 `--max-output` 截断过，也已经带上了它那行 `[exit 0 · 92ms]` 页脚。
模型读到的就是这些字节。同一条命令换一个预算，产出的字节就不一样。

**环境变量**，因为 shell 会把它继承下去，而程序会去读它。`sort` 认
`LC_ALL`，`grep` 从前认 `GREP_OPTIONS`，而这份名单是列不完的。

那么现在：这四个里有三个，在进程跑着的时候根本变不了。Agent 从不切换目
录，`findBash` 只跑一次，flag 在启动时就解析完了。把常量塞进缓存键，看着
像迷信。

它是给下一个特性买的保险。等哪天有人把这个缓存持久化到文件，或者给子
Agent 各自的工作目录，又或者让 `--max-output` 在会话中途可调，它们就不再
是常量了——而只是*碰巧*正确的那个键，会开始不声不响地返回错的答案。现在
就把它们背上，代价是每次查找 11.7 微秒，这个数下面会测，等于没有。

哈希之前先给环境变量排序，同样不是装饰。`os.Environ()` 对顺序不作任何承
诺，而一个会因为两个毫不相干的变量换了位置就跟着变的键，就是个永远不命
中、也永远不解释自己为什么不命中的缓存。

## 命令到底读了什么

真正难的地方在这里。

要判断一个答案是不是还成立，你得知道那条命令读过什么。工具带 schema 的
时候——`read_file(path)`——这是一个字段。换成 bash，一般情况下这件事不可
判定。`grep -r foo .` 读的是一整棵树，而没有哪个参数点出过它的名字；
`cat "$F"` 读的那个文件，名字在变量里。一条命令可以去读时钟、读网络、读
进程表，也可以读另一个程序的输出。

阶段 08 从安全那一侧撞上的是同一堵墙，当时的说法是：*靠读命令，你保不住
一个 shell*。墙是同一堵。不一样的是，你被允许朝哪个方向摔下去。

一份拿不准就放行的安全黑名单，会让危险的东西跑起来。一份拿不准就拒绝的
缓存白名单，只是把这条命令照跑一遍——而那正是压根没有缓存时本来就会发生
的事。**所以整条准入规则是拿拒绝搭出来的**，而且它被允许朝一个方向、并
且只朝这一个方向犯傻。

### 看不懂就拒绝的 parser

`splitPipeline` 认识单引号、双引号、反斜杠转义和管道符。除此之外的一切
都是错误：

```go
case '$', '`', ';', '&', '<', '>', '(', ')', '{', '}', '\n', '\r', '#',
     '*', '?', '[', ']', '~', '!':
    return nil, fmt.Errorf("unsupported shell character %q", string(c))
```

重定向、命令替换、变量展开、子 shell、控制操作符和 glob，全都落在这一行
上。glob 和控制操作符待在一起，理由是相关的，但不是同一个：`cat *.md` 点
名的是一组文件，而这组文件是由 *shell* 解析出来的，所以这个函数报出去的
路径并不是命令真正读的路径——目录里冒出一个新文件，答案就变了，而记录在
案的见证一个都没变。

它不是 shell，也绝不能长成一个 shell。哪天它非得支持 `$(...)` 才有用了，
诚实的修法是阶段 08 那个真正的解析器，不是在 switch 里再加一个 case。

### 白名单的单位不是程序

显而易见的设计，是列一份只读程序的名字清单。而这份清单上的十一个程序里，
有两个光按名字判断就是错的。

`sed` 是读，`sed -i` 是就地改文件。`sort` 是读，`sort -o` 把输出写进一个
文件。按名字来的白名单会把这两条都放过去，然后把一次写操作的结果缓存起
来。

所以规则的单位是一个程序，*外加*它被允许收到的那一组确切的 flag；碰上不
认识的 flag，是拒绝，而不是耸耸肩放过去：

```go
"sort": {boolFlags: set("-n", "-r", "-u", "-h", "-b", "-f", "-V", "-g"),
         valueFlags: set("-k", "-t", "-S")},
```

`-o` 不在那张表上，而且它不需要被点名禁掉。它被拒，是因为它没被允许——正
是这条性质让规则维护得下去：2029 年谁给 `sort` 加了个新 flag，它在发布当
天就会被拒，这里一个字都不用改。

有两条规则带的东西不止 flag。`grep` 不许收 `-r` 或者 `-R`，因为递归 grep
的见证集是一整棵树，而一份路径清单装不下一棵树——一个悄悄缺了东西的见证
集，比没有缓存更糟：它产出的是理直气壮的失效答案，不是慢一点的正确答
案。`sed` 带一段脚本，而 sed 脚本就是程序：

```go
func sedScriptSafe(script string) error {
    if i := strings.IndexAny(script, "wWrRe"); i >= 0 {
        return fmt.Errorf("script contains %q, which could be a file or exec command", script[i])
    }
    return nil
}
```

`w` 把模式空间写进文件，`r` 读一个文件进来，`e` 执行一条 shell 命令。这
个检查看的是每一个字符，而不是命令的位置——因为要判断某个 `w` 到底是不是
命令，就等于写一个 sed 解析器。

### 有一次拒绝是错的，故意的

这条规则会拒掉 `sed -n '/word/p'`——它读一个文件，什么也不写。它分不清
"word" 里的那个 `w` 和 sed 的 `w` 命令。

这笔交易是对的，而且值得把理由摊开说。一次错误的拒绝，代价是多跑一条命
令：按前面量到的中位数，92 毫秒。一次错误的接受，是往用户的磁盘上写东
西，然后再把这次写操作从缓存里端出来。有一个测试专门断言了这次拒绝，这
样谁想"修好"它，就得先删掉一条自己解释了自己的断言。

### 这条规则实际拒掉了什么

在那 107 条真实命令上，审计报出来的是：

```text
refused, by reason:
    4  unsupported shell character "*"
    3  unsupported shell character ">"
    2  unsupported shell character "{"
```

九次拒绝，而**没有一次是冲着程序去的**。十六个会话里模型跑过的每一条命
令，用的都是 `sed`、`wc`、`cat`、`ls`、`find` 或者 `grep`——六个程序，全
是读的，其中五个在清单上。规则真正把拒绝花在了 shell 语法上：四个
glob、三处重定向（两个 `2>&1`，一个 `2>/dev/null`），还有两条
`find ... -exec ... {} +`。

第六个是 `find`，它是故意*不*在清单上的；而它没出现在这份统计里，是一
个值得知道的巧合：它出场的三次，全都先被分词器拒了——两次是因为 `-exec`
里的 `{}`，一次是因为 `2>/dev/null`。程序那一层的检查根本没看到它。同一条
命令被两条互不相干的规则拒掉，看上去就像只有一条规则在干活，而这份统
计告诉不了你到底是哪一条开的火——这是这份报告的局限，不是规则的。

这正是一份拒绝统计能教给你的东西，也是审计为什么要打印一份。命中率是一
句判决；拒绝理由是一张待办清单。它点名了那条得长大的规则，再让你自己决
定，让它长大值不值。在这里，支持 glob 能换来 107 条里的四条，所以一点
也不值，规则就保持小。

这张单子上确实有一条被真动了手，而两者的差别就是你为什么该看统计而不
是只看命中率。拿给这一章跑的那几场会话去审计，报出三条拒绝：
`grep: unknown flag -oE`、`-oP`、`-noiE`。那不是三次意外，那是规则不知道的
同一件事——`-oE` 就是 `-o` 加 `-E` 挤在一起，而短标志模型就是这么写的。
把一串拆开是八行的事，而且只有每个字母都已经在那个程序的布尔标志清单
上才放行，所以 `grep -oP` 仍然因为那个 `-P` 被拒，`grep -om` 也仍然是拒，
而不是去猜 `-m` 的值跑哪儿去了。四个 glob 是意外；三个挤在一起的短标志是一
类。

这份样本有一点得说在前面：这些会话领到的任务都是读，所以命令 100% 是读
操作——这不是普遍数字。一个又改文件又编译的会话，长相和这里完全不一样。

---

## 这个答案还成立吗

见证，是答案所依赖的一条路径，外加命令跑的时候这条路径的摘要。查缓存的
时候重新算一遍摘要，比对。

有意思的问题是摘要该怎么算。便宜的答案——几乎每一份实现伸手就拿的那个——
是 `(size, modification time)` 这一对。它是 `stat` 上的两个字段，而且不
用读文件。

### 大小加修改时间看不见一次改写

失败的形状是：一次时钟 tick 之内、长度不变的改写。先写 `route2:x`，再写
`route3:y`。长度一样，字节不一样。要是这两次写都落在文件系统实际记录的
那个分辨率的同一个 tick 里，两边的 stat 结果一模一样。

听起来像是那种得倒霉才会输掉的竞态。在这台机器上，是得走运才赢得了。两
千次背靠背的试验：

```text
P2 same-length rewrite, back to back
   1498/2000 rewrites were invisible to (size, mtime)
   the bytes differ every time: "route2:x" -> "route3:y"
```

**四分之三**——上面打印的那一跑是这个数。这个数稳得足以拿来做判断，
但稳不到可以报到三位：同样两千次试验连跑五遍，得到的是 1440、1442、
1449、1456、1457——大约 72%——而在机器忙着干别的事时跑的那一遍是
1087，也就是 54%。这个数随着这个进程被允许跑多快而动，而这本身就是在提
示到底量的是什么。

原因就在它上面那个探针里：

```text
P1 mtime granularity
   1897 writes in 300ms produced 555 distinct mtimes
   smallest gap between two distinct mtimes: 501200 ns (501.2µs)
   median gap: 527000 ns (527µs)
   writes that landed on an mtime a previous write already had: 1342
```

这台机器交回来的修改时间，是以差不多半毫秒为一步往前跳的，所以 1,897 次
写里有 1,342 次——70.7%——被盖上了某次更早的写已经用过的时间戳。这不是
NTFS 存的那个 100 纳秒分辨率；这是文件系统写下的那个时间戳实际被更新的频
率，而它是这台正在运行的系统的性质，不是磁盘的性质。

换成 FAT 或者 exFAT 卷，粒度还要粗得多。有一个已经上线的 Agent，给工作区
做快照的时候，凡是落在它自己那次索引保存**两秒**以内的修改时间，一概不
信，理由正是这一条；它源码里那个常数带的注释写着，这说的是 FAT 的粒度，
不是时钟偏差。

不拿时间戳当地基，还有第二个理由，和分辨率无关：时间戳是可以设的。
`os.Chtimes` 是一次调用，`touch -r` 是一条命令，而会保留修改时间的编辑
器，一点也不稀奇。机器上随便哪个程序都能伪造的见证，不是见证。

### 正确的那个检查要花多少钱

另一条路是把文件读出来算哈希。常见的反对意见是这要贵上好几个数量级，那
就把数字摆出来——两边放在同一轮里测，这样不管机器在拿时钟做什么，两边一
起受影响：

```text
file                                  bytes        stat   read+hash   ratio
go.mod                                  149      16.9µs      34.3µs    2.0x
docs/00-loop.md                       11801      16.9µs        40µs    2.4x
docs/wire-notes.md                    49616      17.8µs      68.1µs    3.8x
```

**两到四倍，不是一百倍。**在 Windows 上，`stat` 不是朝 inode 瞥一眼那种
免费动作——它要开一个句柄——所以便宜的那个检查，并没有脑子里的模型以为的
那么便宜；而正确的那个，在 50 KB 的文件上是 68 微秒。对上一条中位数 92
毫秒的命令，这是 0.07%。

所以摘要就是内容哈希。这个决定只花了一次测量，而且胜负毫无悬念。

（两个数都是热缓存下测的；在 Linux 上 `stat` 比 17µs 便宜得多，所以那边
的比值更难看。但那仍然是拿微秒去比一条以几十毫秒计的命令。）

### 目录也是见证

不带参数的 `ls` 读的是工作目录，而它是整份样本里唯一一条从来不带路径跑
的命令。它的见证就是那个目录，而目录的摘要，是对它一层列表的哈希——名
字、大小、模式和修改时间，大致就是 `ls -l` 打出来的东西，也因此大致就是
一次 `ls` 的结果所依赖的东西。

一层，不是一棵树。这就是 `ls -R` 不在 flag 表上的原因。

### 前后各哈希一次，以及为什么只做一次不够

这一块是被一个测试失败逼出来的，而那次失败比修法更有教育意义。

第一版只哈希一次见证，在命令跑完之后，然后把结果按这些摘要存起来。设想
一个文件正在被写，而命令同时在读它。命令产出一个撕裂的结果——一半旧文
件，一半新文件——然后这个结果被按文件*最后落到*的那个摘要存了下来。下一
次查询找到了对得上的见证，端出一个从来没对应过这个文件任何一个状态的结
果。缓存现在是理直气壮地错着，而且会一直错下去，直到有什么东西再碰一次
这个文件。

显而易见的订正，是改成在读之前哈希。这样永远不会端出错的答案，但它带来
另一种失败：在查询和命令之间变过的文件，会被按一个它已经不再拥有的摘要
存下来，于是这条记录从生下来那一刻就是失效的，往后每一次查询都会把命令
重跑一遍。安全，而且悄无声息地没用——下一节会讲，这恰恰是缓存最不擅长告
诉你的那种失败。

那就两次都做。进去的路上哈希一次，出来的路上再哈希一次，两边对不上就什
么都不存：

```go
ws := digestAll(witnessPaths(look.before))
for i := range ws {
    if ws[i] != look.before[i] {
        return // it changed under the command; this text describes nothing
    }
}
```

多算一次哈希——68 微秒——而这是唯一一个既不错、也不白搭的版本。

## 什么绝对不能存

**非零退出码。**退出码是一次结果，不是答案；而会重复出现的那些结果，恰
恰是你最不想把它冻住的：一次权限抽风、一个文件正被读的时候被人写了、磁
盘满了一分钟。缓存一个下来，Agent 就被它拴住，直到底下的字节碰巧变了
为止。

反过来的选择也有一份实地报告，而它不是失误——是一次刻意的交易。有一个代
码索引，把解析*失败*按内容哈希缓存了下来，于是一个解析不了的文件再也不
会被重试。把解析器修好，什么也不会被重新索引，因为每个文件哈希出来还是
当初失败的那些字节。他们选了终止而不是正确，并且把这个选择写了下来。这
里的交易方向相反，因为一条失败过一次的 shell 命令，通常下次就会成功。

**超时、取消，还有没回收干净的进程树**，理由一样，而且更强。这几段文字
没有一段讲的是命令干什么；它们讲的是有一次它遇上了什么。阶段 10 那句
`[TIMED OUT after 30s]`，说的是一个瞬间。

### 两条上限，因为它们在不同的时候用完

缓存同时受两条上限约束：条目数，*以及*总字节数。

只设一条，另一条就没人管，而这两条是被不同的会话耗光的。一个对四百个文
件跑 `wc -l` 的会话，会拿四十字节的答案把条目数填满，永远够不着字节预
算。一个读四个大文件的会话，会拿四条记录把字节预算填满，永远够不着条目
数。长会话里一个不设上限的结果缓存，是一次动机良好的内存泄漏。

这两条上限背后的一般规则是：**凡是 key 空间随输入增长的缓存，都要设上
限。**如果 key 是有界的——一个工作区一条、一个供应商一条——就不需要，
而且不设反而更清楚。

## 没有症状的缓存 bug

上面讲的全是"答错"。这一节讲的是另一种更难发现的失败——缓存还有第二种
坏法，而它不留下任何证据。

某个上了线的 Agent 把 `git log --name-only` 的结果缓存了起来，生存期
（TTL）15 秒。调用它的那一方每 30 秒重取一次。每一条缓存到被问起的时候
都早就过期了，于是命中率精确地等于零，每一份打开的文档每一次都照付那条
0.3 秒的命令。

什么都没出错。没有答错，没有报错，没有日志，没有告警。永不命中的缓存，
行为跟正常工作的缓存一模一样——结果是对的，代码在跑，测试在过。它就这样
跑了几个月。

这就是反对把 TTL 当成*主*机制的理由，而这个缓存默认压根没有 TTL。这里
判定失效靠的是内容：内容是事实，而 TTL 是在猜一件事实还能真多久。

TTL 仍然留着当兜底，而且理由是实打实的：见证集合是命令实际读了什么的
**下界**。它装的是命令行上点了名的路径，而命令可以依赖任何没有路径点到
的东西。TTL 给错答案能在这道缝里活多久划了个上限。它默认关着，是因
为在这种负载上这道缝很窄，也因为 TTL 一旦选歪，会让你赔掉一切，看上去
却一分钱不花。

对付不吭声的这一种坏法，办法一点也不聪明——就是个计数器，而且打出来：

```text
  result cache: 0 hits / 12 lookups (0 refused · 0 stale) · 0B not re-read · 0s not re-run
```

这块面板上别的条件行，值为零就不打，道理是每场干净的会话都顶着一行
"0 retries"，人会练成不看这一行。这一行是例外，而这个例外本身就是要说
的事。没有重试的会话，是什么都没出错的会话；没有命中的缓存，跟正在起作
用的缓存长得*一模一样*，把两者分开的只有一样东西：有人把那个数打了出
来。

同一个道理也解释了为什么 `refused` 和 `miss` 要分开计。连着十次未命
中，是冷缓存在热身，往后会变好。连着十次拒绝，是这个缓存在这种负载上再
跑多久也帮不上忙，往后也不会变好。把它们并进"不是命中"这一格，你就分不
清眼前的是这两种会话里的哪一种——而它们的修法不一样。

## 命中不是命令

由缓存供出的命令会发出 `result_cache` 事件，而**不会**发
`command_start` 或 `command_end`。

照发不误、只多带个标志位，这不过是半行的工作量，而且下游好几处会因此简
单一些：面板上的命令计数、重放的表头、以后任何人照着 trace 写的东西。值
得把这半行买来的东西说清楚——这个 Agent 此后记下的每一场会话里，都会有
一份 trace 说某个进程跑过，而实际上一个都没跑。

trace 要么是证据，要么是装饰。它没法两样都是；从它开始描述没发生过的事
那一刻起，它就只剩下后一样。

看得见的后果是：十次工具调用、其中四次命中的会话，老老实实报出六条命
令，看上去像是有四次调用不见了。所以重放的摘要把命中单独摆成一个数：

```text
trace · 103 events · 2 turns · 1 command · 24.203s · 2 cached
```

两个数，不是一个数，因为这里有两件事实，任何单独的数都装不下两件。上
面那行表头来自一场真实会话：模型被要求读一个文件，再把自己读的东西核
对两遍，于是它发了三次一模一样的工具调用，其中两次从未变成进程。

### 唯一一处，trace 和模型被告知的东西不一样

上面那条规则有一个例外，而它是故意的，不是漏掉的。缓存存的是*渲染好*的
结果，而每一份渲染好的结果末尾都带着一行模型会读的页脚：

```text
[exit 0 · 92ms]
```

把它从缓存里端出去，模型就被告知这次调用花了 92 毫秒，而它实际只花了微
秒。按两段之前那个论证，这就是在描述一件没发生过的事。

它留下来，是因为模型不是 trace。trace 的活是记下发生了什么，而它记了：它
说发生了一次缓存命中，没有命令跑。工具结果的活是回答模型的问题，而“这
个文件里是什么”的答案，不会因为字节是从内存里来的而变。改写那行页脚，意
味着模型对同一个问题看到两个不同的答案，还得自己去想该信哪个——这比一
个它根本用不上的耗时要糟得多。真遇上某个数字对模型确实要紧的情况，诚实
的修法是另一条：那条命令就别缓存。

## 它确实划算的地方

为这一章跑的三场真实会话里，压缩带来的命中一次都没有——这件事值得报出来，
因为审计当初指的就是这种情形。有一场会话的窗口紧到压缩了五次，它把一份
文件分成十二段顺着读完，一段都没重读：摘要器记下了哪些区间已经读过，模
型信了。**摘要做得好的压缩器，会把缓存本来打算吸收的那些重复直接消
掉。**这不是让人失望的结果，这是比缓存更好的修法，而它属于阶段 14。

真正划算的场景，是阶段 07 造出来的那个。四个 Agent——父 Agent 加三个子
Agent——同时被要求读同一份文件：

```text
  38 calls · 44 commands
  prompt tokens billed: 499172  (full 80484 · write 0 · read 418688)
  result cache: 12 hits / 56 lookups (2 refused · 0 stale) · 63.8kB not re-read · 1.107s not re-run
```

**五十六次查询，十二次命中：21%。**按提问的 Agent 分组：

```text
List every JSON field name#1   sed -n '1,300p' wire-notes.md      5449B   99ms
List every HTTP status code#3  sed -n '1,300p' wire-notes.md      5449B   99ms
List every HTTP status code#3  sed -n '301,600p' wire-notes.md    5447B   83ms
List every HTTP status code#3  sed -n '601,952p' wire-notes.md    5448B   90ms
List all section headings#2    sed -n '301,600p' wire-notes.md    5447B   83ms
List all section headings#2    sed -n '601,952p' wire-notes.md    5448B   90ms
...
```

三段区间，四个读者，后到的那个白拿答案。这就是缓存要按指针分享给子
Agent、而不是每个 Agent 各造一份的原因——而分享是个决定，不是默认。阶段
10 就因为反过来的疏忽整整丢了一个特性：子 Agent 的结构体字面量里压根没
列 `dl`，于是子 Agent 全跑在所有 deadline 都关掉的状态下，没有任何东西
失败，也没有任何东西说一声。

该不该分享，判据是这件事实是谁的。"这个端点在拒绝调用"是关于端点的事
实，所以供应商的梯子要共用。"这份文件的内容是这些字节"是关于工作树的事
实，而父 Agent 和每个子 Agent 同时都盯着同一棵工作树，所以缓存要共用。
"这段对话有 12,000 个 token"是关于某一段对话的事实，所以压缩器不共用。

## 那到底值多少，精确地算

扇出会话是这个缓存能碰上的最好情况，所以它的数字是天花板，不是平均值：

| | |
|---|---|
| 会话墙上时钟 | 4 m 23 s |
| 模型时间 | 360,656 ms |
| 实际花掉的命令时间 | 3,789 ms |
| 靠缓存省下、没花掉的命令时间 | 1,107 ms |

缓存干掉了 56 条命令里的 12 条，砍掉了 22.6% 的命令时间。拿它去比上面那
张表里的模型时间，是 **0.3%**；比墙上时钟，是 0.4%。随便挑一个——要紧的
是它俩都在哪一列。

同一件任务又跑了一遍，这回把缓存关掉；这个对照值得摆出来，恰恰因为它什
么也证明不了。那一趟跑了 47 条命令，开缓存那趟是 44 条；模型调用少了三
次；输出 token 多了 2,300 个；撞上一次 500，赔进去一次重试；最后
4 m 50 s 收工，对开缓存那趟的 4 m 23 s。非确定的 Agent 跑两趟，量不出
1.1 秒的差别——两趟之间的噪声比效应本身大两个数量级。**算得上测量的那个
数，是从单独一趟的内部拿到的**——有十二条命令没有发生，而且是缓存自己说
的。当你要找的效应比被测对象本身的方差还小，A/B 对照就是演戏，内部计数
器才是证据。

而在同一份摘要里、同一趟跑出来的，还有这一行：

```text
prompt tokens billed: 499172  (full 80484 · write 0 · read 418688)
```

**83.9% 的 prompt token 是从缓存里供出来的。**不是这一个——是阶段 04 那
个，供应商的 prompt 缓存：它早就在那儿了，不需要白名单，不需要见证集
合，不需要分词器，而它干的活是这一章造的这个特性的两百多倍。

这才是阶段 12 真正的教训，而它不是"别做缓存"。它是：**Agent 里那些昂贵
的重复发生在线上，不在 shell 里**，而伸手去够结果缓存的那份直觉，通常
指的是这两者里错的那一个。那八十行仍然值得写，因为你要弄清这件事，办法就是
把仪表造出来、读一遍——也因为在命令要跑三十秒而不是九十毫秒的负载上，同
样这八十行会把答案彻底改掉。

### 缓存自己的开销

便宜到不必参与这个决定，而且是量出来的，不是想当然的：

| | |
|---|---|
| `eligible` —— 分词并检查一条带管道的命令 | 759 ns |
| `keyOf` —— 把命令、cwd、shell、预算和整个环境哈希一遍 | 11.7 µs |
| 50 KB 文件上的一次完整未命中，含前后两次见证哈希 | 73.7 µs |

73.7 微秒，对上中位数 92 毫秒的命令，是 0.08%。这个缓存不划算，原因不
在开销。

## 这一阶段没做到的

- **glob。**九次拒绝里有四次是 `ls *.md` 和 `wc -l src/*.go`。要支持它
  们，就得自己把模式展开，把目录*和*每一个匹配到的文件都记进见证，还得
  把 shell 的匹配规则弄对。在这里它值 107 条命令里的四条；在成天列目录
  的负载上，可能值得多得多。
- **能活过进程的缓存。**这里所有东西都住在内存里，会话一结束就没了——正
  因为如此，shell、工作目录和环境才是常量，也正因为如此，它们照样进了
  key。要持久化，见证集合就得跟着一起活下来，而一条失效的条目从此可以
  比当初支撑它的那份机器状态活得更久。
- **任何模型看得见的东西。**命中对模型是不可见的：它拿到同样的字节，带
  同样的页脚。告诉它"这条是缓存来的"，就是往永久记录里再加一句话，而阶
  段 11 花了一整节讲这为什么是成本，不是礼貌。
- **缓存模型调用。**差一个时间戳的两个 prompt 不是同一个 prompt，而它们
  共享前缀的那种情形，供应商自己的缓存已经处理了。prompt 的形状和缓存
  对齐，会在阶段 17 有它们自己的一章。
- **把相同的结果去重。**四个 Agent 各自在自己的上下文窗口里拿到了同一段
  文本的 5,449 字节副本。缓存省下的是那次读，不是那些 token。那是另一
  套机制，有另一套失败模式。
- **Windows 上的可见性保护。**某个上了线的 Agent 在子进程退出之后先睡
  200 ms，再去给工作区拍快照，理由是子进程写下的东西可能还看不见。这台
  机器上两百次试验，需要重试的次数是零，所以这道保护没有做——为了防一件
  你复现不出来的事，每条命令赔上 200 ms，在你能复现它之前都是笔亏本买
  卖。

## 练习

1. **审计你自己的 trace。** 拿 `--cache-audit` 跑一遍你前面几个阶段留下
   的每一份 trace。如果你的命中率也在 5% 以下，那你刚刚省下的，是拿一周
   时间去把这件事用贵的方式弄明白。如果是 30%，你就知道了一件关于自己负载
   的事，而这件事靠推理是推不出来的。
2. **让见证说谎。** 缓存一次 `cat notes.md`，改完这份文件之后，用
   `touch -r` 或者 `os.Chtimes` 把它的修改时间设回原来的值。内容哈希会
   抓住它。现在把 `digestOf` 改成返回
   `fmt.Sprintf("%d:%d", size, mtimeNs)`，再看同一串动作把旧字节供了出
   来。
3. **给它配个坏 TTL。** 拿 `--cache-ttl 2s` 跑一场会话，让它的重复间隔
   比这更远。一切正常，结果都对，命中率是零——而你之所以看得见，只因为
   摘要把它打了出来。然后找出仍然能命中的最小 TTL。
4. **删掉一道上限。** 把 `--cache-entries 0` 设上，跑点会列出很多文件的
   东西，盯着进程占用。然后改成 `--cache-bytes 0`，读几份大文件。两道上
   限拦的是不同的会话，所以拿掉其中任何一道，都不是"半个问题"。
5. **把双重哈希弄坏。** 让 `store` 跳过前后对比，然后对着一份正被后台循
   环反复重写的文件跑命令。去找那种供出来的结果——它跟这份文件的任何一
   个版本都对不上。
6. **把规则放宽。** 加上 glob 支持：展开模式，把目录和每一个匹配项都记
   进见证。再跑一遍审计，看看那四条命令到底值多少。
7. **找出这东西能赢的负载。** 把 Agent 指到某个大到 `grep -n` 一遍就要
   一秒以上的仓库上，交给它一件需要反复搜索的活，再拿审计报出的省时数
   字，跟这里量到的 401 毫秒比一比。

## 读完这一章，你能回答什么

**在这样的 Agent 里，结果缓存为什么这么不值钱？**
因为时间不花在命令上。十六场记录下来的会话里，107 条命令一共
10,041 ms，173 次模型调用一共 864,374 ms——大约 86 比 1。把每一条命令
都干掉，能省下 1.2% 的墙上时钟，而实际拿得到的命中率是 3.7%，值
401 ms。要是你的命令是慢命令，整幅图就完全变了。

**怎么在造出来之前就知道缓存有没有用？**
把你手上已有的 trace 里的命令，喂进冷缓存重放一遍，然后数。
`--cache-audit` 干的就是这件事：不要 API key，不要模型，什么都不用真
跑。它数出来的命中是上界，因为 trace 不记录会话底下磁盘发生了什么变
化。

**Agent 到底为什么会重跑命令？**
在这份样本里，从来不是随机的。四次重复无一例外，要么跟在一次压缩后面，
要么跟在一条新的用户消息后面——是模型在找回它丢掉的东西。所以拿"你已经
跑过了，见回合 2"去回应一次重复，不可能管用：它指过去的那个结果，恰恰
就是已经不在那儿的东西。

**结果缓存省 token 吗？**
不省。命中返回的是同样的字节，所以记录长出来的量，跟命令真跑过一模一
样。它省的是进程和墙上时钟。在那场扇出会话里，就算缓存在命中，四个
Agent 也还是各自收到了同一段文本的 5,449 字节副本。

**缓存 key 里该放什么？**
所有能改变答案的东西：命令、工作目录、shell、输出预算（因为存下来的是
渲染并截断之后的结果），还有环境——环境要排序，好让顺序不携带信息。这里
面有三样在今天的单个进程里根本变不了，它们照样在 key 里，因为只是碰巧
正确的 key，会在有人加特性的那天一声不响地坏掉。

**为什么不能直接检查一条命令是不是只读的？**
理由和阶段 08 判断不出一条命令危不危险是同一个：命令是程序，而读一遍程
序说明不了它会干什么。区别在于失败往哪边倒。缓存被允许朝拒绝那一边失
败，所以这条规则会拒掉每一样它没有完全弄懂的东西——每一个 glob、重定
向、替换和子 shell，外加任何没被明确列出来的程序或 flag。白名单管的是
flag 而不是程序名，因为 `sed` 读而 `sed -i` 写，`sort` 读而 `sort -o`
写：一份按名字来的清单，会在它上面十一个程序里的两个上判错。在 107 条真
实命令上，这条规则拒了九条，全是因为 shell 语法，没有一条是因为程序。

**怎么判断缓存下来的答案还成不成立？**
把命令点了名的每一份文件的内容哈希一遍，哈两次。不用 `(size, mtime)`：
在这台机器上，2,000 次同长度重写里有 1,498 次对这一对是隐形的，因为时
间戳是按大约半毫秒一格往前跳的，70.7% 的写落在了某次更早的写已经用过的
时间戳上——何况机器上任何程序都能把时间戳设成它想要的值。读加哈希的开销
是 `stat` 的 2.0× 到 3.8×，17 µs 对 34–68 µs，是一条 92 ms 命令的
0.07%。之所以要两次：只在命令跑完*之后*哈希，会把一次撕裂的读按文件最
终的摘要存下来，然后照供不误；而只在*之前*哈希，存下来的条目在诞生那一
刻就已经失效了——安全，而且不声不响地毫无用处。

**哪一种缓存失败不留任何证据？**
永不命中的缓存。没有错答案，没有报错，没有日志——它跟正常工作的缓存无从
分辨。某个上了线的 Agent 拿 15 秒的 TTL 对着 30 秒一次的重取，跑了几个
月，命中率 0%。防线是数命中，并且哪怕是零也把这个数打出来——这是这块面
板上唯一一行"什么都没有也照样显示"的行。

**为什么缓存命中不发 `command_start` 和 `command_end`？**
因为没有命令开始，也没有命令结束，而一份记录了从不存在的进程的 trace 不
是证据。代价是：十次调用、四次命中的会话报出六条命令，所以命中在重放的
表头里单独占一个数，而不是被折进命令计数里。

**这个 Agent 里，真正在干活的是哪一个缓存？**
阶段 04 那个，供应商的 prompt 缓存。就在同一场扇出会话里，结果缓存从
361 秒里省下了 1.1 秒——0.3%——而 499,172 个 prompt token 里有 418,688
个是 prompt 缓存供出来的，占 83.9%。Agent 里那些昂贵的重复发生在线上，
不在 shell 里。

## 思考题

1. 见证集合是下界：它装的是命令行上点了名的路径，而命令可以依赖任何没
   有路径点到的东西。要把它变成上界，你得观测什么，代价又是多少？你的
   Agent 会跑的那些工具里，哪几个仍然能把它破掉？
2. 命中返回的是同样的字节，所以上下文窗口长出来的量，和命令真跑过分毫
   不差。设计一套连 token 也一并省下来的机制，然后决定：在压缩之后的那
   个回合里，模型再次发问，而它发问的原因恰恰是它已经看不见先前那份副
   本了——这套机制该怎么办？
3. 这个缓存在父 Agent 和子 Agent 之间共用，理由是工作树是它们共同观测的
   同一件事实。等到子 Agent 有了自己的工作目录、自己的容器、或者自己的
   机器，这条理由会怎么样？而要让共用继续是正确的、而不只是继续能跑，
   key 里得多出什么？
4. 拒绝统计是一份待办清单，在这里它说 glob 值 107 条命令里的四条。在什
   么样的负载下，这份统计足以撑起一个真正的 shell 解析器？而要知道自己
   确实越过了那条线、不是猜自己越过了，你得量什么？
5. 这个仓库里有两个特性都叫"缓存"，而它们互相毫无关系。在你自己在做的
   系统里，再找出一对这样撞名的东西，然后弄清楚：这种混淆有没有已经害
   谁拿到过一个错的数字——判据是这两样有没有被打在过同一行上。
