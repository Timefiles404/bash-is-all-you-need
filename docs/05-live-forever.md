# 阶段 05 — 永久存活

一个 Agent 有三个记忆地平线，三个都需要：

```
within a request   the messages array                        stages 00–04
within a session   compaction, when the array outgrows the window
across sessions    a file
```

第三个需要一段话。第二个占了本章剩下的部分，并
结束在你可能没预料到的地方：**上下文压缩没省钱。**
在一次对照实验中，它的成本比做同样的工作多了 25%。
那个结果不是实现中的 bug，它改变了上下文压缩的用途。

---

## 长期记忆是一个文件

`AGENTS.md` 和 `MEMORY.md` 在工作目录里，启动时读入，
追加到系统提示词。Agent 用它已有的工具写第二个：

```sh
printf '\n- the test suite needs CGO_ENABLED=1 or three packages fail to link\n' >> MEMORY.md
```

这就是全部特性。没有存储，没有嵌入，没有检索步骤，
没有对 `grep` 能处理的语料库进行相似度搜索。

分割的标准是**作者**，不是内容。`AGENTS.md` 由人
为 Agent 写——约定、构建命令、什么不要碰。`MEMORY.md`
由 Agent 写给未来的自己。把它们分开意味着一个人可
以查看 Agent 决定记住的东西，不用看完自己的指令，
也可以用编辑器删除一个坏记忆。一个往人类文件里写
的 Agent，最后会跟它吵架。

选择一个文件会带出三件事，最后一件是有趣的。

**一个文件是可 grep 的、可 diff 的、可查看的、可版本管理的、可手工编辑的。**
这五个属性是向量索引没有的，代价是一个你不需要的
相似度搜索。

**机制虽然简单，策略问题却不会因此消失。**完全
交给模型自行判断，记忆几乎从来不会被写下——当前回
合里没有什么会奖励这么做。每个真正积累出有用记忆的
Agent 都有一个显式触发器。这一个有 `/remember`，系
统提示词里也有一条规则，决定这份文件在六个月后是
否还值得读：

> 记录你学到的东西，不是你做过的东西。

这就是知识库和日记的区别。

**记忆是上下文注入，而被注入的上下文会被相信。**
看看第一次真正运行时发生了什么。Agent 在 `sandbox/s05`
启动，带着一份仓库 `AGENTS.md` 的副本——一个描述
**仓库**的文件，提到像 `docs/wire-notes.md` 这样的路径。
Agent 被要求数一数 `wire-notes.md` 的行数——这个文件
明明就在工作目录里——结果它运行了：

```
  $ wc -l docs/wire-notes.md
  │ wc: docs/wire-notes.md: No such file or directory
```

没有任何东西故障。记忆文件说 `docs/`，模型信任它
的系统提示词里的一句话，胜过信任它站着的目录。这
是正确行为，也是风险：**一个记忆文件不是笔记，它是
模型在看之前就会行动的一个断言。**这样廉价的缓解措
施就值得做——每行都注明日期，好让过时的行能被发现、
删除，把记忆限定在它们真实的地方，把文件保持得足够
短，让人实际会去读它。

**这个会话写的记忆，在下一个会话之前是不可见的**
——那是一个缓存决定，不是疏忽。记忆活在系统提示词
里，所以在会话中途重读文件会重写前缀，使 stage 04 赚
到的一切失效。一个回合的延迟，换来一个会话的缓存
命中，是这笔交易正确的一方。值得记住，这是你自己
做的选择。

---

## 上下文被允许去的地方

这是本章不关于上下文压缩的一半，也是你每天都会
用的一半。

每一块注入的上下文是两件事之一，不同点不是它包含
什么，而是**它的值改变得多频繁**：

| | 去向 | 成本 |
|---|---|---|
| **对会话稳定的** — 记忆文件、cwd、操作系统、shell | 系统提示词，在缓存断点之前 | 它的 token，一次，无论会话运行多久 |
| **易变的** — 时钟、git HEAD、工作树的脏状态 | 消息创建时冻结进该消息 | 它的 token，每回合一次，永久 |

第二行是人们会搞错的地方，而且错的方向正好是烧
钱的那个方向。本能是保持易变上下文**新鲜**——在每个
请求上重新计算时间戳，好让模型总是知道时间。那是
stage 04 的 `--break-cache` 实验，它测出了 3.4x。

决议是"新鲜"和"在前缀里"是两件你不能同时拥有
的东西——新鲜度是你能几乎免费放弃的那个：

> **注入一次并冻结。永远不要重新计算已经在前缀里的东西。**

快照是在用户按下 Enter 时取的，对它所属的整个回
合都准确，之后在历史里保持不变，这正是字节稳定前
缀的意思。模型每回合都能得到新鲜信息，**并且**缓存
还能存活，因为每个回合的快照是一个不同的永久行，
而不是同一行带着一个移动的值。下面是这样一份快照
在真实对话中间的样子——取自它被记录三个回合之后：

```
  [3] user
  │ <now>2026-08-27 04:38:53 +0800</now>
  │ <git branch="main" dirty="3">Stage 04: the cache</git>
  │
  │ 2. sed -n '91,180p' wire-notes.md
```

还要注意 `cwd` 在这条线的哪一边。它是稳定的——因为
shell 不持久，所以在命令内 `cd` 不能移动它（stage 00）。
给 Agent 一个持久 shell，cwd 就变得易变，得挪到另一
行去。执行模型中的改变，直接传播到缓存布局。

## 不用分词器数 token

上下文压缩需要在**发送之前**知道 prompt 有多大。
通常建议是自带一个分词器。对于这份工作那是错误的
工具：它是一个大的、每模型的依赖，在工具模式和消
息包装的框架开销上，它跟服务器的算法对不上；它告
诉你的，没有一样不能免费得到——因为**每个响应都已
经包含了你刚发送的 prompt 的确切 token 数。**

所以改为测量。注意你发了多少字符，注意服务器说
那是多少 token，记住比率，每次调用都更新它。

```go
func (a *agent) runTurn(msgs []Msg) []Msg {
    sentChars := convChars(msgs) + base
    res, err := a.call(turn, msgs)
    ...
    a.comp.est.observe(sentChars, res.Usage.Prompt())
}
```

微妙的部分，也是它一切工作的原因：**估算器不需
要准确，它需要一致。**它自始至终只被问一件事——"我
们是不是快到墙了"，而它拿来校准的，正是后来要求它
换算的那同一个字符数。系统偏差——JSON 包装、工具
模式、系统提示词——被吸收进比率，而不是累积为错误。
会破坏它的，是测一件东西而估另一件。

仪表板会把实时比率打印在上下文水位线旁边，好让
你看着它稳定下来：

```
  └ context 5893 / 12000 (49.1%) · ≈3.7 B/tok
```

它在那个会话开始是 3.3，当对话从系统提示词移动
到 Markdown 时爬到 3.7——一个会话内 11% 的漂移，单
向。任何固定除数，在一端或另一端总会错；测量出来
的那个，两端都不错。

### 它真的工作吗？

一个真实运行里的三次上下文压缩。每一次都预测它
刚产出的对话的大小；紧接着的下一个调用，就报告了
它实际花费的：

```
  predicted ~3556   billed 2842   +25.1%
  predicted ~3823   billed 3624    +5.5%
  predicted ~3332   billed 3256    +2.3%
```

第一个很差，理由比数字还值钱：那时估算器只有七
个样本，是在 prompt 大多还是系统提示词的时候取的，
而它被问到的却是一个大多已经变成 Markdown 的对话。
再经过两次上下文压缩，它就收敛了，并稳定在 6% 以内。

一个综合检查把它钉得更硬。针对一个假供应商——它
按 `chars/2.9` 收费，还加收一个 700 token 的包装开销，而
这个开销估算器永远不会直接看到——十轮校准之后，它
预测出**21,708 个 token，对应 21,389 个账单 token——偏
差 1.5%**，而它从来没被告知过除数或开销本身。

对于一个阈值检查，6% 是免费准确度。把阈值设在
70% 而不是 78%，你是拿一份本来就想留的余量，把这
点误差的账付清了。

## 你被允许切的地方

这一部分会在真实 Agent 里产生真实的 bug，而这个
bug 的形状，正是它难找的原因。

上下文压缩用一个摘要替换 `msgs[:cut]`。不是每个
`cut` 都合法：

**1. `msgs[cut]` 一定不能包含工具结果。**它的匹配工具
调用活在 `msgs[cut-1]`，即将被删除。一个调用消失的工
具结果是孤立的，两个协议都拒绝它——OpenAI 用 *"messages
with role 'tool' must be a response to a preceding message with
tool_calls"*，Anthropic 用一个意外的 `tool_use_id`。

**2. `msgs[cut]` 一定是一个 Assistant 消息。**摘要被注入
为一个用户消息，所以在另一个用户消息前切，会产生
两个用户消息连在一起。某些端点合并它们，某些拒绝，
合并的做法彼此也不同。

两条都可以归结成一条你能装进脑子里的规则：

> **一个对话只能在一个 Assistant 回合之前切开。**

现在说说它为什么难找。上下文压缩在回合 14 发生。
畸形请求在回合 15 出去。错误信息指向的是请求构建
器。栈踪迹里没有什么提到压缩器，而那个能重现它的
对话已经不再存在，因为它被压缩了。**bug 离它的症状
一百行远，还晚了一个回合。**

所以它由一个不变式而不是测试用例保护。`validConversation`
是照着协议的规则写的，特意**不是**照切割逻辑写的，
属性测试断言两者在每个索引上都一致：

```go
for i := range msgs {
    if canCutBefore(msgs, i) {
        got := validConversation(append([]Msg{summaryMsg("s")}, msgs[i:]...))
        // must be ""
    }
}
```

一个和代码出自同样假设写成的检查，总会跟代码意
见一致。一个从另一端写的不会，那正是拥有它的全部
价值所在。对这一对做变异测试，抓住了所有四种破坏
它的手法，包括最重要的一种——删除工具结果检查后，
套件在切点碰巧安全的对话上依然会通过。

### 地板

上下文压缩有一个下限，在它之下你的问题是一个不
同的问题：

```
cannot compact: the newest message alone is ~11400 tokens against a keep budget
of 3000 — lower --max-output or use a command that filters
```

一条比整个保持预算还大的消息，没法被压缩绕过去。
那是一个输出大小问题——stage 01 的截断限制，或者一
个过滤而不是倾倒的命令。

那个代码的第一个版本，为第二种、不同的情况打印
了同样的句子：一个恰好有一条消息空间的预算，这时
候修复该用的是 `--keep`，不是 `--max-output`。**一个错误
消息是一个关于因果关系的声明。**把这一点搞错，你就
不只是没帮上忙，而是在误导人——读者会去改你说的那
个设置，结果没用，于是他们断定诊断是对的，情况没
救了。它现在能区分这两种情况了。

## 摘要

摘要器得到自己的系统提示词，根本没有工具，以及
一个**平铺的**记录，而不是消息数组。

平铺是非显然的选择。传递真实数组看起来更忠实，
行为却更差：给定一个对话，一个模型**继续**它——它
再答一次最后一个问题，或发出下一个工具调用。平铺
把任务从"对话"变成了"读这份文档"。它还让又长的工
具输出能在计费前先被截断，也让这次调用完全不带工
具定义——这样一来，工具调用不只是不被鼓励，而是根
本不可能。

选择标准是值得偷的部分：

> **保留会花工具调用去重新发现的东西。**

这是一个经济测试，不是语义测试，模型用起来也比
"保留重要的东西"容易得多。一个要花三次 grep 才能找
到的文件路径，值一行。Agent 自己的一段叙述则一文不
值，因为重新生成它不费分毫。

长工具输出从**中间**被切，不是从头。一个构建日
志把错误放在结尾；一个栈踪迹把原因放在结尾。留住
两端，就留住了命令一开始宣布的，和它最终得出的结
论，丢掉的是重复的中间部分——那才是长的地方。

### 从一份真实摘要里读出的 bug

第一个版本逐字产出了这个：

```
4. STATE
- Not done: Chunks 2–8 were never run.
```

它是假的，而且是那种只有在生产环境里才会露馅的
假。在那个摘要被写的时刻，块 2**确实**运行过了——它
的调用和输出，就在那四条被**保留**的消息里，而这些
消息摘要器根本没看到。于是模型收到的这段文字断言
某事从未发生——而这段文字的正下方，紧跟着它确实发
生过的证据。

摘要器拿到的是一段前缀，被要求给出一份摘要，回
答时却好像看过整个会话一样。提示词里没有任何东西
告诉它还有别的情况。一句话就把它修好了：

> You are reading only the EARLIER part of the session. More recent messages are
> being kept verbatim and will appear immediately after your summary, and you
> cannot see them. So never write that something was "never done" or "not
> started" as a statement about the session — say "as of the end of this
> transcript".

同样任务，同样模型，下一个运行：

```
4. STATE — Chunk 1 has been read (twice). Chunks 2–8 remain outstanding
           as of the end of this transcript.
```

一般教训不是关于摘要。**一个只看到系统一部分的
组件，会把整个系统都描述出来，除非你告诉它它正在
看的是什么**——而且无论如何，它听起来都一样自信。

## 从一个真实运行

一个任务，三个策略，输入在全部三个臂上是字节相
同的：十个用户消息，从 trace 验证过。

```sh
agent --yolo --window 12000 --compact-at 0.5  --keep 0.25   # tight
agent --yolo --window 12000 --compact-at 0.85 --keep 0.35   # roomy
agent --yolo --window 12000 --no-compact                    # none
```

| arm | compactions | prompt sent | full price | cache read | output | at 0.1x read | wall |
|---|---:|---:|---:|---:|---:|---:|---:|
| tight | 3 | 92,553 | 30,601 | 61,952 | 3,673 | **36,796** | 105s |
| roomy | 1 | 102,315 | 21,739 | 80,576 | 2,004 | **29,797** | 69s |
| none | 0 | 121,850 | 12,858 | 108,992 | 865 | **23,757** | 58s |

读第三和第四列彼此相对。**发最多 token 的臂，付
了最少的钱**，因为它从不破自己的缓存：`none` 整个
prompt 花费里，89% 是十分之一价格的缓存读。

`roomy` 和 `none` 运行了**同样八个命令**——根本没
有混杂——上下文压缩花了：

- **+25% 在全价格等价 token**
- **+132% 在输出 token**（摘要是输出，输出是贵的一方）
- **+19% 墙时钟**

`tight` 更糟，还有一点附带说明：它运行了三个额
外命令（`ls -la`、`cat task.txt` 和一个重复的块）。这三个
全都发生**在它的第一次上下文压缩前**，所以上下文压
缩没有导致它们——那是普通的模型方差——但它们确实
把它的行膨胀了几个百分点。`roomy`/`none` 这一对，才
是干净的比较。

### 缓存悬崖

在 `tight` 臂内，每个调用：

```
  #   kind     prompt   full   read  cached%
  6              5174   1654   3520     68%
  7              5258    138   5120     97%
  8 COMPACT      3310   3310      0      0%      ← the summarising call
  9              2842   2330    512     18%      ← the first call after
 10              2927    111   2816     96%
 ...
 14              5701    133   5568     98%
 15 COMPACT      3383   3383      0      0%
 16              3624   3112    512     14%
 17              3709    125   3584     97%
```

**上下文压缩是一个两调用缓存断电**，它在那张表
里发生了三次。摘要调用根据构造就是一个冷 prompt——
不同的系统提示词，一次性的用户消息，没有什么可匹
配。它后面的调用是冷的，因为前缀刚被重写。第三个
调用回到了 95% 以上。

正因如此，Agent 会在它**被引发**的那一刻打印警告，
而不是等它显现出来的时候：

```
  ≡ compacted: 15 → 5 messages · ~7714 → ~3556 tokens (-54%) · 6976ms
  ! the prompt prefix was rewritten — every cache entry from before this point
    is now unreachable, and the next call is a full-price miss
```

没有那一行，下一个调用上的红条看起来像一个退步，
而不是一个结果。

### 振荡

`tight` 压缩了三次，而 `roomy` 只压缩了一次。算术
如下：

```
headroom = (threshold − keepRatio) × window
tight:  (0.50 − 0.25) × 12,000 = 3,000 tokens
roomy:  (0.85 − 0.35) × 12,000 = 6,000 tokens
```

一个工具结果在 `--max-output 8000` 下大约是 2,200
token。所以 `tight` 在两次上下文压缩之间，只有**一个
回合**的空间，而那些上下文压缩，每一次都要花掉一次
整个历史的全价读，再加一次两调用缓存断电，再加约
七秒。

> 决定你多久压缩一次的，不是阈值。而是**阈值和保持比率
> 之间的间隙**，用你实际工具输出的回合数来衡量。

## 那么上下文压缩**为了**什么？

不是为了省钱。这一点是可以量出来的：每个指标都
变差了——更多的全价 token，多得多的输出 token，更多
的墙时钟，还有一份**天生**就有损的摘要。

> **上下文压缩是一个生存机制，不是一个优化。**你之所
> 以压缩，是因为不压缩换来的是一个 400 和一个死会话，
> 不是因为它更便宜。

它反转了通常的设计建议。如果上下文压缩从来都只
会让你多花钱，那么目标就是尽可能**晚、尽可能少**地
压缩——不是在一个舒适的 70%，而是在最后那个负责任
的时刻，事后能留多少余量就留多少。最便宜的上下文
压缩，是那种从不运行的——这让 stage 01 的输出限制，
还有"用 `grep` 而不是 `cat`"的习惯，都变成了上下文窗
口的特性，而不是单纯的礼貌。

反论证，公平陈述：这些会话都没有接近真实的 131k
窗口。在一个**会**打墙的会话上，上下文压缩的成本是
要跟无穷大相比——这样一比，它按定义就赢了。这里的
数字并不是说上下文压缩不好。它们说的是：**它不是免
费的，它不是一种节省，大多数教程里的默认阈值，是
为了错误的目标而设的。**

## 练习

1. **重现三个臂。**绝对数字会不同；"at 0.1x read" 列
   的顺序是发现。
2. **找到你自己的余量。**在好几组 `(threshold, keep)`
   参数下运行同一个任务，画一张 compactions 对总
   成本的图。拐点就是你工具输出的大小。
3. **故意破坏"切"这个不变式。**删除 `canCutBefore`
   里的工具结果检查，用平行工具调用运行一个会话，
   看 API 拒绝一个压缩器在栈踪迹里根本挨不上边的
   请求。
4. **让估算器说谎。**在 `convChars` 上校准，但在
   `len(requestBody)` 上估算，看比率变得无意义——
   这就是"一致，而非准确"的证据。
5. **删掉限定的那句话**——就在 `summarySystem` 里——
   然后读三份摘要。数一数有多少份，对着自己看不
   到的东西下了断言。
6. **把易变块移进系统提示词**，并比较缓存读列。你
   已经从一个不同方向，重新推导出了 stage 04 的臂 C。
7. **给 Agent 一个真实任务，做两次，分两个会话**，
   中间用 `/remember` 隔开。然后读一读 `MEMORY.md`，
   问问有没有哪一行本可以省下一次工具调用。那个
   问题，就是一整套记忆系统设计的简介。
