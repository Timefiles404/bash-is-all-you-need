# 阶段 11：畸形

模型产出的其他字段全是文字。文字写错了，无非是答得不好，你读一眼就翻过
去了。**参数不一样：它会一路走进 `exec.Command`。**

所以工具调用是唯一一处，"模型说了句怪话"和"机器动了手"是同一件事；这一
章讲的就是隔开这两者的那道边界——一次调用出问题的时候，每套协议实际递到
你手上的是什么，以及那几个显而易见的修法里，哪一个是陷阱。

测出来的结果和我进场时想的不一样：危险的失败不是模型写了段胡话，而是
**宿主在帮倒忙**。

---

## 一次工具调用出错，到底会来什么

三个来源，其中只有一个是模型。

### 1. 截断：每条路上长得都不一样

模型写参数写到一半，输出预算用完了。事件本身很简单；客户端能看见的形状
却有四种，各不相同，线上记录也是为了装下它们才改的。

| 哪条路 | 信封上写的 | 你收到的 |
|---|---|---|
| OpenAI，**非**流式（§A2） | `finish_reason: "length"`，`tool_calls: []` | 网关自己那套 `<tool_call><function=bash>` 标记，塞在 `message.content` 里 |
| OpenAI，**流式**（§E15） | `finish_reason: "length"` | 货真价实残缺的 `arguments`——没有收尾的字符串 |
| Anthropic，网关把这个块补完了（§A3c） | `stop_reason: "tool_use"`——**在说谎** | `input` 被换成 `{"raw_arguments": "<invalid JSON>"}` |
| Anthropic，流到一半被切断 | `stop_reason: "max_tokens"` | 攒到一半的 `input_json_delta` |

§E15 是这一阶段新加的，它订正了 §A2 当初下的结论：

> **不会。`tool_calls[].function.arguments` 永远不会以截断的形式返回，
> 因为工具调用一旦被截断，`tool_calls` 压根就不会有内容。**

这话对 `"stream": false` 成立，对 `"stream": true` 不成立。同一个请求，
`max_tokens: 40`，改成流式：26 帧，其中第 2 到 21 帧只带参数碎片、别的什
么都没有，拼起来是

```
{"command": "find /srv/app -type f -name \"*.go\" -not -path \"*/vendor/*\" -not -path \"*/testdata
```

——没收尾的字符串，不合法的 JSON，从头到尾没有一点标记。两种形状的差别，
来自网关那次服务端解析（解析的是模型那套宿主语法）站在响应的哪一侧：非
流式时，解析跑在已经写完的文本上，失败了，于是退回去把原始标记整个倒出
来；流式时，解析是边收边跑的，被切之前解析出来的东西早就发走了。没有退
路可退。

**真实的 Agent 全都在流式。**所以 §A2 那条结论——这条路上你永远不必处理
残缺的参数 JSON——放进 Agent 真正运行的那个模式里，正好说反了。这个我拿
`curl` 是探不出来的；是 Agent 自己撞上去，它才冒出来。

Anthropic 那一行最要紧，因为只有那一行**信封在说谎**。`stop_reason` 写着
`"tool_use"`，意思是"模型要跑个工具"，而唯一能说明有东西被切掉的证据，只
剩 `input` 自己的形状。阶段 01 那条规矩——*凡是以 `length` 收尾的响应，里
面的东西一概不许执行*——在这里根本不会触发。它触发不了。这个响应就不是
`length` 收尾的。

### 2. 没人执行的 schema

§E13 问的是：这两条路，有没有哪一条会拿自己发出去的 schema 去校验模型回
来的调用。没有。三次探针，每次都让模型产出 schema 明令禁止的东西：

```
enum ["bash","sh"], asked for "powershell"
  OpenAI     arguments: {"command": "echo hi", "shell": "powershell"}     200
  Anthropic  input:     {"command": "echo hi", "shell": "sh"}             200

additionalProperties:false, asked for an extra timeout_ms
  OpenAI     arguments: {"command": "echo hi", "timeout_ms": "5000"}      200
  Anthropic  input:     {"command": "echo hi"}   (twice — two tool_use blocks)

command declared "string", asked for the array ["echo","hi"]
  OpenAI     arguments: "{\"command\": \"[\\\"echo\\\",\\\"hi\\\"]\"}"
  Anthropic  input:     {"command": "[\"echo\",\"hi\"]"}
```

前两个是明摆着的违规，200 返回，finish reason 也正常。**你发出去的 schema
只是个建议。**它影响模型倾向于产出什么，但什么也约束不了；你的客户端不
查，就没人查。

第三个更有意思，也是这一整章诚实的边界。声明的是字符串，我要的是数组，结
果两边都**把数组序列化成了声明的那个类型**。这个结果能通过你写得出来的任
何 JSON Schema 校验器——`command` 确实是字符串——而它不是一条 shell 命令。
schema 校验查的是参数的*形状*，至于这个值到底有没有意义，它一个字都说不
出来。

### 3. 累加器

参数是分片到的，而 §B4 显示切口就落在 token 中间。最显而易见的实现是把它
们接起来，而"接起来"这个做法，在野外存在的三种方言里只对其中一种：

```
incremental   每一片都是接下去的那几个字节        append
cumulative    每一片都是到目前为止的整个值        replace
re-send       最后一片把整个值重复一遍            replace
```

没有任何一份协议文档给它们起过名字。这个端点是 incremental 的，所以在这里
"接起来"是对的；换一个会在最后一块里把完整参数重发一遍的网关，"接起来"就
变成了 `{"command":"ls"}{"command":"ls"}`，而它的报错——
`invalid character '{' after top-level value`——只给你一个字节偏移量，关于
原因一个字都没有。能把三者分开的判据是：**一次工具调用的参数，恰好是一个
顶层 JSON 值**，所以"缓冲区已经能解析了"是个终态，后面再来的东西就不是续
上来的。

## 陷阱：把被截断的调用修好

每个"修复坏掉的 LLM JSON"的库做的都是同一件事——把没闭合的字符串闭上，把
没闭合的容器闭上——二十行代码。下面把它用在五个真实的截断载荷上：三个来自
§A3c 抓下来的报文，两个来自一次新跑的会话。

**五个全变成了合法 JSON。五个里没有一个是模型本来要的那条命令。**

每一次的意图都是同一件事：*找出 `/srv/app` 下 14 天内改过的所有 `.go` 文
件，排除 vendor 和 testdata，grep 出 `TODO(security)`，排序，写进
`/tmp/audit.txt`*。修出来的是什么，以及每一条在一次性目录树里真跑起来的下
场：

| 修完的命令 | 退出码 | 跑出来什么 |
|---|---|---|
| `find` | **0** | 把整棵树列了一遍，12 行 |
| `find /srv/app -name "*.go" -mtime -14 -not` | 1 | `find: expected an expression after '-not'` |
| `find /srv/app -name '*.go' -not -path '*/vendor` | 2 | `bash: unexpected EOF while looking for matching '` |
| `… -exec grep -nH 'TODO(security)' {} + \|` | 2 | `bash: syntax error: unexpected end of file` |
| `… -mtime -14 -exec grep -Hn 'TODO(security)'` | 1 | `find: missing argument to '-exec'` |

五个里有四个**响亮地失败了**，这一条把我原本以为自己要论证的那个版本削掉
了。bash 和 `find` 拒绝半截命令的本事很好；截断落下来的位置，通常正好能产
生一个语法错误，而语法错误是模型读得到的、看得见的失败。

所以危险比"修完就跑垃圾"更窄，也更糟：

> **修复真正危险的时候，是截断留下的那个前缀本身就是一条合法、完整、而且
> *更宽*的命令。**

shell 命令把约束放在末尾。排除项、过滤器、上限、`-e` 标志全是尾部参数，所
以截断先削掉的就是它们，留下的是完好无损的破坏性动词。最干净的一例，真跑
过：

```
本来要的：  git clean -fdx -e .env -e vendor
修完的：    git clean -fdx

之前：  .env 在，vendor 在
之后：  .env 没了，vendor 没了                退出码 0，没有报错
```

`find` 光杆一条是同一个形状，只是换了身人畜无害的行头：退出码 0，输出看着
像那么回事，Agent 报告"做完了"。整份记录里没有任何一处会告诉你，真跑的那
条命令不是模型写的那条。

同一个论点，别人给出的版本比我这个更锋利。筹备这一阶段的时候我读过一个已
经上线的 Agent，它拒绝修复截断，理由里压根没有 shell：一段被截断的文件编
辑参数，括号补齐之后，是*一处看着没毛病、实际少了一块的编辑*，而把它一声
不响写进用户的文件，比任何报错都糟。bash 好歹对语法有自己的看法。文件写入
器没有。

**所以这一阶段不修被截断的参数。**数括号的那个扫描器还在——叫 `jsonIsOpen`，
用途换成了判断*该怪谁*，而不是判断该跑什么。到末尾还没闭合的载荷，是被切
断的；已经闭合又解析不了的，它压根就没当过 JSON。同样的二十行，用途正相
反。

## 那道边界

就一个函数，`checkCall(t Tool, raw string) argCheck`。每一次工具调用，在被
派发之前**以及**进入消息数组之前，都要从它身上过一遍。

```go
faultCut      生成停在了值的中间——网关那个 raw_arguments 形状，
              或者一段 JSON 还没闭合的碎片
faultNotJSON  闭合了，但不是 JSON。散文、标记、一句道歉
faultSchema   合法的 JSON，但和我们公布的 schema 相抵触
```

三个值而不是一个，理由和阶段 09 要三种分诊裁决一样：它们通向不同的动作。
真正要紧的是 `faultCut` 和 `faultSchema` 这一对，因为它们对**这是谁的错**
给出了相反的答案。模型压根没写完的调用，不是一次参数写错了的调用；明明是
预算用光了，却告诉模型它的 JSON 不合法，等于拿一次往返去买一个错的诊断。

它收的是整个 `Tool`——就是进了请求的那张 `Schema` map——所以检查和对外的声
明不可能各说各话。阶段 10 有一个 `parseBashArgs` 和一个 `parseTaskArgs`，
各自用 Go 把 `bashToolDef` 和 `taskToolDef` 已经用 JSON 说过的话再说一遍，
而没有任何东西保证这两遍说的是同一件事。

### 早就发生了的那次漂移

双向测试一写出来就抓到一处。`taskToolDef` 声明 `description` 是**必填**
的；`parseTaskArgs` 在它缺席时默认填 `"subtask"`。模型被告知某个字段是必须
的，然后被一条根本不需要它的规矩去评判。

阶段 07 有一个测试管的正是这件事，而且它是过的——因为它只查了一个方向：
*parser 要的每个字段，schema 都要求了吗？* 反过来那一问，它从来没问过。换
上去的测试从构造上把两边都断言了——只带必填字段的调用必须被接受，少掉其中
任何一个都必须被拒绝——而 `description` 不再声明为必填。

### 边界上故意宽松的地方

`additionalProperties: false` 的执行方式是**剪掉，不是拒绝**。

定这件事的是一笔账。§E13 量到模型确实会自己加字段，而上游没有任何东西拦得
住。没声明过的属性，按定义就是工具不会去读的东西，所以丢掉它不可能改变真
正跑起来的是什么——而拒绝要花掉一整个往返：模型写，宿主拒，模型读拒信，模
型再写一遍。花这笔钱去删一个本来就会被忽略的键，是亏本买卖。丢掉这件事会
以通知的形式报出来，所以它看得见，又不留下永久痕迹。

同样的推理，也是数字只检查"是不是数字"、不检查是不是整数、在不在范围内的
原因。声明的是 `5`，模型给 `5.0`；上限是 `100`，模型给 `200`——而钳一下不
要钱，拒绝要花掉一个回合。**边界上严不严，是个延迟和成本的决定，不只是正
确性的决定。**这一阶段最后定下的规矩是：读法唯一的，就顺手改对；读法不唯
一的，拒绝。

## 绝不让没验过的调用进历史

这是花钱的那一半，而 §E14 就是那次测量。OpenAI 那条路上六份请求体，除了
`arguments` 之外完全相同，每一份都当成三条消息的历史重放一次：

| `arguments` | HTTP |
|---|---|
| `{"command": "echo hi"}` | 200 |
| `""` | **400** |
| `{}` | 200 |
| `{"raw_arguments": "{\"command\": \"find"}` | 200 |
| `{"command": "find /srv/app -name ` | **400** |
| `I will run: echo hi` | **400** |

**规则恰恰就是"能解析成 JSON"，此外一条都没有。**`command` 明明是必填的，
`{}` 照样收。整个对象只有一个键、而这个键 schema 根本不认识，也照样收。只
有压根不是 JSON 的才会被拒——而阶段 09 把 400 分诊成致命，这是对的，因为拿
服务器已经拒过的参数去重试，正是客户端 bug 变成线上事故的那条路。

两件事放一起看：**历史里只要有一次解析不了的工具调用，这个会话就永久死
了。**后面每一个请求都会把它重放一遍，然后拿到同一个 400。

同一组探针打到 Anthropic 那条路上，五份请求体全返回 200，包括 `{}`、类型
写错的属性，以及网关自己那个 `{"raw_arguments": …}`。它从来不拿 `input` 和
`input_schema` 去比，两个方向都不比。这种失败更安静，但并不更好：模型被要
求接着往下聊一段对话，而在那段对话里，它看起来调用过一个工具，用的是它从
来没写过的参数。

400 的响应体里还捎带着两个陷阱：

```json
{"error":{"param":"","type":"server_error","message":"Error from provider (Console Go): Upstream request failed: [400] Invalid request parameters"}}
```

这明明白白是客户端的错，`error.type` 却写着 `server_error`——这是 §D11 那个
模式的第二例，而这一次**说真话的字段是 HTTP 状态码**。阶段 09 把决定挂在
状态码上，只把 `error.type` 留作证据；这个 case 正好证明那个先后顺序定对
了。

而 `arguments: ""` 会得到 400，之所以要紧，是因为空字符串正是零参数调用
*最自然*的写法。§E15 显示，流式下第一个 `tool_calls` 增量到手时就是
`"arguments":""`，所以一条流如果断在"宣布调用"和"第一片碎片"之间，攒出来的
恰好就是这个。能用的写法是 `{}`，而 `renderArgs` 现在是 `anthropicToolInput`
对称的另一半——阶段 10 只做了一边。

### 身份

网关完全可以给它发出的每一次调用都铸同一个 tool-call id。在一个回合内部，
除了配对结果之外没人读这个 id，所以它能跑；跨回合就不行了，协议会因为 id
重复把整个请求拒掉，而拒信报的是*消息下标*，不是工具名，于是错误指向了错
的地方。

`uniqueIDs` 负责把撞车的 id 改名，而它有两条性质，都是一路走过来时踩出来的
bug。见过的 id 那个集合覆盖的是**整个会话**，不是一个回合，因为真正会撞的
重复分散在不同的 assistant 消息里——按回合查什么也查不到，请求照样被拒。另
一条是：改名发生在结果块被构造出来**之前**，因为一次调用如果在它的答复已
经存在之后才改名，那个结果就成了孤立工具结果：同样被拒的请求，报错还更没
用。

## 光是正确拒绝还不够

下面这次测量，在代码已经能跑之后改掉了设计。

边界写完了，测试过了，行为也对。拿 `--max-tokens 110` 打到活的 Anthropic
那条路上，把 trace 里的数量点一遍：

```
16 次模型调用 · 0 条命令 · 16 次 faultCut
```

每一次调用都被截断。每一次都被正确分类、正确拒绝、正确上报。**而 Agent 连
续十六个回合，什么都没跑**，最后停下来靠的只是回合预算。

模型不是在犯轴。它被告知自己的调用被切断了，而它看不见 `max_tokens`——所以
"你被切断了"点出的是一个它无从下手的原因，它手上剩下的招只有换个说法。它
把一条同样长的命令重写了十六遍。

所以这个分类必须带来行为上的改变，否则分了也白分。一个回合里*每一次*调用
都被切，就把连续计数往前推一格；一个回合只要有东西通过了，就清零；连着三
次就结束循环，而话是说给**人**听的——因为能改那个数的是人：

```
error: 3 turns in a row produced only truncated tool calls. The model cannot
see the output budget, so it will keep re-sending calls of the same length;
raise --max-tokens (currently 110)

3 calls · 0 commands · 3 malformed
```

十六次降到三次。这是一根保险丝，和 `maxTurns`、`maxDepth` 是一家的：它不是
修复，是给一个已知修不好的循环划一条花费上限。

那次运行还有一点值得读，因为它说明了这条路的性质。三次拒绝里有两次是残缺
的 JSON 碎片，第三次是网关合成的那个 `raw_arguments` 对象——**Anthropic 的
两种形状，在同一个会话里都出现了**，取决于切口落在网关那次解析的哪一边。

## 重放的消息里不许有指令

这条规矩来自读别人的代码，而它让这一阶段删掉了自己的四条字符串。

工具结果不是一条消息。它是对 prompt 的永久追加：它进消息数组，此后每一个
请求都会把它再发一遍。搁在里面的祈使句，几个回合之后会被读成一条崭新的指
令——那时候让它显得合理的上下文早就滚出屏幕了——于是模型重新发起一次已经处
理过的调用，而且这条消息越老，它发得越理直气壮。

阶段 10 发布了四条：

```
"— send valid JSON"
"the call was probably cut short; send it again"
"Retry with a shorter command."
"Do not retry it unchanged."
```

四条全没了，而 `TestReplayedTextContainsNoInstructions` 会把这一阶段可能塞
进工具结果的每一条字符串都扫一遍，找祈使句的开头。它必须是机械的守卫，因
为这些字符串写着写着，自然就写成了建议。

**陈述事实的话，放旧了还是陈述事实。**整条规矩就这一句。

### 为什么有两个测试文件

`toolcall_test.go` 盖的是边界。`wiring_test.go` 之所以存在，是因为光盖边界
不够，而说出这句话的是变异测试。

第一轮把代码破坏了 42 处，一次一处。**十六个变异体活了下来**，其中十个是同
一个形状：检查本身被盖住了，*调用这些检查的地方*没有。把边界那次调用从
`dispatch` 里删掉，活了——因为下游碰巧还有第二道守卫会拒掉同一份载荷，而测
试只断言了"它被拒了"。把 `uniqueIDs` 从主循环里删掉，活了。把保险丝关掉，
活了。把累加器改回无脑追加，活了。

另外六个是那种通过了、却根本没碰自己声称在测的东西的测试——id 长度上限那个
用例，用的 id 短到那道上限从来没响过；还有四个 `jsonIsOpen` 的用例，括号深
度在被测的那个分支之前就已经把答案定死了。

对一个函数写的单元测试，证明的是这个函数没写错。只有真的把主循环跑起来的
测试，才能证明主循环用了它。`wiring_test.go` 拿一个写好剧本的供应商去驱动
`runTurn`——不用网络——然后对着 trace 断言。

有一个活下来的变异体不是测试缺失。`jsonIsOpen` 还检查了末尾的逗号或冒号，
而把这段删掉什么都没变，因为没有任何输入能走到那里：切在 `{"a":` 正后面，
对象是开着的，`depth > 0` 早就把答案定了。两行代码加一个变量，永远改变不了
任何一个答案，所以它们没了。这是这个仓库里第二次，一个等价变异体给出的信
号是**删掉**代码，而不是给它补个测试。

最终：**41/41 全抓住，0 个活下来。**

### 这一阶段翻出来的两处对阶段 10 的订正

**子 Agent 跑起来的时候，每一道期限都是关着的。** `newChild` 从来没复制过
`dl`，所以子 Agent 拿到的是一个全零的 `deadlines` 结构——而 `guardBody` 和
`waitFor` 都把 `<= 0` 当成"没有看门狗"。阶段 10 整章的主题对子 Agent 一概
不适用，一声不响，也没有任何东西因此报错。那个会永远挂住的子 Agent，正是
阶段 10 存在的理由，而它恰恰就是仍然暴露在里面的那一个。

**`argsForDisplay` 是宽松解析，被隔离起来了。**面板和压缩摘要需要从可能已
经坏掉的参数里拿出一条能读的命令——那才是宽松解析*该待*的地方，而一个把命
令显示得残缺的查看器，比什么都不显示的有用。它是个独立的函数，名字就把这
件事说明白了，而它的结果绝不许流到执行那一步。它也从不返回空：
`{"raw_arguments":""}` 抽出来是空字符串，而一次工具调用从记录里凭空消失，
等于丢掉了"Agent 试过点什么"的最后一份证据。

### 一处查过之后发现本来就是对的

我读过的一个已经上线的 Agent 撞上过一个值得点名的 bug：它的卡死看门狗**先
取消 reader，再拒绝**，而取消会把挂着的那次读结算成一次干净的流结束——于是
一条卡死的流被报成了一条正常结束的流，一声不响地把这个回合截断，而不是抛
出一个可重试的错误。这种失败露出来的样子，是一个又短又像模像样的答案，不
是一个错误。

阶段 10 没有复现它，而这个原因值得知道，不值得靠猜：取消一个 Go 的请求
context，会让 `resp.Body.Read` 返回错误，永远不会是 `io.EOF`；`readSSE` 会
把任何非 EOF 的错误往上传；而两个解码器都返回 `res, err`，并且是故意不发
`KindResponseEnd` 的。如果守卫恰好在流正常收尾的那一刻响了，赢的是
`err == nil`，那个原因会被忽略掉——同一个竞态的正确解法，只是从另一头走过
来的。

## 这一阶段没修的

- **schema 合法、语义错误的参数。** `{"command": "[\"echo\",\"hi\"]"}`
  能过这里的每一道检查，而它不是一条 shell 命令。除了真跑一遍，没别的办法
  知道，所以权限闸仍然是最后一道防线。
- **一声不响把长参数值丢掉的供应商。** 这是一个已经上线的 Agent 报出来的
  失败模式：值到了服务器，却没到模型，于是回来的是*合法的 JSON，少了一个
  必填的键*。模型认为自己发了这个字段，一模一样地重试，传输层再吞一次——观
  测到连着八次失败。任何 JSON 校验都看不见这件事；要检出它，得跨回合地比对
  参数*和*结果，两边都一模一样才算。
- **完整回合里漏出来的标记。** `stripHarnessMarkup` 挂在 `StopMaxTokens`
  上，所以某个供应商的兼容层要是没能解析出一次已经写完的调用，它的标记就会
  留在原地。这道闸是故意的：截断的回合里，文本按定义就是不完整的，剪掉不损
  失什么；而在一个完整的回合里，一个被要求解释这套线上格式的 Agent，它的答
  案会在它引用的第一个 `<tool_call>` 处被一声不响地截断——而这个仓库自己的
  文档里，这玩意儿到处都是。
- **schema 里嵌套的对象属性。** 这里没有哪个工具有这种东西，而会递归的
  schema 遍历器，就是揣着一个环引用 bug 等着发作的 schema 遍历器。

## 自己试一遍

1. **看着保险丝烧断。** 拿 `--max-tokens 110` 打 Anthropic 那条路，prompt
   要它给一条长命令。然后把它提到 4096，看同一个 prompt 在第一次调用就成
   了。错误信息里点出来的那个数，就是能修好它的那个数——把话送给人看，图的
   就是这个。
2. **把边界关掉。** 让 `checkCall` 永远返回 `argCheck{Args: obj}`，再跑同一
   个会话。数数有多少东西进了 shell。
3. **把修复加回来。** 实现那个二十行的补括号器，拿 §A3c 里逐字记下的
   `raw_arguments` 载荷跑一遍，把每个结果和模型本来想干的事对一遍。然后拿
   `git clean -fdx -e .env` 再试一次。
4. **把累加器弄坏。** 把 `mergeArgs` 改回无条件追加，喂它 `toolcall_test.go`
   里那种 re-send 方言。你拿到的报错只报一个字节偏移量，关于原因什么都不说
   ——这类 bug 之所以贵，就贵在这里。
5. **把一句指令放回去。** 往某条 fault 文本里加上 "Retry with a shorter
   command."，然后跑一个长会话。要过一阵才看得出来，而这正是那个测试必须是
   机械的理由。
6. **找出第四种方言。** 把 Agent 指到另一个网关上，把每一个
   `tool_args_delta` 都记下来。这里记了三种；没有任何理由认为就这三种。
