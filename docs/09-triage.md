# 第 09 阶段 — 分诊

一个想法：

> **一个错误是一个决策，不是一个字符串。**

一个刚刚在模型调用上失败的 Agent，恰好只有三种动作。等一会儿，把同样的字节
再发一次。把它们发到别处去。停下来，说明为什么。`triage.go` 里的每一行代码，
都是为了把一次失败变成这三者之一。

这听起来像一个小小的 `if`。它之所以是一整个文件，是因为所有人最先写下的那两条
规则，在**这个仓库所针对的那个端点上都是错的**，而且错的方向正好相反：

```
"401 说明密钥是坏的，所以停。"
    一个写错的模型名在这里返回的是 401，信封的形状和一把被吊销的密钥
    一模一样。停下来，对其中一种是对的，对另一种则是白扔掉一个还能用
    的会话。

"5xx 是瞬态的，所以带退避重试。"
    一个畸形的请求体在这里返回的是 500。那是客户端的一个 bug，而一个
    只认状态码的策略会永远重试它：它永远不会成功，也永远不会停。
```

这两条都不是靠把状态码读得更仔细修好的。它们都靠同一件事修好：把失败中足够多
的东西带上，好拿来做决定——而这就是一个 struct 和 `fmt.Errorf` 的区别。

## 第 08 阶段留在地上的东西

在这个阶段之前，Agent 的错误处理总共就是六行：

```go
res, err := a.call(turn, msgs)
if err != nil {
    a.bus.Error("%v", err)
    return msgs
}
```

这里面有三处不对，而其中只有一处是"没有重试"。

**状态码活不下来。** `a.call` 返回的是 `fmt.Errorf("http %d: %s", ...)`，于是
调用方想知道这是一个 429，唯一的办法就是
`strings.Contains(err.Error(), "429")`。真有人这么写，而在某条消息正文恰好含有
这个数字的那天，它就是错的。

**部分结果被丢掉了。** 两个适配器的结尾都是

```go
if err != nil {
    // 没有 KindResponseEnd：响应不是结束了，是断了。
    return res, err
}
```

——一个非 nil 的结果*同时*带着一个非 nil 的错误，这是故意的，从第 02 阶段起就有
注释这么写。到这个阶段之前，每一个阶段都接住了那个值，却从来没看过它。那些
token 已经生成了。生成出来的 token 是要计费的。

**压缩有它自己的、更糟的一份拷贝。** 第 05 阶段的摘要器自己发 POST，而它的错误
路径根本不读响应体：一次失败的压缩，永远只能报出 `http 500`，别的什么都没有。
两条把同一个失败分类成不同结果的路径，就是两条你没法为之写出一份策略的路径。

## 环节在前，状态码在后

```go
const (
    phaseBuild   callPhase = "build"   // 我们连请求都渲染不出来
    phaseConnect callPhase = "connect" // 没有响应：DNS、被拒、TLS、reset
    phaseStatus  callPhase = "status"  // 响应到了，而且不是 200
    phaseStream  callPhase = "stream"  // 200，然后 body 断了
)
```

分类器先看环节，再看状态码，因为环节回答的是决定其余一切的那个问题：
**有没有东西被生成出来？** 什么都没生成，意味着重试是免费的。生成了东西，意味
着第一次尝试已经上了账单，而重试是第二笔。

`CallError` 就是那个能拿来做决定的东西：

```go
type CallError struct {
    Phase      callPhase
    Status     int           // 没有响应时为 0
    Type       string        // 供应商的 error.type，逐字保留
    Message    string
    Body       string        // 前 8 KiB，逐字保留
    RetryAfter time.Duration // 服务器要求的时长，没要求就是 0
    Partial    *CallResult   // 流断掉时适配器手里有的东西
    Err        error         // 这样 errors.Is 还能用
}
```

`Body` 挨着 `Type` 和 `Message` 看起来是多余的，而它最常挣到自己的位置。§D11
记下过一个 400，回来的东西**根本没有错误信封**——只是请求的一个 24 字节回显，
`{"model":"qwen3.7-plus"}`。对那个响应，`Type` 和 `Message` 都是空的，原始
body 是唯一存在的证据。消息把这个"没有"点名说出来，而不是打印一个 `http 400: `
而冒号后面什么都不跟，因为一条空的尾巴读起来像是 Agent 自己的 bug，而
"`http 400 with no error envelope: {"model":"qwen3.7-plus"}`"指向的是服务器。

`Type` 从不做归一化。当状态码分不出错误的模型名和被吊销的 key 时，是这个字段分
得出来，所以归一化它就等于把它所驱动的那个决定的证据丢掉。

## 那张表

每一行都能追到 `docs/wire-notes.md`，而那些*不是*观察到的行为的行会自己说明这
一点。这就是 `triage_test.go` 的那张表，同一张表：

| 观察到的 | 显而易见的规则 | 它实际上是什么 | 裁决 |
|---|---|---|---|
| `401` + `AuthError` | 致命 | 对 | **致命** |
| `401` + `ModelError` | 致命——同一个状态码！ | 一个*模型*问题；另一个端点可能有这个模型 | **降级** |
| `401`，没有信封 | 在 `error.type` 上崩掉 | 没有东西可分类 | **致命** |
| `404` | 降级 | 对 | **降级** |
| `429` | 重试 | *这里没有观察到*；RFC 9110 | **重试** |
| `413` | 重试 | 问题在字节本身；只有压缩会改变它们 | **致命** |
| `400` / `422` | 按 5xx 的样子重试 | 是我们的问题 | **致命** |
| 畸形 body 之后的 `500` | 瞬态 | **一个穿着服务器状态码的客户端 bug** | 重试，短牵绳 |
| `503` | 瞬态 | 对 | 重试，全长牵绳 |
| 连接被拒 | 重试 | 什么都没生成，什么都没计费 | **重试** |
| 流断了，没有 type | 重试 | 传输死了 | **重试** |
| 流里的 `overloaded_error` | 重试 | 对 | **重试** |
| 流里的 `invalid_request_error` | 重试——它是个流错误 | 它到来是因为我们发出去的东西 | **致命** |
| 任何未分类的东西 | 重试 | 未知 | **致命** |

有两行值得单独一段。

**`error.type` 的匹配是子串匹配，不是相等判断。** §D11 观察到的是 `ModelError`
和 `AuthError`——PascalCase——而两份协议规范写的都是 snake_case
（`not_found_error`、`invalid_request_error`）。拿任何一种拼法做相等判断，对着
文档都是对的，对着线上都是错的。

**未分类是致命，不是重试。** 一个未分类的失败被重试，就是同一个失败重复一遍。
它发出的 `call_error` 事件带着状态码和逐字保留的 `error.type`，缺的那一行就是
这样被找出来的。

### 牵绳

一条额外的规则，一个理由：

```go
func (e *CallError) leash() int {
    if e.Phase == phaseStatus && e.Status >= 500 && e.Status != http.StatusServiceUnavailable {
        return 2
    }
    return 0 // 策略给的全额
}
```

一个 `503` 是真实的容量信号，给它全部额度。一个光秃秃的 `500` 一共只给两次尝
试，因为在这个端点上，它是*我们*配置错了的可能性，至少不低于它是对方宕机
——§D11 拿到 500 的场合，既有一个畸形的 body，*也有*把 OpenAI 形状的 body POST
到 Anthropic 路由上。两次尝试能扛过一次抽风，又远远不足以把一个永久性的错误藏
在重试循环后面。

## Retry-After，以及这个仓库无法证明的那件事

`parseRetryAfter` 读 RFC 9110 允许的两种形式——delta-seconds 和一个 HTTP-date
——而服务器给的数字直接压过算出来的退避时间，因为它是这个函数里唯一一个来自
"知道容量什么时候回来的人"的数字。

它同时也是**这个阶段里根据最不充分的代码，而这件事值得大声说出来。** 拿
`429|Retry-After|timeout|502|503|504|408` 在 `wire-notes.md` 全部 731 行里 grep
一遍，正好命中一次，而那一次不是抓下来的字节——它是 §D11 自己给出的规范性
结论：

> 要点：永不按 HTTP 状态对这些错误分类。在 429 和连接失败上重试；将 401 视为
> 致命但模糊的并记录 `error.type`；以及将 5xx 视为*可能*永久的，限制重试。
> 总是防护一个没有 `error` 字段的错误体。

建议是好建议，第 09 阶段基本上就是它的实现——但这个仓库探过的那个网关，实际上
从来没发过 429，从来没发过 `Retry-After`，也从来没断过流。这个仓库的证据里没有
任何一处记录下 `Retry-After`。`docs/` 里其他每一个论断都立在字节上；这一个立在
RFC 加上 `triage_test.go` 里一个本地服务器上。仓库其余部分说"观察到"的地方，这
里说的是"照规范写的"。

把它当成一份规范来读、而不是当成一个愿望来读，得出两道保护：

```go
if secs <= 0 { return 0 }                    // "-5" 不是一次负数的睡眠
if d := t.Sub(now); d > 0 { return d }       // 过去的时间点意思是"现在"
```

没有它们，一个服务器本意是"立刻"的头，会以一个负的时长流进 `time.Sleep`，而那
会立即返回——正好在服务器要求退避的那一刻把退避关掉。而服务器是允许说"一个小
时"的，所以这个值会被夹住：请求的形状被尊重，长度不被尊重。

### 全抖动，不是半抖动

```go
return time.Duration(rnd() * float64(exp))
```

从 `[0, exp)` 里均匀取一个数，不是更常见的 `exp/2 + rand(exp/2)`。这个区别在这
里格外要紧：第 07 阶段派出的子 Agent 共用一个 `http.Client` 和一个端点，所以供
应商打一个嗝，就会让好几个调用在同一毫秒里失败。半抖动会让那些调用继续挤在一
起，每一次尝试它们都会再撞一次。一个把自己的客户端同步起来的重试策略，就是一台
对着已经在挣扎的服务开火的负载发生器。

## 梯子

```sh
agent --provider primary --fallback backup,local
```

每一级都在**启动时**就构建好、key 也检查过，在第一个请求之前。一个按需构造的降
级目标就会按需失败，而它被需要的那一刻，是它唯一为之存在的那一刻；`--fallback`
里的一个拼写错误，代价应该是一次启动报错，而不是宕机期间一个死掉的会话。

它故意不是的三样东西：

- **不是负载均衡器。** 没有任何东西在分摊流量，顺序也永远不变。
- **不是熔断器。** 它永远不会爬回去，因为"主供应商是不是又健康了"这个问题，不
  花一次真实的调用去问就答不出来。降级是一次你会一直留着的降级——这正是为什么
  每一次切换都要发一个事件。一个会话被便宜的模型悄悄服务了一个小时，就是这个设
  计为了简单而换来的那种失败，而它只有在可见的时候才是能活下来的。
- **不是无共享架构。** 子 Agent 按指针共用这把梯子，因为"这个端点在拒绝调用"是
  关于端点本身的一个事实。发现了这件事的子 Agent，不该还得回去教它的父 Agent。

最后这一条是并发唯一露面的地方，而它产出了这个文件里唯一一行微妙的代码：

```go
func (l *ladder) advance(from int) bool {
    if l.cur > from { return true } // 已经有兄弟把我们挪走了
    ...
}
```

对两个在同一级上失败的兄弟来说，`cur = from + 1` 本来就是幂等的：两个都写同一个
值。真正需要这道保护的情形有三个参与者，而它是一次**回退**。A 在第 0 级失败，挪
到 1。C 在 1 上失败，挪到 2。然后 B——手里还捏着这一切发生之前读到的第 0 级——要
求降级，没有这道保护它就会写下 `cur = 1`，把下一个调用发给一个已经被两个兄弟放
弃了的供应商。

## 来自真实运行：一个断掉的流要花多少钱

这是那次纠正了代码的测量，而这次纠正比功能本身更有意思。

那个网关从来没对我们断过流，所以这个失败得自己造。一个用完就扔的反向代理——围着
`httputil.ReverseProxy` 写的 121 行，不属于任何一个阶段，因为 `triage_test.go`
用 `httptest` 可复现地覆盖了同样的分支——把请求转发到上游，让模型生成，然后在
body 传到一半时切断连接（354 字节之后 `panic(http.ErrAbortHandler)`，而
`Content-Length` 承诺的还更多）。**供应商看到的是一次完成的生成，并为此计费。
客户端看到的是一个断掉的流，而且永远收不到那个 usage 帧。**

```
  call failed (attempt 1, retry): the stream broke: unexpected EOF
  retrying in 313ms (attempt 2) — the stream broke: unexpected EOF

  ┌─ call 1 · tool_calls
  │ in 963    █░░░░░░░░░░░░░░░░░░░  full 3 · write 0 · read 960  100% cached
  ...
  ── session ──────────────────────
  cost: $0.000155
  1 retry
  retried attempts re-sent ≥963 prompt tokens (≥$0.000030)
```

最后一行是一个别的 Agent 都不报的数字，而它不可能来自 API：usage 在流的*末尾*才
到，而这个流没有末尾。所以它是在这个 prompt 唯一存在真实数字的那一刻推断出来的
——就是最后终于成功的那次尝试——而且它是作为一个界打印出来的，带一个 `≥`，因为
一次冷调用在第一次尝试时付的是缓存**写**，在重试时付的是更便宜的**读**，所以照
抄成功那次尝试的拆分，会把第一次算少了。

那个面板里还有一个值得注意的安慰：`full 3 · read 960 · 100% cached`。**那次断掉
的尝试并没有白费——它把缓存热起来了**，而重试把它读回来了。一个断掉的流第一次很
贵，之后每一次都便宜。

### 这次运行在我自己的面板里找到的 bug

这个阶段第一次实跑用的是*另一种*故障：注入两个 503。面板说的是

```
  cost: $0.000276
  retried attempts re-sent ≥1926 prompt tokens (≥$0.000301)
```

这是胡说八道。重复计费的数字比整个会话还大，而它更大是因为它是虚构的：**那些请
求在生成之前就被拒了，所以供应商一分钱都没为它们计费。** 一个在 status 环节的
503 和一次被拒的连接都是免费的。只有一个开了又死掉的流才真的花了钱。

这就是为什么 `Phase` 要放在事件上，而不只是待在 `CallError` 里面。`Status` 替代
不了它：一次连接失败和一次流断裂都带着状态 0。面板现在维护两个计数器——每一次等
待，以及只有那些真的到达了模型的尝试——而同一个会话报出来的是：

```
  cost: $0.000287
  2 retries
```

有重试，没有重复计费。`TestARefusedRequestIsNotReBilled` 的存在就是为了让它保持
这样。

更一般的教训，就是第 04 阶段和第 05 阶段从不同方向落到的同一个结论：一个报出看
起来合理的错误数字的仪表，比一个什么都不报的仪表更糟，因为看起来合理的那个数
字，正是人们会去引用的那个。

## 一次降级要花多少钱

一个 prompt 缓存是按供应商、按模型、按前缀分的，所以一次降级**在构造上**就是冷启
动的。同一个 963 token 的 prompt，在这个供应商第一次见到它的时候，和它热了之后：

| | full | 缓存读 | prompt 的成本 |
|---|---|---|---|
| 热的 | 3 | 960 | **$0.0000297** |
| 第一次见到这段 prefix | 963 | 0 | **$0.000289** |

（这两个数字来自两次不同的运行，不是同一个会话里相邻的两个回合。冷的那次正是上面
那次降级之后的第一次调用；它之所以是冷的，是因为那个供应商还没见过这段 prefix，
而这恰好就是降级每次都会造成的状况。）

**同样的字节，9.7 倍。** 挪到第 1 级把供应商、模型、前缀这三个条件全都丢掉。你救
回来的那个回合，花掉了你十个 prompt 的缓存折扣，而且会一直这么花下去，直到新供应
商的缓存热起来——而在一个只剩几个回合的会话上，那可能永远不会发生。

这不是一个反对降级的论证。这是一个支持那个事件的论证：成本基准在会话中途变了，
而面板是从 `KindProvider` 事件、而不是从启动时的配置来重新定价的。没有它，第二
个供应商的 token 会按第一个供应商的价格计费——一份自信地算错了的成本报告，那比
一份承认自己不知道的报告更糟。

一个值得拥有的副作用：一份 trace 现在会记录**是哪个端点产出了它**，以及在什么价
格下产出的。在这个阶段之前，你可以把一个存档会话的每一个字节都读完，却重建不出
它的成本。现在在一台没有 `providers.json` 的机器上跑 `--replay`，看到的是真实的
钱。

## 压缩调用也是一次模型调用

```go
res, err := retryLoop(bus, 0, pol.forCompaction(), newLadder(rung{p: p}), ...)
```

一把只有一级的梯子，这是故意的：这个调用可以被重试，但不可以被降级。因为一次摘
要打嗝就把整个会话的供应商换掉，那不是恢复，那是惊吓——而且价格会在一个只被告知
"正在压缩"的用户脚下变掉。

还有一根更短的牵绳，不管会话的策略是什么：

```go
if p.attempts > 2 { p.attempts = 2 }
if p.budget > 5*time.Second { p.budget = 5 * time.Second }
```

压缩本来就有一种安全的失败方式——Agent 不压缩继续跑，并且把这件事说出来——所以早
点放弃代价很小，而拼命重试代价极大：每一次尝试都按全价把整份记录重发一遍，而且
它是在那个需要空间的回合还在等着的时候干这件事的。

## 三个事件，不是一个

```
call_error   什么坏了，以及我们对它做了什么决策
retry        我们正在等，等多久，以及那个数字是谁给的
provider     从这里往后由谁来服务调用，按什么价钱
```

和第 05 阶段那个压缩三件套是同一套论证：它们回答的是不同的问题。`call_error` 故
意**不**叫 `error`。一个 `error` 是终结性的——是会话在告诉人它失败了。一个
`call_error` 是一次带着决定的尝试失败，而它们大多数后面跟着的是一次成功。把它们
当成 error 发出去，会训练人们忽略这个词，而真正的那一个就是这样被漏掉的。

composer 把裁决显示在那一行上，因为在一份 trace 里你总是从一个症状往回读，而问
题从来不只是"什么坏了"——而是"它对此做了什么"：

```
   1    0.00s  provider         flaky (openai · mimo-v2.5) · session start
   4    0.31s  request          openai · 1 messages · 0 cache marks · 3.2kB
   5   37.15s  call_error       RETRY attempt 1 · the stream broke: unexpected EOF
   6   37.15s  retry            wait 313ms · attempt 2 · the stream broke: unexpected EOF
   7   37.46s  request          openai · 1 messages · 0 cache marks · 3.2kB
   8   43.88s  first_token      TTFT 6414ms
  20   44.26s  usage            prompt 963 (full 3 · write 0 · read 960) · out 41
```

两个 `request` 事件，一个 `usage`。那个不对称*就是*那笔重复计费，不用算术就看得
见。

## 诚实的限制

- **模型调用上没有截止时间。** `http.Client{Timeout: 10 * time.Minute}` 是唯一的
  钟，而它盖住的是整个 body 的读取：一个慢但活着的流在第十分钟会死在生成中途，
  而且没有任何东西能取消一个正在飞的调用。`BuildRequest` 返回的是一个不带
  context 的 `*http.Request`，所以障碍在*接口*上。这件事要到第 10 阶段才变。
- **一个可重试的失败被假定是幂等的。** 它确实是，理由是一次失败的模型调用没有跑
  过任何工具——但这个理由是这个 Agent 形状的性质，不是重试的性质，等到哪天工具调
  用在流完成之前就被派发出去，它就不再成立了。
- **重复计费的数字是一个估算**，它出现的每一处都标着 `≥`，而它永远只是一个界，
  因为没法去问 API。
- **没有任何东西把部分结果喂回给模型。** 它做到一半的那个计划没了，而半个工具调
  用比没有更糟。留下部分结果是为了记账，不是为了对话。
- **梯子永远不会往回爬**，一个长会话可以在第 2 级上结束，而除了通过那个事件，没
  有人会注意到。
- **`!= http.StatusOK`，不是一个 2xx 区间。** 一个 202 会被分类成失败。这个仓库
  的证据里没有端点返回过 202；它仍然是表里潜伏的一行。

测试：49 个变异体施加在 `triage.go`、`render.go`、`events.go` 和 `replay.go` 上
——每一个分类器分支、每一道保护、每一个 json tag——49 个全部被抓住。有一个变异体
在运行器里被记为*等价*而不是被测试（`cur = from + 1` 对 `cur = l.cur + 1`，在它
们上面那道保护之下可证明相等），这是收尾一份变异报告的诚实做法。

## 练习

1. **把牵绳弄断，看看它让你付多少钱。** 把 `--provider` 指向一个永远返回 500 的
   URL，加上 `--retry 8 --retry-budget 2m`，然后把 `leash()` 那个子句删掉再跑一
   遍。给两次都计时。第二次就是"5xx 是瞬态的"买来的东西。

2. **加一个 402。** `insufficient_quota` 是每个业余项目最先遇到的那个失败。哪个
   裁决，为什么它和 401 不一样？先写出那一行，再写出证明那一行是承重的那个变异
   体。

3. **让降级能爬回去。** 加一个半开探测：在第 1 级上成功了 N 次调用之后，往第 0
   级发一个调用，如果它能工作就把它提上来。然后测一下这个探测在缓存未命中上要花
   多少钱，再决定你是不是还想要它。（这就是一个熔断器，而这就是一个熔断器的账
   单。）

4. **把部分结果喂回去。** 流断掉时，部分结果里有时含有*完整*的工具调用——§A3c 记
   录过一个完整的 `tool_use` 旁边跟着一个被截断的。别丢掉，照发出去，然后找一个
   这么做是错的案例。这不难找，而这就是为什么默认是丢掉。

5. **让 `Retry-After` 变成观察到的，而不是照规范写的。** 找到任何一个真的会发它
   的端点，把字节抓下来，把那一节加到 `wire-notes.md` 里。这是这里唯一一个改进的
   是仓库的证据、而不是它的代码的练习。
