# 阶段 11：畸形

模型产出的其他字段全是文字。文字写错了，无非是答得不好：你读一遍，不同
意，对话接着往下走。**参数不一样，因为它会一路走进 `exec.Command`。**

所以工具调用是整个循环里唯一一处，"模型说了句怪话"和"机器动了手"是同一
件事。这一章讲的就是隔开这两者的那道边界——一次调用出问题的时候，每套协
议实际递到你手上的是什么；那个显而易见的修法，为什么比它要修的那个故障
还糟；以及一次拒绝之后还得做点什么，才不至于让拒绝本身变成另一种卡死的
方式。

测出来的结果指向一个容易看漏的地方。模型写了段胡话不是危险的失败，因为
shell 拒绝胡话的本事很好。危险的失败是宿主在旁边帮倒忙。

**动手之前。**你需要阶段 03 的两个协议适配器，因为两条路把一次坏掉的工具
调用搞砸的方向正好相反，而一道边界得同时盖住两边；需要阶段 07 的子 Agent，
因为派发循环住在那里，而边界就嵌在它里面；还需要阶段 09 的分诊，因为一次
坏的工具调用之所以贵，正是因为 `400` 被正确地判成了致命。

**你会做出什么。**一个函数，每一次工具调用在能跑起来之前*以及*在能被记
住之前，都要从它身上过一遍；一套三个值的说法，用来讲清楚一次调用为什么
被拒；一处针对重复调用 id 的修复；一个能扛住三种线上方言的参数累加器；
外加一根保险丝，管的是"正确拒绝了，结果还是不够"的那种情况。一个新文
件，再加上凡是构造、重放、显示工具调用的地方各改一点。

## 起点在哪里

阶段 10 读工具调用的参数，靠的是每个工具一个手写的 parser。bash 那个的
全部内容就是这些：

```go
func parseBashArgs(raw string) (string, error) {
    var args struct {
        Command *string `json:"command"`
    }
    if err := json.Unmarshal([]byte(raw), &args); err != nil {
        return "", fmt.Errorf("could not parse tool arguments: %v — send valid JSON", err)
    }
    if args.Command == nil {
        return "", fmt.Errorf("tool call is missing the required \"command\" field — ...")
    }
    ...
}
```

还有第二个，`parseTaskArgs`，是给子 Agent 那个工具用的。两个都能跑。两个
都有同样的三个毛病，而这三个毛病，站在函数内部一个也看不见。

**每个 parser 都在用 Go 把请求已经用 JSON 说过的话再说一遍。**Agent 会给
模型发一份 *schema*——一份机器可读的说明，讲清楚一次合法的调用长什么样：
有哪些属性、哪些是必填的、每一个是什么类型。`bashToolDef` 把这份 schema
公布出去，`parseBashArgs` 再手工把它实现一遍。没有任何东西保证这两遍说的
是同一件事，也没有任何东西会在它们开始各说各话的时候提醒你。

**它们只守住派发这一关。**没通过 parser 的调用不会被执行，这是明摆着的
那一半。另一半是：这次调用照样会作为"assistant 说过的话"被追加进消息数
组，而此后这个会话里的每一个请求都会把它再发一遍。一次畸形调用的成本，
有一半是花在那里的，而阶段 10 在那条路上一道守卫都没有。

**它们的回话里带着指令。**"send valid JSON"、"send it again"。为什么这是
个 bug，本章后面细说；眼下只要注意一件事：这句话进了对话记录，而且会一直
待在那儿。

## 一次工具调用出错，到底会来什么

三个来源，其中只有一个是模型。

### 截断：每条路上长得都不一样

模型写参数写到一半，输出预算用完了。事件本身很简单，客户端能看见的形状
却有四种，彼此差得够远——照着其中任何一种写出来的客户端，剩下三种都会处
理错。

| 哪条路 | 信封上写的 | 你收到的 |
|---|---|---|
| OpenAI，**非**流式（§A2） | `finish_reason: "length"`，`tool_calls: []` | 网关自己那套 `<tool_call><function=bash>` 宿主标记，塞在 `message.content` 里 |
| OpenAI，**流式**（§E15） | `finish_reason: "length"` | 货真价实残缺的 `arguments`——没有收尾的字符串 |
| Anthropic，网关把这个块补完了（§A3c） | `stop_reason: "tool_use"`——**在说谎** | `input` 被换成 `{"raw_arguments": "<invalid JSON>"}` |
| Anthropic，流到一半被切断 | `stop_reason: "max_tokens"` | 攒到一半的 `input_json_delta` |

§E15 是这几种里最新的一个，而它订正了 §A2 当初下的结论：

> **不会。`tool_calls[].function.arguments` 永远不会以截断的形式返回，
> 因为工具调用一旦被截断，`tool_calls` 压根就不会有内容。**

这话对 `"stream": false` 成立，对 `"stream": true` 不成立。同一个请求，
`max_tokens: 40`，把流式打开：26 帧，其中第 2 到 21 帧只带参数碎片、别的
什么都没有。把它们拼起来，一字不差就是这个：

```
{"command": "find /srv/app -type f -name \"*.go\" -not -path \"*/vendor/*\" -not -path \"*/testdata
```

没收尾的字符串，不合法的 JSON，从头到尾没有一点宿主标记。

两种形状的差别，来自网关那次服务端解析站在响应的哪一侧。模型在线上发出
来的压根不是 JSON，而是一套 XML 式的语法，
`<tool_call><function=bash><parameter=command>…`，由网关把它解析成协议规
定的那种工具调用。非流式时，这次解析在已经写完的文本上跑一遍，在被拦腰
截断的宿主标记上失败，于是退回去把原始宿主标记整个递给你；流式时，它是
边收边跑的，被切之前解析出来的东西早就转发走了，于是没有什么退路可退。

**真实的 Agent 全都在流式。**所以 §A2 那条结论——这条路上你永远不必处理
残缺的参数 JSON——放进 Agent 真正运行的那个模式里，正好说反了。这件事讲
的既是这个端点，也是方法本身：一次协议探针，如果跑在你根本不会上线的模
式里，它给出的结论可以在你真正上线的那个模式里错得理直气壮。这个形状拿
`curl` 是探不出来的，是一个正在跑的 Agent 把它撞出来的。

Anthropic 那一行最要紧，因为只有那一行**信封在说谎**。`stop_reason` 写着
`"tool_use"`，意思是"模型要跑个工具"；而唯一能说明有东西被切掉的证据，只
剩 `input` 自己的形状。阶段 01 那条规矩——凡是以 `length` 收尾的响应，里
面的东西一概不许执行——在这里根本触发不了，因为这个响应就不是 `length`
收尾的。

以正常收尾的样子出现的截断，还有一个纯本地的对应版本，值得点名，因为它
很容易被无意中造出来。要是卡死看门狗**先**取消 reader、再拒绝，而 I/O 层
又把一次被取消的读结算成一次干净的流结束，那么一条卡死的流就会被报成一条
正常结束的流：这个回合被一声不响地截断，而不是抛出一个可重试的错误，露出
来的症状是一个又短又像模像样的答案，不是错误。Go 的取消不是这个
形状——取消一个请求的 context 会让 `resp.Body.Read` 返回错误，永远不会是
`io.EOF`——而如果守卫恰好在流正常收尾的那一刻响了，赢的是 `err == nil`。

### 没人执行的 schema

§E13 问的是更前面那个问题：一次调用完整地到了，它就一定符合请求里公布的
那份 schema 吗？不一定。三次探针，每次都让模型产出 schema 明令禁止的东
西：

```
enum ["bash","sh"]，却点名要 "powershell"
  OpenAI     arguments: {"command": "echo hi", "shell": "powershell"}     200
  Anthropic  input:     {"command": "echo hi", "shell": "sh"}             200

additionalProperties:false，却要求多带一个 timeout_ms
  OpenAI     arguments: {"command": "echo hi", "timeout_ms": "5000"}      200
  Anthropic  input:     {"command": "echo hi"}   （两次——两个 tool_use 块）

command 声明为 "string"，却要求传数组 ["echo","hi"]
  OpenAI     arguments: "{\"command\": \"[\\\"echo\\\",\\\"hi\\\"]\"}"
  Anthropic  input:     {"command": "[\"echo\",\"hi\"]"}
```

前两个是明摆着的违规，200 返回，finish reason 也正常。**你发出去的
schema 只是个建议。**它影响模型倾向于产出什么，但什么也约束不了；你的客
户端不查，就没人查。

第三个更有意思，也是这一整章诚实的边界。声明的是字符串，要的是数组，结
果两边都**把数组序列化成了声明的那个类型**。这个结果能通过你写得出来的
任何 JSON Schema 校验器——`command` 确实是字符串——而它不是一条 shell 命
令；把这个字符串交给 shell，它会去跑一个叫 `[echo,hi]` 的程序。schema 校
验查的是参数的*形状*，至于这个值到底有没有意义，它一个字都说不出来。

### 碎片，以及把它们接起来的三种方式

参数不是整块到的，是分成碎片到的，而 §B4 显示切口就落在 token 中间——
`" /srv"` 和 `"/app"` 是同一条路径的两个不同的帧。总得有点什么把它们拼回
去，而最显而易见的实现就是往后接。往后接这个做法，在野外存在的三种方言
里，只对其中一种：

```
incremental   每一片都是接下去的那几个字节        append
cumulative    每一片都是到目前为止的整个值        replace
re-send       最后一片把整个值重复一遍            replace
```

没有任何一份协议文档给它们起过名字。这个端点是 incremental 的，所以在这
里往后接是对的。换个网关，它要是在最后一块里把完整参数重发一遍，往后接
就变成了 `{"command":"ls"}{"command":"ls"}`，而你拿回来的报错是
`invalid character '{' after top-level value`——它报出一个字节偏移量，关
于原因一个字都没说。这类 bug 之所以贵就贵在这里：报错讲的是症状，而且指
向了管道错的那一头。

不用知道自己在哪种方言上、也能把三者分开的判据是：**一次工具调用的参
数，恰好是一个顶层 JSON 值**——一个完整的对象，不是一串对象。所以"缓冲区
已经能解析了"是一个终态，此后再到的东西就不是续上来的。`mergeArgs` 就是
这条规矩，几乎没有别的：已经攒下来的东西如果本身已经是合法 JSON，那么后
面来的碎片是替换它，不是接在它后面；如果新到的碎片是以已经攒下的全部内
容开头的，那就是 cumulative，同样是替换；其余情况才往后接。

## 为什么把截断的调用修好是个陷阱

每个"修复坏掉的 LLM JSON"的库做的都是同一件事——把没闭合的字符串闭上，把
没闭合的容器闭上——大概二十行代码。下面把它用在五个真实的截断载荷上：三
个是 §A3c 里逐字记下来的，两个来自一次新跑的会话。

**五个全变成了合法 JSON。五个里没有一个是模型本来要的那条命令。**

每一次的意图都是同一件事：*找出 `/srv/app` 下 14 天内改过的所有 `.go` 文
件，排除 vendor 和 testdata，grep 出 `TODO(security)`，排序，写进
`/tmp/audit.txt`*。修出来的是什么，以及每一条在一次性目录树里真跑起来的
下场：

| 修完的命令 | 退出码 | 跑出来什么 |
|---|---|---|
| `find` | **0** | 把整棵树列了一遍，12 行 |
| `find /srv/app -name "*.go" -mtime -14 -not` | 1 | `find: expected an expression after '-not'` |
| `find /srv/app -name '*.go' -not -path '*/vendor` | 2 | `bash: unexpected EOF while looking for matching '` |
| `… -exec grep -nH 'TODO(security)' {} + \|` | 2 | `bash: syntax error: unexpected end of file` |
| `… -mtime -14 -exec grep -Hn 'TODO(security)'` | 1 | `find: missing argument to '-exec'` |

五个里有四个**响亮地失败了**，而这一条是把论点收窄，不是把它削弱。bash
和 `find` 拒绝半截命令的本事是真的好：截断落下来的位置，通常正好能产生一
个语法错误，而语法错误是模型读得到、也能作出反应的、看得见的失败。

所以危险比"修完就跑垃圾"更窄，也更糟：

> **修复真正危险的时候，是截断留下的那个前缀本身就是一条合法、完整、
> 而且*更宽*的命令。**

shell 命令把约束放在末尾。排除项、过滤器、上限、`-e` 标志全是尾部参数，
所以截断先削掉的就是它们，留下的是完好无损的破坏性动词。最干净的一例，
真跑过：

```
本来要的：  git clean -fdx -e .env -e vendor
修完的：    git clean -fdx

之前：  .env 在，vendor 在
之后：  .env 没了，vendor 没了                退出码 0，没有报错
```

`find` 光杆一条是同一个形状，只是换了身人畜无害的行头：退出码 0，输出看
着像那么回事，Agent 报告"做完了"。整份对话记录里没有任何一处会说，真跑起
来的那条命令不是模型写的那条。

同一个论点还有更强的一个版本，里面压根没有 shell。把工具换成一个改文件
的工具试试。一段被截断的编辑参数，括号补齐之后，是*一处看着没毛病、实际
少了一块的编辑*——而把它一声不响写进别人的文件，比任何报错都糟，因为那里
没有退出码，也没有 stderr。bash 好歹对语法有自己的看法。文件写入器没有。

**所以这一阶段不修被截断的参数。**数括号的那个扫描器还在，叫
`jsonIsOpen`，用途换成了判断*该怪谁*，而不是判断该跑什么。到末尾还没闭合
的载荷，是生成到一半被切断的；已经闭合、又解析不了的，它压根就没当过
JSON。同样的二十行，指向的是相反的那个问题。

## 那道边界

就一个函数，`checkCall(t Tool, raw string) argCheck`。每一次工具调用，在
被派发之前**以及**进入消息数组之前，都要从它身上过一遍。它给出的回答，
要么是三种 fault 之一，要么是可以拿去跑的参数。

```
faultCut      生成停在了值的中间——网关那个 raw_arguments 形状，
              或者一段 JSON 还没闭合的碎片
faultNotJSON  闭合了，但不是 JSON。散文、宿主标记、一句道歉
faultSchema   合法的 JSON，但和我们公布的 schema 相抵触
```

三个值而不是一个，理由和阶段 09 要三种分诊裁决一样：它们通向不同的动
作，合并成一个，动作就丢了。真正要紧的是 `faultCut` 和 `faultSchema` 这
一对，因为它们对**这是谁的错**给出了相反的答案。模型压根没写完的调用，
不是一次参数写错了的调用。明明是预算用光了，却告诉模型它的 JSON 不合
法，等于拿一次往返去买一个错的诊断；而面对一个错的诊断，模型手上唯一能
出的牌，就是把同一次调用再写一遍。

`checkCall` 收的是整个 `Tool`——就是进了请求的那张 `Schema` map——而不是
每个工具一个校验器。这就是阶段 10 那三个毛病里第一个的修法：检查和对外
的声明现在是同一个对象，所以它们不可能各说各话。

### 早就发生了的那次漂移

把 schema 和 parser 拿来*两个方向*都比一遍的测试一写出来，立刻就抓到一处
漂移。`taskToolDef` 声明 `description` 是**必填**的；`parseTaskArgs` 在它
缺席时默认填 `"subtask"`。先告诉模型某个字段非有不可，再拿一条根本不需要
它的规矩去评判它。

阶段 07 有个测试管的正是这件事，而且它是过的——因为它只查了一个方向：
*parser 要的每个字段，schema 都要求了吗？* 反过来那一问，它从来没问过。
换上去的那个测试从构造上把两边都断言了：只带必填字段的调用必须被接受，
少掉其中任何一个都必须被拒绝——而 `description` 不再声明为必填。

这看起来是一句没有受害者的便宜谎话，可它两头都要花钱：一个相信这个标签
非填不可的模型，会给那些根本用不上它的调用硬编一个出来；而一个正确地把
它省掉的模型，会被任何一个比阶段 07 手上那个更严的校验器拒掉。

### 边界上故意宽松的地方

`additionalProperties: false`——这个 schema 关键字的意思是"除了这里声明过
的属性，别的都不许有"——的执行方式是**剪掉，不是拒绝**。没声明过的属性会
被丢掉，调用照跑，另有一条通知说明丢掉了哪些键。

定这件事的是一笔账。§E13 量到模型确实会自己加字段，而上游没有任何东西拦
得住。没声明过的属性，按定义就是工具不会去读的东西，所以丢掉它不可能改
变真正跑起来的是什么——而拒绝要花掉一整个往返：模型写，宿主拒，模型读拒
信，模型再写一遍。花这笔钱去删一个本来就会被忽略的键，是亏本买卖。丢掉
这件事仍然会报出来，因为另一条路是让"模型以为自己要的"和"实际发生的"之
间悄悄分岔。

同样的推理，也是数字只检查"是不是数字"、不检查是不是整数、在不在范围内
的原因。声明的是 `5`，模型给 `5.0`；上限是 `100`，模型给 `200`——而钳一下
不要钱，拒绝要花掉一个回合。**边界上严不严，是个延迟和成本的决定，不只
是正确性的决定。**这一阶段最后定下的规矩是：读法唯一的，就顺手改对；读
法不唯一的，拒绝。

### 宽松解析有它该待的地方，但不在这里

面板和压缩摘要都需要从可能已经坏掉的参数里拿出一条能读的命令。这正是这
一阶段在别处拒绝的那种宽松解析的正当用途——查看器把命令显示得残缺，也比
它什么都不显示有用。想两头都要，办法是把它做成一个独立的函数，名字就把
它是干什么的说明白，再确保它的结果永远流不到执行那一步。
`argsForDisplay` 有什么就吃什么，实在不行就退回原始字节。

它还从不返回空，而这一点是大家最常漏掉的。`{"raw_arguments":""}` 是真实
存在的载荷，`command` 的值只有空白字符也是；从这两者里抽出来的都是空字
符串，而面板上或者压缩摘要里的一个空字符串，就是一次凭空消失的工具调
用。退回原始字节，留住的是"Agent 试过点什么"这份记录，而查看器之所以要做
宽松解析，图的从头到尾就是这个。

## 绝不让没验过的调用进历史

这是花钱的那一半，而 §E14 就是那次测量。OpenAI 那条路上六份请求体，除了
`arguments` 之外完全相同，每一份都当成三条消息的历史重放一次：

| `arguments` | HTTP |
|---|---|
| `{"command": "echo hi"}` | 200 |
| `""` | **400** |
| `{}` | 200 |
| `{"raw_arguments": "{\"command\": \"find"}` | 200 |
| `{"command": "find /srv/app -name ` | **400** |
| `I will run: echo hi` | **400** |

**规则恰恰就是"能解析成 JSON"，此外一条都没有。**`command` 明明是必填
的，`{}` 照样收。整个对象只有一个键、而这个键 schema 根本不认识，也照样
收。只有压根不是 JSON 的才会被拒——而阶段 09 把 `400` 分诊成致命，这是对
的，因为拿服务器已经拒过的请求体去重试，正是客户端 bug 变成线上事故的那
条路。

把这两件事放在一起，就得到管着这一阶段后半章的那句话：**历史里只要有一
次解析不了的工具调用，这个会话就永久死了。**后面每一个请求都会把它重放
一遍，然后拿到同一个 400。不是下一次调用——是每一次调用，直到会话结束。

Anthropic 那条路收下了这六份里的五份——`arguments: ""` 在那边没有对应的
形状，因为 `input` 是 JSON 对象，不是字符串——五份全返回 200，包括 `{}`、
类型写错的属性，以及网关自己那个 `{"raw_arguments": …}` 对象。那条路从来不拿
`input` 和 `input_schema` 去比，两个方向都不比：出门的时候不比（§E13），
回来的时候也不比。这种失败更安静，但并不更好——模型被要求接着往下聊一段
对话，而在那段对话里，它看起来调用过一个工具，用的是它从来没写过的参
数，并且没有任何东西会报告这处分岔。

那个 400 还捎带着两个陷阱。第一个在它的响应体里，一字不差：

```json
{"error":{"param":"","type":"server_error","message":"Error from provider (Console Go): Upstream request failed: [400] Invalid request parameters"}}
```

这明明白白是客户端的错，`error.type` 却写着 `server_error`。这是 §D11 那
个模式的第二例——一个错误响应体，自己对自己的分类是错的——而这一次**说真
话的字段是 HTTP 状态码**。阶段 09 把决定挂在状态码上，只把 `error.type`
留作证据；这一例正好证明那个先后顺序定对了。

另一个陷阱是 `arguments: ""` 会得到 400，之所以要紧，是因为空字符串正是
一次不带参数的调用*最自然*的写法。§E15 显示，流式下第一个 `tool_calls`
增量到手时就是 `"arguments":""`，所以一条流如果断在"宣布调用"和"第一片碎
片"之间，攒出来的恰好就是这个，而一个把攒到的东西重放出去的 Agent 会把它
发出去。能用的写法是 `{}`，所以 `renderArgs` 在出门的路上把空字符串换成
`{}`。Anthropic 那边的适配器在 `anthropicToolInput` 里一直是这么做的；阶
段 10 只在一边有这条规矩，而这正是协议不对称通常长的样子——缺的那半边，
就是你后写的那半边。

### 两次调用，同一个 id

网关完全可以给它发出的每一次调用都铸同一个 tool-call id。在一个回合内
部，这是无害的，因为除了配对结果之外没人读这个 id。跨回合就不行了：协议
会因为 id 重复把整个请求拒掉，而拒信报的是*消息下标*，不是工具名，于是错
误指向了错的地方，读起来像是你组装消息的代码有 bug。

`uniqueIDs` 负责把撞车的 id 改名，而它有两条性质是承重的，并且都很容易想
反。见过的 id 那个集合覆盖的是**整个会话**，不是一个回合，因为真正会撞的
重复分散在不同的 assistant 消息里——按回合查什么也查不到，请求照样被拒。
另一条是：改名发生在结果块被构造出来**之前**，因为一次调用如果在它的答复
已经存在之后才改名，那个结果就成了孤儿：同样被拒的请求，报错还更没用。

## 光是正确拒绝还不够

下面这次测量，是在代码已经能跑之后改掉了设计。

边界写完了，测试过了，行为也对。拿 `--max-tokens 110` 打到活的 Anthropic
那条路上，把 trace 里的数量点一遍：

```
16 次模型调用 · 0 条命令 · 16 次 faultCut
```

每一次调用都被截断。每一次都被正确分类、正确拒绝、正确上报。**而 Agent
连续十六个回合，什么都没跑**，最后停下来靠的只是回合预算。

模型不是在犯轴。它被告知自己的调用被切断了，而它看不见 `max_tokens`——所
以"你被切断了"点出的那个原因，它根本无从下手，手上剩下的招只有换个说
法。它把一条同样长的命令重写了十六遍。

所以这个分类必须带来行为上的改变，否则分了也白分。一个回合里*每一次*调
用都被切，就把连续计数往前推一格；一个回合只要有东西通过了，就清零；连
着三次就结束循环，而话是说给**人**听的，因为能改那个数的是人：

```
error: 3 turns in a row produced only truncated tool calls. The model cannot
see the output budget, so it will keep re-sending calls of the same length;
raise --max-tokens (currently 110)

3 calls · 0 commands · 3 malformed
```

十六次降到三次。这是一根保险丝，和 `maxTurns`、`maxDepth` 是一家的：它不
是修复，是给一个已知修不好的循环划一条花费上限。定三次而不是两次，是因
为连着两次还说得通——可能只是模型把命令缩短了一点，运气不好；连着三次就
是个规律了。

这个形状会反复出现：一次拒绝总是说给某个人听的。这一阶段的拒绝大多是说
给模型听的，模型能照着做点什么。而这一次点出来的条件只有人能改，所以它
必须换个收件人。

那次运行还有一点值得读，因为它说明了这条路的性质。三次拒绝里有两次是残
缺的 JSON 碎片，第三次是网关合成的那个 `raw_arguments` 对象——**Anthropic
的两种形状，在同一个会话里都出现了**，取决于切口落在网关那次解析的哪一
边。

## 重放的消息里不许有指令

工具结果不是一条消息。它是对 prompt 的永久追加：它进消息数组，此后每一个
请求都会把它再发一遍。搁在里面的祈使句，几个回合之后会被读成一条崭新的
指令——那时候让它显得合理的上下文早就滚出屏幕了——于是模型重新发起一次已
经处理过的调用，而且这条消息越老，它发得越理直气壮。

阶段 10 发布了五条：

```
"— send valid JSON"
"the call was probably cut short; send it again"
"— send an actual shell command"
"Retry with a shorter command."
"Do not retry it unchanged."
```

五条全没了。`TestReplayedTextContainsNoInstructions` 会把这一阶段可能塞进
工具结果的每一条字符串都扫一遍，找祈使句的开头——"send "、"retry"、
"do not "、"you should"、"make sure"，等等。它必须是机械的守卫，而不是一
条评审规矩，因为这些字符串最自然的写法就是写成建议；这里的失败模式不是
粗心，是热心。

**陈述事实的话，放旧了还是陈述事实。**整条规矩就这一句。

## 测了这道检查，不等于测了那次调用

给一个校验函数写的单元测试，证明的是这个函数没写错。只有真的把主循环跑
起来的测试，才能证明主循环调用了它。这是两个不同的主张，而一套对前者面
面俱到、对后者一声不吭的测试，是很容易攒出来的。

这一阶段里的具体例子：把 `checkCall` 从 `dispatch` 里整个删掉，边界自己
那些测试全都照样过——它们本来就没走 `dispatch`。更糟的是主循环的测试也照
样过：一次参数从没被检查过的调用走到 bash 那个分支时，手里没有 `command`
值，`emptyCommand` 会因为它是空的把它拒掉，而一个只断言"这次调用被拒了"
的测试，分不出到底是哪道守卫拒的。检查被盖住了，它的调用点没有。

所以测试拆成了两份。一份直接考边界；另一份拿写好剧本的供应商去驱动
`runTurn`——不用网络——然后对着产出的事件 trace 断言，每一处接线一条断
言：id 是*跨回合*改名的，宿主标记没进历史，保险丝在第三个全截断的回合上
烧断，请求构造器从不发出 `arguments: ""`。

配置结构体有同样的失败模式。`newChild`——就是那个构造子 Agent 的函数——复
制了 provider、client、闸门和配置，唯独没复制 `dl`，也就是装着阶段 10 那
三个期限的那个结构体。一个全零的 `deadlines` 结构体意味着每一个钟都是关
着的，因为 `guardBody` 和 `waitFor` 都把 `<= 0` 读成"没有看门狗"。于是阶
段 10 整章的主题对子 Agent 一概不适用，一声不响：没有卡死检测，没有总调
用时长兜底，而父 Agent 两样都有。没有任何东西失败，也没有任何东西说一
声，而那个会永远挂住的子 Agent，恰恰就是阶段 10 存在的理由。**一个没被
复制进子 Agent 的特性，在那里就是不存在的特性，而这份缺席在真正出事那天
之前，没有任何症状。**

## 这一阶段没修的

- **schema 合法、语义错误的参数。**一个 `command`，值是字符串
  `["echo","hi"]`，能过这里的每一道检查——它确实是字符串，跟声明的一样
  ——而它不是一条 shell 命令。除了真跑一遍，没别的办法知道，所以权限闸仍
  然是最后一道防线。
- **一声不响把长参数值丢掉的供应商。**这是别处的生产环境报出来的一种失
  败模式：值到了服务器，却没到模型，于是回来的是*合法的 JSON，少了一个
  必填的键*。模型认为自己发了这个字段，一模一样地重试，传输层再吞一次
  ——观测到连着八次失败。任何 JSON 校验都看不见这件事；要检出它，得跨回
  合地比对参数*和*结果，两边都一模一样才算。
- **完整回合里漏出来的宿主标记。**`stripHarnessMarkup` 挂在
  `StopMaxTokens` 上，所以某个供应商的兼容层要是没能解析出一次已经写完的
  调用，它的宿主标记就会留在原地。这道闸是故意的：截断的回合里，文本按
  定义就是不完整的，剪掉不损失什么；而在完整的回合里，要是有个 Agent 被
  要求解释这套线上格式，它的答案会在它引用的第一个 `<tool_call>` 处被一
  声不响地截断——而这个仓库自己的文档里，这玩意儿到处都是。在这个端点
  上，这道闸在截断的回合里打开，却找不到什么可剪的，因为 §E15 记下来的那
  个流式形状压根不带宿主标记；剪这一步留着，是为了非流式的那个形状，以及
  为了某个糊涂到把工具调用语法当普通散文来写的模型。
- **schema 里嵌套的对象属性。**这里没有哪个工具有这种东西，而一个会递归
  的 schema 遍历器，就是一个揣着环引用 bug 等着发作的 schema 遍历器。

## 练习

1. **看着保险丝烧断。** 拿 `--max-tokens 110` 打 Anthropic 那条路，prompt
   要它给一条长命令。然后把它提到 4096，看同一个 prompt 在第一次调用就成
   了。错误信息里点出来的那个数，就是能修好它的那个数——把话送给人看，图
   的就是这个。
2. **把边界关掉。** 让 `checkCall` 不管收到什么都返回解码出来的对象、不
   带 fault，再跑同一个会话。数数有多少东西进了 shell。
3. **把修复加回来。** 实现那个二十行的补括号器，拿 §A3c 里逐字记下的
   `raw_arguments` 载荷跑一遍，把每个结果和模型本来想干的事对一遍。然后
   拿一个被截断的 `git clean -fdx -e .env` 再试一次。
4. **把累加器弄坏。** 把 `mergeArgs` 改回无条件追加，喂它 re-send 那种方
   言。你拿到的报错只报一个字节偏移量，关于原因什么都不说——这类 bug 之所
   以贵，就贵在这里。
5. **把一句指令放回去。** 往某条 fault 文本里加上 "Retry with a shorter
   command."，然后跑个长会话。要过一阵才看得出来，而这正是那个测试必须是
   机械的理由。
6. **找出第四种方言。** 把 Agent 指到另一个网关上，把每一个
   `tool_args_delta` 都记下来。这里记了三种；没有任何理由认为就这三种。

## 读完这一章，你能回答什么

**为什么工具调用是模型输出里唯一一个、在别的任何事发生之前就必须先验一
遍的东西？**
因为它是唯一一个会走进 `exec.Command` 的字段。模型产出的其他字段全是文
字，文字写错了不过是个你读一遍就翻过去的坏答案。参数写错了，是一条真的
会跑起来的命令。

**一次被截断的工具调用，在线上长什么样？**
两条路上一共四种形状。OpenAI 非流式：`message.content` 里是原始的
`<tool_call>` 宿主标记，而 `tool_calls: []`。OpenAI 流式：货真价实残缺的
参数 JSON。Anthropic：要么是一个合成的 `{"raw_arguments": …}` 对象，要么
是残缺的 `input_json_delta`，取决于切口落在网关那次解析的哪一边。

**为什么 OpenAI 那边截断的形状，取决于你有没有用流式？**
因为网关是在服务端解析模型那套宿主标记的。非流式时，这次解析在已经写完
的文本上跑一遍，失败，然后退回去把原始宿主标记整个倒出来。流式时，它是
边收边跑的，解析出来的东西早就转发走了，于是没有退路可退。§A2 当初的结论
是你永远不会见到残缺的参数 JSON；§E15 把它订正了，订正的正是每个真实
Agent 都在跑的那个模式。

**这两个端点，有没有哪一个会拿你发出去的 schema 去校验回来的工具调用？**
没有。§E13 拿回来了一个 schema 明令禁止的 `enum` 值，还有一个被
`additionalProperties: false` 禁掉的属性，两次都是 200，finish reason 也
正常。schema 只是个建议：它影响模型倾向于产出什么，此外什么也约束不了；
你的客户端不校验，就没人校验。

**五个修好的截断里有四个响亮地失败，那为什么还是不修？**
因为要紧的是第五个。shell 命令把约束放在最后，所以截断削掉的是排除项，留
下的是动词：本来要的 `git clean -fdx -e .env -e vendor` 修完变成
`git clean -fdx`，退出码 0，把这条命令本来要保护的那两样东西删了个干净。

**为什么是三种 fault，而不是一个"invalid"？**
因为它们通向不同的动作。`faultCut` 和 `faultSchema` 对这是谁的错给出了相
反的答案；明明是预算用光了，却告诉模型它的 JSON 不合法，等于拿一次往返去
买一个它根本无从下手的诊断。

**一次解析不了的工具调用进了消息数组会怎样？**
在 OpenAI 那条路上，§E14 量到的是此后每一个请求都得到 400——而 400 被正确
地判成致命，所以一次没验过的调用就是一个永久死掉的会话。在 Anthropic 那
条路上什么都收，包括网关自己那个截断形状，于是会话转而安静地退化。

**为什么一次不带参数的调用必须渲染成 `{}`，不能是 `""`？**
因为 §E14 量到 `arguments: ""` 是 400，而 `{}` 会被接受；而且空字符串不是
假想出来的：§E15 显示流式下第一个 `tool_calls` 增量到手就是
`"arguments":""`，所以一条流如果断在第一片碎片之前，攒出来的恰好就是这
个。

**为什么正确地拒绝一次被截断的调用还不够？**
因为模型看不见 `max_tokens`。它只被告知自己被切断了，于是重写一条同样长
的命令——一次会话里量到的是 16 次模型调用、0 条命令。修法是一根保险丝：连
着三个回合全是截断就结束循环，并且把话说给人听，因为能改那个数的是人。

**工具结果里为什么不能带指令？**
因为它不是一条消息，而是对 prompt 的永久追加，此后每一个请求都会把它再发
一遍。祈使句在几个回合之后、在让它显得合理的上下文滚走之后，会被读成一条
崭新的指令，于是模型重新发起一次已经处理过的调用。阶段 10 里的五条这样的
字符串已经被删掉，另有一个机械的测试挡着它们别再回来。

## 思考题

这些问题在这个仓库里没有答案。它们的答案取决于你在做什么。

1. 没声明过的属性是被剪掉、不是被拒绝，理由是一次往返比一个工具本来就不
   会去读的键更贵。描述一个让这笔账反过来的工具——在那里，模型发来一个未
   知的键，意味着它对这个工具信了某件假的事，而照跑不误才是贵的那个选
   项。
2. 那三种累加器方言是撞上了才知道的。你要怎么写一个累加器，让它对一种你
   还没见过的第四种方言也是对的？为此你必须放弃关于线上格式的哪一条假
   设？
3. 这一阶段的拒绝有两个收件人：大多数给模型，截断保险丝给人。挑一个你用
   过的 Agent，找出一次寄错了收件人的拒绝。判断一次拒绝该归谁，判据是什
   么？
4. 这道边界校验时依据的是 Agent 当下对外声明的那份工具清单，而这份清单是
   递归深度的函数。如果工具清单可以在会话中途变化——动态注册，或者一个重
   连之后换了 schema 的工具服务器——什么会坏掉？为了让一次重放仍然能被校
   验，你得在每一次调用旁边额外记下什么？
5. 这里没有任何东西能把一个 schema 合法但语义荒唐的参数和一个好参数分开。
   在你正在做的系统里，这个判断可以住在哪儿？它可能以什么为依据？为了
   它，你愿意为每一次调用付多少钱？
