# Stage 08 — Sandbox

*Optional, and the only stage with a dependency. Most of this chapter is about
why that dependency earns its place, and about what it does **not** buy.*

---

## One rule

> **The agent may not read `.env`.**

Not "the agent may not do dangerous things". A rule that vague cannot be tested,
and a policy you cannot test is a policy you are guessing about. One file, one
verb, small enough to reason about completely — and still, three implementations
in, the honest answer is "this is not a security boundary".

Three places to stand:

```
inspectString   look at the command text            defeated by quoting
inspectAST      parse it and look at the words      defeated by expansion
sandbox.exec    BE the shell and look at the argv    see the limits below
```

The progression is not "add more patterns". Each level moves the check to a
place where more of the truth is available.

---

## The table

Fourteen commands that read the file. Every one is **verified to work first**,
by running it with the policy off and checking the contents actually came out —
a bypass table full of commands that never worked proves nothing, and that is
the commonest way this kind of table is wrong. Generated by
`stages/08-sandbox/bypass_test.go`, not written from memory:

```
command                works?  string   ast    sandbox
plain                  true    blocked  blocked blocked    the command everybody blocks
single quotes          true    blocked  blocked blocked
split across quotes    true      --     blocked blocked    one word to the shell, two strings to a regexp
empty quotes inside    true      --     blocked blocked
backslash              true      --       --    blocked
leading ./             true    blocked  blocked blocked    a different string, the same file
ANSI-C quoting         true      --       --    blocked    the name never appears as text at all
variable               true    blocked    --    blocked    the value does not exist until runtime
command substitution   true    blocked  blocked blocked
eval                   true    blocked    --    blocked    the program is data until it is not
parameter default      true    blocked    --    blocked
loop                   true    blocked    --    blocked
redirect               true    blocked  blocked blocked    argv is just ["cat"] — no filename anywhere in it
nested shell           true    blocked    --    blocked    a whole program smuggled in one argument

string missed 4 · ast missed 7 · caught only by ast: 2 · caught only by string: 5
```

### Level 1 loses to the shell's own syntax

```go
var denyPattern = regexp.MustCompile(`\.env\b`)
```

`cat ".e""nv"` is one word to bash and a different string to that regexp. So is
`cat .en''v`, `cat .en\v`, and `cat $'\x2eenv'` — where the filename never
appears as text at all.

No amount of pattern refinement fixes this, because the pattern is looking at
source text while the shell is looking at what the source text *means*. You are
not competing with an attacker; you are competing with a language.

### Level 2 is a real improvement, and still loses

Parsing with a real shell parser knows that `".e""nv"` is one word whose literal
parts concatenate, that `'.env'` is a quoted literal, and — pleasantly — it
finds `.env` inside `$(echo .env)`, because walking the tree descends into the
command substitution and finds the `echo` call inside it.

What it cannot know is any value that does not exist yet:

```
X=.env; cat $X                the value is assigned at runtime
cat "${MISSING:-.env}"        the expansion is decided at runtime
eval "cat .env"               the program is data until it is not
for f in .env; do cat "$f"    the word is in an iterator, not an argument
```

That is not a gap in the implementation. **The shell is not a syntax, it is an
evaluator, and a parse tree of an evaluator's input does not tell you what the
evaluator will do.**

`literalWord` returns "I do not know" rather than a partial value, deliberately.
Returning `".en"` for `.en$X` would be worse than returning nothing, because a
caller would then compare a partial value against a policy and conclude it was
safe.

### The finding that kills "just run both"

Look at the last line of the table: **caught only by ast: 2 · caught only by
string: 5.** Neither check's misses are a subset of the other's. They fail on
disjoint sets.

The obvious response to this chapter is "so run both checks". It does not work,
because an attacker does not have to defeat a conjunction. **Every command only
has to defeat one property at a time, and shell syntax offers a choice of
which.** One line defeats both:

```sh
X=.en; eval 'cat ${X}v'
```

The text `.env` appears nowhere, so the regexp has nothing to match. The word is
`${X}v` — a parameter expansion glued to a literal — so the parser correctly
reports that it cannot know. The file is read.

## Level 3: be the shell

Stop being an outside observer. Embed the interpreter, and every command it is
about to run arrives as a finished argument vector — after quote removal,
parameter expansion, command substitution, arithmetic, tilde expansion, globbing
and `eval`. There is no syntax left to hide behind, because syntax is what was
just consumed.

```
command:  X=.en; eval 'cat ${X}v'
argv:     ["cat", ".env"]
```

```go
interp.New(
    interp.Dir(root),
    interp.StdIO(nil, &stdout, &stderr),
    interp.ExecHandlers(s.execHandler(bus)),  // every program, final argv
    interp.OpenHandler(s.openHandler(bus)),   // every file the SHELL opens
)
```

### Why two handlers, and why the second one is the surprise

```sh
cat < .env
```

That runs `cat` with **no arguments**. The shell opens the file and hands over a
file descriptor. A policy that inspects argv never sees the filename at all —
at *any* level, including this one. `OpenHandler` is the only thing that can see
it, and without it an argv-based policy has a hole shaped exactly like `<`.

It has its own test, because it is the case a reader is most likely to assume
was already covered.

### The other thing you get for free

`sandbox_exec` fires for **every** program the shell runs, including the ones
nobody typed: what a pipeline, a loop, a glob or an `eval` expanded into. Most of
the value here is not refusal at all — it is that "what did that command
actually do" becomes a question with an answer.

```sh
agent --sandbox --observe    # report every exec and open, block nothing
```

### Where the sandbox has to reach

`--sandbox` is a claim about a session, and a session delegates. The first
`task` call used to be the end of it: `newChild` builds a subagent by naming the
fields it inherits, one at a time, and the sandbox was not one of them. A child
got a nil `sb`, `runCommand` took its other branch, and the delegated work ran
in a real bash — no policy, no `sandbox_exec` events, and nothing in the tally
printed at the end of the session. The parent's own commands were still checked,
which is what made it invisible: everything a reader would think to look at
looked right.

The missing line is one field, and the reason nobody noticed is worth more than
the field. A child is assembled field by field rather than as `child := *a`, and
that is not a style preference: `agent` holds a `sync.Mutex`, and `go vet`
correctly refuses to copy a struct containing one. The explicit form is the safe
one and it is the honest one — every line of it is a decision about what a
subagent is. What it also is, permanently, is a list somebody has to remember to
add to.

> **Every field added to `agent` after `newChild` was written is a field the
> child silently does not get.**

The same function does it again later: stage 10 puts three deadlines on `agent`,
subagents do not get them, and stage 11 is where somebody notices. Nothing fails
and nothing warns, because both defaults are wrong in one direction or the other
— a struct copy inherits what must not be shared, an explicit one fails to
inherit what must. What catches it is a test that runs a command through the
child and looks at what came back, which is why the one in `bypass_test.go`
calls `runCommand` rather than comparing `child.sb` against `parent.sb`. A
refactor can copy the pointer and then stop using it.

Sharing the sandbox then asks a second question, and it is the more interesting
one. The sandbox reports what it saw on an event bus — and once one sandbox
serves the whole tree, *which* bus? A field set at construction is the obvious
answer and the wrong one: it would hold the root agent's bus, so every exec,
open and refusal a subagent produced would arrive stamped depth 0 with no agent
name. The trace would be complete, correctly ordered, and confidently
mislabelled, which is a worse failure than a missing line — a gap you notice.

So the bus is an argument to `run`, not a field on `sandbox`. Which agent ran a
command is a property of the call; the policy and the audit log are properties
of the tree. This is the same distinction `render.go` makes when it reads depth
off the event rather than tracking "which agent are we inside" as renderer
state, and for the same reason: stage 07 made the tree concurrent, so *when*
something happened stopped being enough to say *who* did it. A fresh interpreter
is built for every command anyway, so the handlers it gets can close over the
answer at no cost.

> **Shared state may not remember who last used it.**

## The honest limit

An embedded interpreter sees every command. **It cannot see inside one.**

```sh
awk -v a=.en 'BEGIN{f=a"v"; while((getline l < f)>0) print l}'
```

The sandbox sees `awk -v a=.en <a program>` and has no opinion about the
program's contents, because having one would mean implementing awk. It allows
the exec, and awk does the rest.

That case is a **passing test** in `bypass_test.go`, not an omission:

```
--- PASS: TestTheSandboxCannotSeeInsideAProgram
    as documented: the sandbox saw one exec, allowed it, and the program did
    the rest. An embedded interpreter is a policy and observability layer, not
    a security boundary.
```

The same is true of `perl`, `python`, `ruby`, `node`, `find -exec`,
`git -c core.pager=…`, `make`, and anything else that takes a program as an
argument. The code blocks `sh -c` explicitly and says in a comment that this is
a half-measure that does not generalise — enumerating interpreters is the
denylist game level 1 already lost.

There is more. `isSecretPath` matches on base name: it does not resolve
symlinks, does not canonicalise `..`, and does not know that
`/proc/self/cwd/.env` is the same file. Even a version that did all three would
still race, because a path can be replaced between the check and the open.
**TOCTOU is not an edge case in a sandbox; it is the standard attack.**

So what is this worth? Three things, and they are not nothing:

- **Observability.** Every exec, after expansion, in the trace. No other layer
  can give you that.
- **Policy for a cooperative agent.** The model is not an attacker. It is a
  system that will occasionally do something destructive by accident, and a
  layer that catches the accidental case has done its job.
- **A refusal the model can act on.** `blocked by the sandbox/exec policy: an
  argument resolves to .env after expansion` is a sentence the model can read
  and route around, which is why the refusal text is the refusal.

And what it is not: a boundary. A real boundary is below the shell, at the
operating system — a container, a VM, a separate uid, seccomp-bpf, Landlock, a
mount namespace. Those cost setup, portability and a much larger blast radius
when misconfigured, and none of them fits in a teaching repo without becoming
the whole repo. **The right answer for a coding agent is almost always "run it
in a container", and the layer in this chapter is what you add inside the
container so you can see what happened.**

## From a real run

```
$ agent --yolo --sandbox
sandbox: commands run in the embedded interpreter (enforcing)

> Read notes.txt and tell me how many lines it has. Then try to read the .env
  file in this directory and tell me exactly what happened.

  $ wc -l notes.txt
  $ cat .env 2>&1; echo "EXIT_CODE=$?"
  ⛔ blocked by the sandbox/exec policy: an argument resolves to .env after expansion (matched ".env")
  │ 2 notes.txt
  │ [exit 0 · 64ms]
  │ <stderr>
  │ blocked by the sandbox/exec policy: an argument resolves to .env after expansion (matched ".env")
  │ [exit 1 · 1ms]
```

The model read the refusal, understood it, and moved on. That is the whole
interaction design: **a policy that says "denied" teaches the model to try
again; a policy that says what it objected to lets the model do the task another
way.**

## The dependency, and what it actually cost

This is the one stage that adds a dependency, so it is worth an honest ledger of
what "adding one dependency" meant.

```
go get mvdan.cc/sh/v3@v3.13.1
  → declares `go 1.25.0`, which would raise this module's floor two releases

pin to v3.12.0
  → declares `go 1.23.0`. Fine.

...but interp imports golang.org/x/term
go get golang.org/x/term
  → upgraded golang.org/x/sys  v0.41.0 → v0.47.0
  → bumped this module          go 1.24.0 → go 1.25.0

pin x/term to v0.33.0 (`go 1.23.0`) and x/sys back to v0.41.0
  → floor restored to go 1.24.0
```

One `go get` and the language-version floor moved twice — once for the direct
dependency and once for a transitive one nobody chose. Every reader of this repo
would have needed a newer toolchain, and nothing would have announced it.

> **A dependency's `go` directive is part of its cost**, and it is the part that
> is invisible until you look. Reading `go.mod` after a `go get` is the whole
> discipline.

The criterion that made this one worth paying: **it does something you cannot do
yourself.** A JSON parser you can write. A TOML parser you can write and this
repo refused to, twice. A POSIX shell parser *and evaluator*, with expansion,
`eval`, arithmetic, globbing and job control, is not a thing you write in a
chapter — and there is no version of this chapter's argument that survives
without it, because the argument *is* "you have to be the evaluator".

Stages 00–07 remain standard library plus `golang.org/x/sys`, and their binaries
do not link any of this.

## Exercises

1. **Add a case to the bypass table.** The test verifies your case actually
   reads the file before it counts, so a clever-looking command that does not
   work will fail loudly.
2. **Try to make level 2 win.** Handle backslash escapes and `$'…'` decoding in
   `literalWord`, then find the next bypass. Notice how much of the shell you
   are re-implementing, and that you are now maintaining a second, subtly
   different shell whose disagreements with the first one are security bugs.
3. **Turn the policy inside out**: allowlist programs instead of denying a file.
   Then get past it with `find -exec`, `git -c core.pager=`, and `awk 'BEGIN{system(...)}'`.
4. **Run a real session with `--observe`** and read the `sandbox_exec` events in
   the composer. Count how many programs ran that nobody typed.
5. **Add a containment root**: refuse any `open` outside the working directory.
   Then break it with a symlink, and then with a `..` that only exists after
   expansion. Then decide whether `EvalSymlinks` before every open is a price
   you want to pay per file.
6. **Measure the compatibility cost.** Run the same session with and without
   `--sandbox` and find a command the embedded interpreter does not support. It
   is a very good shell; it is not the shell on your machine, and knowing which
   difference bit you is worth finding out before it matters.
7. **Do the OS-level version.** A container, a `podman run --read-only` with one
   writable mount, and this chapter's layer inside it. Then compare what each of
   the two stops, and notice they are almost disjoint.

## What you can answer now

**Why is the rule one named file rather than "no dangerous commands"?**
Because a rule that vague cannot be tested, and a policy you cannot test is a
policy you are guessing about. One file and one verb is small enough to reason
about completely, which is the only reason three implementations can be compared
at all. It is also the easiest rule in the chapter, and three levels in, the
honest answer is still that this is not a security boundary.

**Why does every bypass in the table have to be verified to work first?**
Because a command that never read the file proves nothing about the check that
missed it, and a table full of those is the commonest way this kind of table is
wrong. Every row is run once with the policy off and checked for the file's real
contents before it is allowed to count. The table is generated by
`bypass_test.go` rather than written from memory, so it cannot drift from the
code.

**Why can no amount of pattern refinement fix the string check?**
Because the pattern reads source text while the shell reads what the source text
means. `cat ".e""nv"`, `cat .en''v`, `cat .en\v` and `cat $'\x2eenv'` all open
the same file, and in the last one the name never appears as text at all. You
are not competing with an attacker, you are competing with a language.

**Why does a real shell parser still lose?**
Because it can only see what is written, and the shell decides much of what it
runs at runtime. The parser handles quoting correctly, and it even finds `.env`
inside `$(echo .env)` by descending into the substitution — but a variable
assigned a moment earlier, a parameter default, an `eval` and a loop iterator
are all opaque to it, and seven of the fourteen commands get through. A parse
tree of an evaluator's input does not tell you what the evaluator will do.

**Why does running both checks not add up to a better check?**
Because their misses are disjoint rather than nested: two commands are caught
only by the parser and five only by the regexp. An attacker does not have to
defeat a conjunction — every command only has to defeat one property at a time,
and shell syntax offers a choice of which. `X=.en; eval 'cat ${X}v'` defeats
both at once, and it is one line.

**Why does `literalWord` return nothing rather than the part it does know?**
Because a partial value invites a wrong conclusion. Returning `".en"` for
`.en$X` hands the caller something to compare against a policy, and the
comparison comes back safe. "I do not know" is the only answer that makes the
caller deal with the case it is actually in.

**Why does an argv-based policy need a second handler for file opens?**
Because `cat < .env` runs `cat` with no arguments at all: the shell opens the
file itself and passes a descriptor. No amount of argv inspection can see that
filename, including at the level where all the syntax has already been consumed,
so without `OpenHandler` the policy has a hole shaped exactly like `<`. It has
its own test because it is the case a reader is most likely to assume was
already covered.

**Why is `awk -v a=.en '…'` a passing test rather than an open bug?**
Because the sandbox sees one exec and has no opinion about the program in the
argument, and having one would mean implementing awk. The same holds for perl,
python, ruby, node, `find -exec`, `git -c core.pager=…` and `make`. The code
blocks `sh -c` explicitly and says in a comment that this is a half-measure that
does not generalise, because enumerating interpreters is the denylist game level
1 already lost.

**Why is a layer that is not a security boundary still worth building?**
Three things. Every exec reaches the trace after expansion, including the
programs nobody typed, and no other layer can give you that. The model is not an
attacker but it will occasionally do something destructive by accident, and a
refusal that names what it objected to lets it do the task another way rather
than simply try again. The boundary itself belongs below the shell, in a
container, and this is the layer you put inside one so you can see what
happened.

**Why did adding one dependency take four steps?**
Because a dependency's `go` directive is part of its cost. `mvdan.cc/sh/v3` at
v3.13.1 declares `go 1.25.0`, which would have raised this module's floor two
releases; pinning to v3.12.0 fixed that, and then `interp`'s own import of
`golang.org/x/term` dragged `x/sys` from v0.41.0 to v0.47.0 and bumped the floor
anyway. Pinning both restored `go 1.24.0`. Nothing announces any of this, which
is why reading `go.mod` after a `go get` is the whole discipline.

## Questions to think about

These do not have answers in the repo. They are the ones where the answer
depends on what you are building.

1. The rule here is one file. Write the rule for your own agent and watch how
   far it gets before it stops being testable: what is the second entry, and
   what do you do with "anything the user would call a secret"?

2. The model in this chapter is cooperative — not an attacker, just occasionally
   destructive. That stops being true the moment it reads text from the
   internet, because an injection makes the model a channel for someone else.
   Which parts of this chapter survive that change, and does it change what you
   put in the container?

3. The sandbox sees every program and nothing inside one. The alternative is to
   stop handing the agent a shell and give it narrower tools instead. Work out
   what that costs in capability, and whether the policy you would gain is one
   you could actually write down.

4. Even a check that resolved symlinks, canonicalised `..` and knew that
   `/proc/self/cwd/.env` is the same file would still lose a race with anything
   that can replace a path between the check and the open. Decide what you would
   write in the refusal message, and in the documentation, for a check you know
   can be beaten — and whether saying so plainly makes it more or less likely to
   be trusted correctly.

5. This dependency was taken because it does something you cannot do yourself,
   and it now sits in the policy path, where a bug in it is a policy bug. What
   is your second criterion — and would you still take it if it were maintained
   by one person who had gone quiet?
