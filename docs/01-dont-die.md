# 阶段 01：活下来

阶段 00 是能跑的，一直能跑到它跑不动的那一刻。这一章讲四种具体的死法，
以及每一种修好各要花多少代价。

**先去复现。** 下面每个修法，读完都显而易见，读之前一个都不明显。
花十五分钟把阶段 00 弄坏，换来的直觉能让阶段 01 读着像必然，而不像
谁拍脑袋定的。

```sh
go build -o agent00 ./stages/00-loop
go build -o agent01 ./stages/01-dont-die
mkdir -p sandbox && cd sandbox
```

## 死法 1：永不返回的命令

**复现**（阶段 00）：

```
> start a simple http server on port 8000 in the foreground
```

Agent 跑的是 `python -m http.server 8000`，然后再也不回来了。没有
超时，没有称得上处理的 Ctrl-C，除了把终端杀掉没有别的出路。

**显而易见的那个修法，以及它为什么不够。** 加个超时，到点就杀
`cmd.Process`。现在试这个：

```
> run: (sleep 300 &) ; echo started
```

shell 立刻退了，`echo started` 也打出来了。Agent 照样永远挂着。

这一下多数人都想不到。`cmd.Wait()` 等的不是进程，它等的是*标准输出
管道关闭*；只要还有任何进程握着写端，管道就一直开着。后台那个 `sleep`
把这个句柄继承过去了。所以只杀 shell，不是漏一个孤儿进程那么简单：
**它把本来要来救你的那个超时也一起挂死了。**

**真正的修法**是让 shell 和它生出来的一切，能一整块地杀掉：

- **Unix**：`SysProcAttr{Setpgid: true}` 把 shell 放进新的进程组，
  `kill(-pgid)` 一发信号就是发给整组。
- **Windows**：开一个 Job Object，所有后代都收进去，
  `TerminateJobObject` 一次把它们全结束。

这就是 `proc_unix.go` 和 `proc_windows.go`，藏在一层很薄的接口后面，
好让 `runBash` 一个字都不用提平台：

```go
g, _ := newProcGroup()
defer g.Close()
g.attach(cmd)          // Start 之前：进程组 / job 创建标志
cmd.Start()
g.adopt(cmd)           // Start 之后：划进 job（Windows）
...
g.kill()               // 把整棵树一起带走
```

**能推广出去的教训：** 清理路径要是依赖它正在清理的那个东西，它就
不是清理路径。凡是写着"然后我们把它杀掉"的地方，都拿这个形状对一遍。

**接着把这条教训用到修法自己身上。** `g.kill()` 本该解开 `Wait()` 的
阻塞——可"本该"正是我们刚刚看着它失效的那种假设。所以收尸这一步也有
自己的五秒截止，超了就报 `[TIMED OUT and could not be reaped]`，然后
往下走。

在这儿放手，`Wait` 那个 goroutine 就泄了，而它握着输出缓冲区，所以
代码还必须**拒绝去读那些缓冲区**——搬数据的 goroutine 可能还在往里
写，硬读就是数据竞争，几周之后它会变成上下文里一段乱码冒出来。泄
一个 goroutine 还能活；把 Agent 卡死不能活；在缓冲区上竞争是三者里
最糟的，因为它出事不出声。

### 一次真实运行

同一个复现，换成做完的 Agent，超时设五秒：

```
> run exactly this: (sleep 300 &) ; echo started ; sleep 300

  $ (sleep 300 &) ; echo started ; sleep 300
  | started
  | [TIMED OUT after 5.046s — the process tree was killed]
```

四件事值得注意，每一件都是某个设计决定在回本：

- **它回来了。** 整场交互前后十八秒，其中五秒是那个超时。换成
  阶段 00，这会儿还在跑。
- **`started` 活了下来。** 被杀之前产出的输出照样抓住、照样显示。
  超时不是把已经学到的东西扔掉的理由。
- **发生了什么，是用人话告给模型的**——它的总结准确说出了后台那个
  sleep 跟着整棵树一起没了。状态行是写给读者看的，因为它真有读者。
- **零个孤儿。** `ps -W | grep -c sleep` 跑之前是 0，跑之后还是 0。
  这一整节存在的意义，就是造出这个数。

### 为什么这里 Unix 严丝合缝，Windows 不是

这个值得记进直觉，因为代码为什么长这样，答案全在这里：

- **Unix** 在 `fork()` 和 `exec()` 中间那道缝里设进程组——子进程
  **在它第一条指令跑起来之前**就已经在自己的组里了。没东西逃得掉，
  因为还没有东西执行过。
- **Windows** 没法把 Job Object 划给还不存在的进程。所以 `adopt()`
  只能在 `Start()` *之后*跑，中间留着一道微秒级的窗口：shell 头一个
  动作要是就生出个孙子进程，它能从这个 job 里溜掉。

Windows 上严丝合缝的做法是 `CREATE_SUSPENDED` + `ResumeThread`，而
`os/exec` 故意让这条路不好走（Go 的收尸逻辑永远不会去恢复一个挂起的
进程，那就把 `Wait()` 挂死了）。这个仓库选择接受这个窗口，并**在代码
里把它写清楚**，而不是装作它不存在。如果你写的是沙箱而不是教学仓库，
就直接驱动 `CreateProcess`——标志位和线程句柄都在
`PROCESS_INFORMATION` 里。

### 你真会撞上的平台坑

| 坑 | 为什么要紧 |
|---|---|
| **`Close()` 不对称** | Windows 的 `KILL_ON_JOB_CLOSE` 让关句柄这个动作*顺手把树杀了*——这是真正的崩溃兜底。Unix 没有这层：Agent 一死，它的子进程就挂到 init 底下继续活。所以 `nohup npm start &` 在 Linux/macOS 上能活过一次工具调用，在 Windows 上**活不过**。 |
| **嵌套 job 要 Win8+** | 有些 CI runner 和容器宿主已经把每个进程都塞进了锁死的 job 里，这时 `AssignProcessToJobObject` 会带着 `ERROR_ACCESS_DENIED` 失败。`runBash` 的做法是降级成一条警告——命令照跑，只是隔离没了——而不是干脆不干活。 |
| **僵尸看着还活着** | 僵尸没被收尸的时候，`kill(pid, 0)` 照样成功。通常 init 会立刻收掉；碰上 PID 1 不收尸的容器，它们就一直赖着。要轮询，别只查一次。 |
| **PID 回用在这里*不是*风险** | `os.Process` 从 `Start()` 到 `Wait()` 一直持着一个打开的句柄，而只要句柄还开着，Windows 就不会回用这个 PID。 |

### 只有 Windows 才有的坑：`$!` 会撒谎

这是给这一章写测试的时候撞出来的，值得单开一段——因为它差点一声不响
地把整件事作废掉。

Git Bash 就是 MSYS2，它**在 Windows 的 PID 之上另铺了一层自己的
POSIX PID 命名空间**。`echo $!` 打出来的是 MSYS 那边的 pid，不是
Windows 的：

```
msys_pid=48908                                <- $! 打出来的就是这个
48908 48907 48905  56176 ... /usr/bin/sleep   <- ps -W：真正的 WINPID 是 56176
```

把 48908 递给 `OpenProcess`，它不报错——它会兴高采烈地去查另一个
Windows 进程：碰巧占着这个号的那个，跟你要找的毫不相干。建立在 `$!`
上的*测试*看着是过了，其实什么都没证明；建立在它上面的*杀手*，杀的
是路人。

换算表在 `/proc/<pid>/winpid`，所以测试夹具写的是
`cat /proc/$p/winpid 2>/dev/null || echo $p`——MSYS2 会给答案；真正的
Unix 没这个文件，就退回那个本来就对的 pid。

这条教训比 Windows 大得多：**当测试和实现共用同一个假设，测试就查不出
这个假设是错的。** 所以这套测试里还专门留了一个用例，就为了把这种
失效演一遍（`TestProcGroupKillingOnlyTheShellLeavesOrphans`）；也所以
这份实现做过变异测试——把 `TerminateJobObject` 换成空操作——用来确认
代码坏掉时测试真的会红：

```
proc_test.go:209: orphans survived kill(): [18592 36592] — the process tree escaped
--- FAIL: TestProcGroupKillsWholeTree (5.22s)
```

一个你从没见它红过的绿测试，不算证据。

## 死法 2：打印 40MB 的命令

**复现**（阶段 00）：

```
> how many files are on this machine?
```

模型先试 `find / -type f | wc -l`，没问题。再看它想看*名字*的那次：
它试的是 `find / -type f`。阶段 00 把每个字节都推进消息数组，之后
整场会话它就赖在那儿，后面每个回合重发一遍、重收一遍钱。

**修法：截断，但别只留前面。** 只保头是本能反应，而这个本能是错的：
一次构建失败，有用的是*最后*二十行。两头都留，中间丢掉，并且把丢了
多少说出来：

```
<预算的前 2/3>

[... 1481923 bytes elided ...]

<预算的后 1/3>
[exit 0 · 3.2s] [output truncated — rerun with a filter such as grep/head/tail]
```

`truncate()` 里有三个细节，比看上去要紧得多：

- **在 rune 边界上切。** 从字符中间切开字节数组，出来的是非法
  UTF-8；有的 API 直接拒收，有的把它变成模型上下文里的一段乱码。
- **把字节数说出来。** 对模型来说，"删掉了一些东西"远不如"删掉了
  1.4MB"有用——后者直接告诉它，这条命令的形状根本就不对。
- **告诉它该改成什么。** 结尾那句点名 `grep`/`head`，实测能减少
  模型把同一份转储再来一遍的次数。

**预算怎么分。** stdout 拿 ⅔，stderr 拿 ⅓。构建失败的时候 stdout
只有一点、stderr 一大堆；列目录正好反过来。分开算，两边就不会互相
饿死。

### 一次真实运行

一份 275KB 的日志，真正要紧的只有*最后一行*：

```
> cat big.log and tell me what went wrong at the end

  $ tail -100 big.log
  | [... 1503 bytes elided ...]
  | NFO  worker-008 processed batch 003976 in 396ms
  | 2026-08-27T02:00:00 ERROR worker-042 FATAL: disk quota exceeded, aborting
  | [exit 0 · 161ms] [output truncated — rerun with a filter such as grep/head/tail]
```

这段值得仔细读，因为"留头加留尾"的全部理由都挤在这一屏里：模型要了
一百行，还是被截了，**而 FATAL 那行活下来了**，因为它在尾巴上。换成
只留头，交上去的会是 5KB 例行 INFO，用户问的那一行正好被丢掉——然后
模型会拿着手里这点东西，自信地答完。

注意上面一行的 `NFO  worker-008`：那是尾部从半行中间接上来的，丑，
但完全无害。别花代码去让截断变好看。

那次运行还看出两件事：

- 系统提示词里那句*"宁可用会过滤的命令，别用往外倒的命令"*真起了
  作用——模型伸手就是 `tail -100`，一次都没用 `cat`。便宜的指令能
  打赢贵的机制。
- 看到截断提示之后，它紧跟着在**同一条 assistant 消息里**发了
  `tail -20` **和** `grep -c 'error\|fatal'`——一次两个 `tool_calls`。
  在这个供应商这儿，并行工具调用不是假想；"每个调用都要有结果，
  一个不落"是规矩不是讲究，原因就在这儿。

## 死法 3：模型被半路切断

阶段 00 对每个回复只问一个问题：*有工具调用吗？* 就这一个问题，藏住
了一整类失败。

**复现**：把 `max_tokens` 设得极小，再派一件活，非得长命令才做得完。
下面是实际收回来的东西，同一个网关上的两套协议各一份。

**OpenAI 那边是诚实的失败。** `max_tokens: 24`：

```json
{"finish_reason": "length",
 "message": {"content": null, "tool_calls": null,
             "reasoning_content": "The user wants to search for Go files containing the word \"deadline\" in the"}}
```

在推理阶段就被切断了，所以工具调用根本没发出来。看清楚阶段 00 在这里
会撒的谎长什么样：它看不到工具调用，于是断定"这个回合说完了"，打一条
空消息，然后等你。没有崩溃，没有报告。任务就这么停了。

**Anthropic 那边才是危险的。** `max_tokens: 10`：

```json
{"stop_reason": "tool_use",
 "usage": {"output_tokens": 136},
 "content": [{"type": "tool_use", "name": "bash", "input": {"raw_arguments": ""}}]}
```

五行里，三处各自独立的错：

1. **`stop_reason` 写的是 `tool_use`。** 不是 `max_tokens`。信封宣称
   这是一次正常、可用的工具调用。
2. **`max_tokens` 没被遵守。** 要的是十个，生成了 136 个。在这个网关
   上，把 `max_tokens` 设小不是成本上限，别拿它当预算的依据。
3. **`input` 不是你公布的那份 schema。** 必填的 `command` 键不见了，
   顶上来的是 `raw_arguments`——规格里根本没这个键——装着空字符串。

### 它在 Go 里长出来的 bug，看着不像 bug

```go
var args struct{ Command string `json:"command"` }
json.Unmarshal([]byte(`{"raw_arguments":""}`), &args)  // err == nil
args.Command                                           // ""
```

反序列化**成功了**。Go 会给缺失的键填零值，于是"模型漏了一个必填
字段"和"模型发来一个空字符串"变成同一个值，Agent 就去跑一条空命令，
还以为这是别人让它跑的。

修法只有一个字符宽：

```go
var args struct{ Command *string `json:"command"` }   // 指针，不是值
```

现在 `nil` 表示没有，`""` 表示空，两个都会被拒。这就是 `main.go` 里的
`parseBashArgs`；而 `render_test.go` 拿六种 payload 一一喂给它——都是
这个网关实测吐出来过的。

**两条要带走的规矩，都比这个 bug 大：**

- **反序列化没报错，不等于校验过了。** 拿你公布的那份 schema 去
  校验——每一次，每一种协议。
- **信封不能给它装的东西作证。** `stop_reason` 和那个畸形的 body
  出自同一个系统。两边对不上的时候，会在你机器上跑起来的是 body。

**半条 shell 命令不是更安全的 shell 命令。** 凡是从 `length` 收尾的
回复里出来的东西，阶段 01 一概不执行；它会用一条工具结果把原因告诉
模型，让模型换个短的再来：

| `finish_reason` | 含义 | 阶段 01 怎么做 |
|---|---|---|
| `tool_calls` / `tool_use` | 正常的工具回合 | 执行 |
| `stop` / `end_turn` | 模型话说完了 | 结束这个回合——但要是里面居然还带着工具调用，信调用，别信标签 |
| `length` / `max_tokens` | 生成中途被切断 | **不要**执行。给每个悬着的调用回一句解释，让它重试 |
| `content_filter` | 供应商拦了 | 报出来，结束回合 |
| 其他任何值 | 新增的，或者厂商自己的 | 把那个字符串原样报出来，结束回合。绝不把未知状态一声不响地当成成功 |

最后那一行是个值得留住的习惯：状态机一旦把未知输入都归到"应该没事"
里，早晚有一天，它也会把一次拒答、一次配额事件、或者一种新的安全
停止，一起归到"应该没事"里去。

## 死法 4：你并不想要的那条命令

阶段 00 里，模型和 `rm -rf` 之间什么都没有。修法是加一道权限闸，而
有意思的地方不在提示语——在于**拒绝**到底是什么。

```go
case deny:
    msgs = append(msgs, toolResult(call.ID,
        "[the user denied this command. Do not retry it unchanged.]"))
    continue
```

拒绝是**数据，不是错误**。它作为工具结果回去，回合继续，模型有机会
提一个更窄的方案。把拒绝当成致命错误，等于恰好在有人认真盯着看的
那一刻把 Agent 杀掉——而那是最不该把线头弄断的时刻。

几种模式：`y` 放行这一次，`a` 整场会话都放行，`n` 拒绝但继续，`q`
停下。`--yolo` 直接跳过整道闸。如果 stdin 是管道，就没人可问，所以闸
会提前发现这一点并把话说明白，而不是一声不响地全拒。

### 一次真实运行

把任务用管道喂进去，不带 `--yolo`，于是每条命令都被拒：

```
> list the files here
  $ ls -la
  [denied: no terminal to ask on — rerun with --yolo to allow commands]
  $ ls
  [denied: no terminal to ask on — rerun with --yolo to allow commands]

It looks like both `ls -la` and `ls` were denied. Could you let me know which
command or approach you'd prefer me to use to list the files?
```

这就是这套设计买到的行为。Agent 被拒，**把方案收窄了**（`ls -la` →
`ls`），又被拒，然后问了一个明白的问题——全都在同一个回合里，因为
拒绝走的是工具结果这条路，不是致命错误。要是那条路上返回 `error`，
你拿到的就是一段堆栈和一场死掉的会话。

### 对"bash 就够了"的诚实反驳

看看这道闸能给你看什么：一个命令字符串。它手上就这么多。

专门的 `write_file` 工具能画出一份 **diff**。专门的 `send_email`
工具能把**收件人**摆给你看。专门的 `edit` 工具能这么判：文件自模型
上次读过之后又变了，那就拒绝写入——这个不变式 bash 根本表达不了。
像 `grep` 这样的只读工具还能标成并行安全；而 `bash -c "..."` 不管
里面装的是 `grep` 还是 `git push`，形状一样不透明，宿主只好把一切
都串起来一件一件做。

这才是真正的取舍。一个工具买来的是广度，而且买得便宜。专门的工具
买给宿主的是**拦、画、审、并行**这几样能力——而那份广度的代价，是
你每次想问用户一个好问题时都要付一遍。这个仓库后面还是只用一个工具，
因为它要讲的就是怎么把仪表装上去；换成产品，会把三四个动作提成
一等公民，把 bash 留作逃生口。

## 净化三件套

命令的输出还不算文本。有三个互不相干的问题，症状却都是"字变怪了"：

| 问题 | 症状 | 修法 |
|---|---|---|
| ANSI 转义 | 上下文里散落着 `[0;32m` 之类；白烧 token | 用正则剥掉 |
| CRLF | 每行 Windows 输出末尾都有个看不见的 `\r` | 统一成 `\n` |
| 非法 UTF-8 | 原生程序按本地代码页输出（中文 Windows 上是 GBK，日文 Windows 上是 Shift-JIS） | 把非法字节换成 U+FFFD |

如果你用的是非英文 Windows，第三条值得多停一会儿：那些字节不是坏的，
它们*在另一套编码里是对的*。把它们替换掉，是让失败**看得见**而不是
无声无息——模型看到 `����` 就知道出了岔子，不会拿着一堆乱码自信地
往下推。真正的转码要靠 `golang.org/x/text/encoding`，这里故意不引它；
走 `chcp 65001` / `PYTHONIOENCODING=utf-8` 那条路，是在源头上解决。

## 代价有多大？

整章讲的是四种失败，而修好它们的代码，比解释它们的代码还少。这个
比例在宿主这一层是常态，也正是宿主工作被低估的原因：这里没有一样
东西让 Agent 变聪明，而这些东西合起来，就是 demo 和工具的区别。

这一章之后，还是故意缺着这些：

- 模型说话的整个过程，你还是只能盯着一个空终端（**阶段 02**）。
- token 账单还是看不出个有用的形状（**阶段 02**，然后是 **04**）。
- 发生过什么，还是没有任何记录（**阶段 02**）。
- 历史还是无限长（**阶段 05**）。

## 练习

1. **把管道挂死复现一遍。** 超时只杀 `cmd.Process`，别动整棵树，
   然后跑 `(sleep 300 &) ; echo hi`。看着 `cmd.Wait()` 照样阻塞。
   这是整章里最值的十分钟。
2. **改成只留开头再截断**，然后丢给它一次失败的构建。注意看：错误
   信息——唯一有用的那部分——正好就是被丢掉的。
3. **把拒绝文案里"不要原样重试"那句删掉**，然后去拒一条命令。数数
   模型把同一条命令又提了几遍。工具结果的措辞就是 prompt 工程。
4. **把 `--timeout 1s` 设上**，再要一件慢活。确认模型真的读了
   `[TIMED OUT]` 那行并且改了做法，而不是把自己重复一遍。
5. **把 stdin 接上管道跑**，别带 `--yolo`。确认你拿到的是一句说清楚
   的话，而不是一整墙一声不响的拒绝。

## 读完这一章，你能回答什么

**超时把 shell 杀掉了，为什么 Agent 还是挂着？**
因为 `cmd.Wait()` 等的不是进程，是标准输出管道关闭；只要还有任何进
程握着写端，管道就一直开着。后台那个孙子进程把这个句柄继承走了，所
以只杀 shell，管道照样开着，`Wait` 照样阻塞。本来来救你的那个东西，
被它要救你脱身的那件事挂死了——所以修法必须一整块地杀掉进程组或者
job，而不是杀一个进程。

**收尸这一步放手之后，为什么抓到的输出也得当没看见？**
因为那五秒收尸截止，本来就是为 `g.kill()` 没起作用的情况准备的；往下
走就等于泄掉了持着输出缓冲区的那个 `Wait` goroutine。搬数据的
goroutine 可能还在往里写，这时候硬去读就是数据竞争，症状是几周之后
上下文里冒出一段乱码。泄一个 goroutine 还能活，把 Agent 卡死不能活，
而在缓冲区上竞争比这两样都糟——因为它出事不出声。

**为什么 Unix 这边严丝合缝，Windows 这边不是？**
因为 Unix 是在 `fork()` 和 `exec()` 中间那道缝里设进程组的——子进程
在它第一条指令跑起来之前就已经在自己组里，没东西逃得掉。Windows 没
法把 Job Object 划给一个还不存在的进程，`adopt()` 只能在 `Start()`
之后跑，中间就留下一道窗口：shell 头一个动作要是就生出个孙子进程，
它人就在 job 外面。这个仓库接下这道窗口，在代码里把它写清楚，而不是
装作它已经关上了。

**隔离的测试跑绿了，为什么不算隔离真的有效？**
因为测试和实现可能共用同一个错误假设。Git Bash 自己另铺了一套 POSIX
pid 命名空间，`$!` 打出来的是 MSYS 的 pid 不是 Windows 的，而拿这个
号去 `OpenProcess` 又不报错——它查的是碰巧占着这个号的那个无关进程，
于是建立在 `$!` 上的测试看着是过了，其实什么都没证明。所以这套测试
里还专门把这种失效演了一遍，也所以那次杀进程做过变异测试：把
`TerminateJobObject` 换成空操作。

**截断为什么两头都留，而不是只留开头？**
因为一条命令跑挂的时候，真正要紧的通常是最后那几行。那次真实运行
里，模型已经要了 `tail -100`，275KB 的日志照样被截，而唯一那行
`FATAL` 能活下来，只因为尾巴留住了；只留开头，交上去的会是一堆例行
`INFO`，问题问的那一行正好被丢掉。提示里还写明少了多少字节，因为
"删掉了 1.4MB"能告诉模型这条命令的形状不对，"删掉了一些东西"不能。

**`json.Unmarshal` 没报错，为什么不等于这个工具调用是合法的？**
因为 Go 会给缺失的键填零值，实测收到的那份 `{"raw_arguments":""}` 反
序列化不报任何错，结构体里的 `Command` 就是 `""`。于是"模型漏了必填
字段"和"模型发来一个空字符串"变成同一个值，Agent 跑起一条空命令，还
以为这是别人让它跑的。把字段声明成 `*string`，两者就分开了：`nil`
表示没有，`""` 表示空，两个都会被拒。

**`stop_reason` 为什么不能给跟它一起来的 body 作证？**
因为信封和 body 出自同一个系统。录下来的那份 Anthropic 响应，对一次
被中途切断的生成写着 `stop_reason: tool_use`，请求里 `max_tokens` 要
的是 10，回来的输出 token 是 136，带着的那个工具调用又不是 Agent 公
布的那份 schema。信封和 body 对不上的时候，会在你机器上跑起来的是
body。

**拒绝为什么走工具结果这条路，而不是返回错误？**
因为这个回合应该继续下去。录下来的那次运行里，模型提了 `ls -la`，被
拒；把方案收窄成 `ls`，又被拒；然后问了一个明白的问题——全在同一个
回合里，因为每一次拒绝回去的都是数据。那条路上要是返回 error，会话
就恰好死在有人认真盯着看的那一刻。

**权限闸为什么只能给你看一个命令字符串？**
因为只用一个 bash 工具，它手上就只有命令字符串。专门的 `write_file`
工具能画出 diff，`send_email` 工具能把收件人摆出来，`edit` 工具能这
么判：文件自模型上次读过之后又变了，那就拒绝写入；只读的工具还能标
成可以并行跑——而 `bash -c` 里装的是 `grep` 还是 `git push`，形状一
样不透明。一个工具买来的广度很便宜，而这就是账单：宿主每次想问一个
好问题，都要付一遍。

**解不出来的字节，为什么要替换掉，而不是原样放过去？**
因为它们不是坏的——它们在另一套没人告诉过 Agent 的编码里是对的，比
如中文 Windows 上原生程序吐出来的 GBK。原样放过去，就是把一堆乱码交
给模型，而模型会拿着它自信地往下推；换成 U+FFFD，失败就看得见了：模
型看到 `����` 就知道出了岔子。真正的转码要引一个依赖，这个仓库不打算
引；而在源头上把编码改对，比这两条路都强。

## 思考题

这些题在仓库里没有答案——它们是上面那四个修法留下来、要你自己拿主意
的地方。

1. Windows 那个 job 有一道已知的逃逸窗口，这里的做法是把它写下来，
   然后照样发出去。换成你，"记下来就行的缺口"和"必须关上才敢让别人
   跑"，这条线画在哪儿？Agent 改成无人值守地跑，这条线会挪吗？

2. 超时是一个数管所有命令，于是跑一整套测试和跑一条 `ls` 拿到的额度
   一样，而宿主手上能依据的只有一个字符串。要给每条命令单独定预算，
   你拿什么当依据？第一次判断错、而且错在把一次跑到 90% 的构建杀掉
   的那个方向上，会怎么样？

3. 截断管住的是一条命令的输出。十条命令，每条都刚好卡在预算下面，
   造成的破坏一样大，只是慢一点，而这一章里没有任何东西会察觉。这
   该算谁的问题——宿主、系统提示词，还是模型？你得量出什么，才下得
   了这个判断？

4. 拒绝回去的是一句话，请模型别原样重试这条命令。那是劝告，不是约
   束。一条模型没法拿话绕过去的规矩，你会把它放在哪儿？等到哪天这
   条规矩本身错了，这个位置又要你付出什么？

5. 这里每个修法都假定：只要把出了什么事讲清楚，模型就会改做法——这
   一章的几次运行也确实支持这个假定。可要是碰上一个不改的呢：同样
   一份 40MB 的转储，一连三个回合。宿主该改什么？除了把同一句提示再
   递一遍，你会让它做什么？
