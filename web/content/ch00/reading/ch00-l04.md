# 每一轮都要重发一遍

请求体里没有「接着上次说」这种东西。每一次 POST 带的都是当时的整个消息数组:

```go stages/00-loop/main.go:134-140
func (c *client) callModel(msgs []message) (*chatResponse, error) {
	body, err := json.Marshal(chatRequest{
		Model:     c.model,
		MaxTokens: 4096,
		Messages:  msgs,
		Tools:     []toolDef{bashTool()},
	})
```

`Messages: msgs` —— 就是关卡 01 那个只增不减的数组。所以接口报回来的 prompt tokens
量的不是你这一轮新说了什么,而是这一次请求整个有多大:

```go stages/00-loop/main.go:94-97
	Usage struct {
		PromptTokens     int `json:"prompt_tokens"`
		CompletionTokens int `json:"completion_tokens"`
	} `json:"usage"`
```

真实代码每一轮把这两个数打出来,你可以在自己的运行里看着它涨:

```go stages/00-loop/main.go:295-296
			fmt.Printf("  [tokens: prompt=%d completion=%d]\n",
				resp.Usage.PromptTokens, resp.Usage.CompletionTokens)
```

# 那次真实运行

docs/00-loop.md 里记了一次六轮的会话:找 bug、读文件、跑一遍、打补丁、再读一遍、
验证。[turns.go](#file:turns.go) 存的就是这六轮。

注意 [Grew](#line:turns.go:8) 这个字段的含义:它是这一轮往数组里添了多少 token,
不是这一轮的账单。两者不是一回事,而这一关要算的两个数,差别正是从这里来的。

# 两个数,两个问题

跑完你会看到两行:

- 最终会话大小:第 6 轮结束的时候,数组一共有多大。这是你手上剩下的东西。
- 实际账单:六次请求各自的 prompt 加起来。这是你付掉的东西。

[第一个空](#hole:1)决定第二个数怎么攒起来。攒之前先想清楚一件事:第 3 轮那次请求,
你送出去的到底是第 3 轮新添的那部分,还是前三轮加在一起的全部。

[表格里那一列](#hole:2)是同一个问题的另一半。它的表头写着 prompt,所以要问的只剩一件
事:一次请求的 prompt tokens,对得上手边这几个数里的哪一个。六行打出来,账单是从第几
轮开始跑赢会话本身的,也就看得见了。[最后一个空](#hole:3)把两个数变成一个比值。

# 为什么它比对话长得快

第 1 轮的内容,到第 6 轮的时候是第六次被计费。轮数每加一,前面所有轮都要再付一遍,
所以这不是「多花一点」,是增长的形状不一样:四十轮的会话,第一轮要付四十次。

这不是代码里的 bug。它就是「每一轮重发整个历史」的意思。六轮的差距还算温和,而这个
倍数只会随着会话继续往上走。

每一个正经的 agent 都有一个对付它的办法。这个仓库的答案在 stage 04:同一个实验跑
两遍,一遍开缓存,一遍 `--break-cache`,把差额变成一个数。跑完这一关的时候,把这两
行留着 —— 它是后面每一章都要对照的基线。
