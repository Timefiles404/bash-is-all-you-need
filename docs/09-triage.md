# Stage 09 — Triage

Until now, a failed model call ended the turn. The agent printed whatever error
value Go had handed it and stopped.

That is survivable while you are the only person running it against an endpoint
you control. It stops being survivable the moment somebody else uses it, because
most failures are not the end of anything. A rate limit clears. A gateway
restarts. A proxy cuts a connection halfway through a reply. An agent that gives
up on all of those gives up several times an hour, and each time it does, the
user loses a session that was going fine.

This chapter is about turning a failure into a decision. There are only three
decisions available:

- **wait**, then send the same bytes again;
- **send them somewhere else**, to a second provider;
- **stop**, and tell the person what happened.

Everything in `triage.go` exists to pick one of those three. The reason that
takes a whole file rather than an `if` statement is the subject of the next
section.

**Before you start.** You need stage 02's event bus, because this stage adds
three new kinds of event to it; stage 03's two protocol adapters, because the
same failure has to be classified whichever protocol produced it; and stage 04's
prompt cache, because the price of moving to a second provider is a cache you no
longer have.

**What you will build.** A failure type that carries enough information to
decide with, a table that maps observed failures onto the three decisions, a
wait that backs off and has a budget, and a list of providers to fall through.
About four hundred lines, nearly all of it in one new file.

---

## Where we are starting from

This is the entire error handling in stage 08:

```go
res, err := a.call(turn, msgs)
if err != nil {
    a.bus.Error("%v", err)
    return msgs
}
```

Three things are wrong with it, and only the first is the one people notice.

**There is no retry.** Obvious, and the easiest of the three to fix.

**The status code does not survive.** `a.call` ended with
`fmt.Errorf("http %d: %s", ...)`, which turns a number into prose. A caller who
wants to know whether this was a 429 has one option left:

```go
strings.Contains(err.Error(), "429")
```

People genuinely write that. It works until the day a message body contains the
number 429 for an unrelated reason, and then it works incorrectly and quietly.
Formatting an error into a string is lossy in exactly the way that matters here:
the thing you need to branch on is the thing you destroyed.

**The partial result was thrown away.** Look at how both adapters end:

```go
if err != nil {
    // No KindResponseEnd: the response did not end, it broke.
    return res, err
}
```

A non-`nil` result *and* a non-`nil` error, on purpose, with a comment saying so
since stage 02. Every stage until this one bound that first value and never
looked at it. Those tokens were generated by the model, which means they were
billed to you, and until now nothing in the agent knew they existed.

There is a fourth copy of the problem hiding in stage 05. The compaction routine
does its own HTTP POST, and its error path never read the response body at all —
so a compaction that failed could only ever report `http 500` with nothing after
it. Two code paths that classify the same failure differently are two paths you
cannot write one policy for, which is why part of this stage is deleting the
second one.

---

## The two rules that look right and are not

Almost everyone writes these two rules first. Both are wrong against the gateway
this repo was built against, and they are wrong in opposite directions.

> **"401 means the key is bad, so stop."**

A wrong *model name* returns 401 here. Not 404 — 401, with the same JSON shape
as a revoked key. The only difference is one field deep in the body:
`AuthError` for a bad key, `ModelError` for a model that does not exist.

Stopping is the right answer for one of those and throws away a perfectly good
session for the other, because a model this provider does not have may well be a
model the *next* provider does.

> **"5xx is transient, so retry with backoff."**

A malformed request body returns 500 here. A body in the wrong protocol's shape
also returns 500. Both are bugs in the client — in your own code — and a policy
that keys on the status number retries them forever. The retry never succeeds,
because the bytes are the problem and the bytes do not change. It also never
stops, because 500 is on the retry list.

Neither rule is fixed by reading the status code more carefully. Both are fixed
by carrying enough of the failure to decide with. That is the whole difference
between this file and `fmt.Errorf`.

## What a failure actually consists of

Before you can decide, you need to know four things, and the status code is not
any of them. It is recorded as well — it is in the struct at the end of this
section — but the previous section is the reason it cannot be the thing you
branch on.

**Where it broke.** A model call has four places it can fail, and they are not
interchangeable:

```go
const (
    phaseBuild   callPhase = "build"   // we could not even render the request
    phaseConnect callPhase = "connect" // no response: DNS, refused, TLS, reset
    phaseStatus  callPhase = "status"  // a response arrived and it was not 200
    phaseStream  callPhase = "stream"  // 200, then the body broke
)
```

The classifier looks at the phase *before* the status, because the phase answers
the question that governs everything else: **was anything generated?**

If the request never reached the model — a refused connection, a rejected
status — nothing was generated and nothing was billed. A retry is free. If the
stream opened and then broke, the model was generating the whole time. The
provider saw a completed request. You will be invoiced for it, and the retry is
a second invoice.

**What the provider called it.** Both protocols return a `type` field inside the
error body. It is the field that separates the two 401s above, so this stage
records it exactly as received and never normalises it. Normalising would throw
away the evidence for the one decision it exists to drive.

**What the body actually said.** Not a summary of it — the first 8 KiB,
verbatim. This is the field that looks redundant next to the other two and
earns its place most often. The wire notes recorded a 400 that came back with no
error wrapper at all: a 24-byte echo of the request, `{"model":"qwen3.7-plus"}`.
For that response there is no `type` and no `message`, and the raw body is the
only evidence in existence.

That case also decides how the agent phrases itself. Printing `http 400: ` with
nothing after the colon reads like a bug in the agent. Printing

```
http 400 with no error envelope: {"model":"qwen3.7-plus"}
```

names the absence and points at the server, which is where the reader needs to
look.

**What had already been generated.** The partial result from the paragraph
above, kept so the accounting can use it.

Put together:

```go
type CallError struct {
    Phase      callPhase
    Status     int           // 0 when there was no response
    Type       string        // the provider's error.type, verbatim
    Message    string
    Body       string        // first 8 KiB, verbatim
    RetryAfter time.Duration // what the server asked for, 0 if it did not
    Partial    *CallResult   // what the adapter had when the stream broke
    Err        error         // so errors.Is still works
}
```

The last field is worth a sentence. Wrapping the original error rather than
replacing it means `errors.Is(err, context.Canceled)` still works from the
outside, so this type adds information without taking any away.

## The three decisions

```go
TriageRetry     // the same bytes, later
TriageFallback  // the same bytes, elsewhere
TriageFatal     // stop, and say why
```

Every row in the table below comes from `docs/wire-notes.md`, and the rows that
are *not* observed behaviour say so. This is also `triage_test.go`'s table — the
test and the documentation are the same list, so they cannot disagree.

| observed | the obvious rule | what it actually is | verdict |
|---|---|---|---|
| `401` + `AuthError` | fatal | correct | **fatal** |
| `401` + `ModelError` | fatal — same status! | a *model* problem; another endpoint may have it | **fallback** |
| `401`, no envelope | crash on `error.type` | nothing to classify | **fatal** |
| `404` | fallback | correct | **fallback** |
| `429` | retry | *not observed here*; RFC 9110 | **retry** |
| `413` | retry | the bytes are the problem; only compaction changes them | **fatal** |
| `400` / `422` | retry the 5xx-shaped way | ours | **fatal** |
| `500` after a malformed body | transient | **a client bug wearing a server's status** | retry, short leash |
| `503` | transient | correct | retry, full leash |
| connect refused | retry | nothing generated, nothing billed | **retry** |
| stream broke, no type | retry | the transport died | **retry** |
| stream `overloaded_error` | retry | correct | **retry** |
| stream `invalid_request_error` | retry — it is a stream error | arrived because of what we sent | **fatal** |
| anything unclassified | retry | unknown | **fatal** |

Three rows in that table deserve to be read slowly.

**Matching `error.type` is a substring test, not an equality test.** The
observed values are `ModelError` and `AuthError` — capitalised words run
together. Both protocol specifications document the same field in lower case
with underscores: `not_found_error`, `invalid_request_error`. An equality check
written against either specification is correct against the documentation and
wrong against the wire. A substring test survives both spellings and any third
one the gateway invents next.

**`413` — payload too large — is fatal, not retryable.** It looks like
congestion and it is not. The request is too big, and the only thing in this
agent that changes the size of a request is compaction. Retrying sends the same
oversized bytes again.

**Anything unrecognised is fatal, not retryable.** This is the row people invert
by instinct, on the reasoning that an unknown failure might be temporary. But an
unclassified failure that gets retried is just a failure that happens several
times, and the retries hide it. Failing on the unknown case means the missing
table row announces itself the first time it occurs, in an event that carries
the status and the verbatim `error.type` — which is exactly what you need to
write the row.

### One rule on top: how many attempts each failure gets

```go
func (e *CallError) leash() int {
    if e.Phase == phaseStatus && e.Status >= 500 && e.Status != http.StatusServiceUnavailable {
        return 2
    }
    return 0 // the policy's full allowance
}
```

A `503` is a service genuinely telling you it is at capacity, and it gets the
full allowance. A bare `500` gets two attempts in total, because on this gateway
a 500 is at least as likely to be *our* mistake as their outage — the wire notes
recorded one for a malformed body and another for an OpenAI-shaped body posted
to the Anthropic route.

Two attempts is enough to ride out a momentary blip and far too few to hide a
permanent client bug behind a retry loop. That is the whole reasoning: pick the
number that distinguishes the two cases fastest.

## How long to wait

A retry that fires immediately is not a retry, it is a second failure. The
standard shape is to wait a little, then longer, then longer again. Two details
turn out to matter more than the shape.

### Use the server's number when it gives you one

Both protocols may return a `Retry-After` header, and RFC 9110 allows two
forms: a plain number of seconds, or an HTTP date. `parseRetryAfter` reads both,
and the server's number beats the computed backoff outright — it is the only
number in the whole function that came from something that knows when the
capacity returns.

Reading it as a specification rather than as a promise produces two guards:

```go
if secs <= 0 { return 0 }                    // "-5" is not a negative sleep
if d := t.Sub(now); d > 0 { return d }       // a date in the past means "now"
```

Without the first, a header the server meant as "immediately" flows into
`time.Sleep` as a negative duration, which returns instantly — turning the
backoff *off* at precisely the moment a server asked for one. Without the
second, a clock skew of a few seconds does the same thing. And because a server
is allowed to say "an hour", the value is clamped: the shape of the request is
honoured, the length is not.

This is also the least well-founded code in the stage, and it is worth saying so
plainly. Searching all 731 lines of `wire-notes.md` for
`429|Retry-After|timeout|502|503|504|408` returns exactly one hit, and it is not
captured bytes — it is the wire notes' own advice:

> Takeaway: never classify these errors by HTTP status. Retry on 429 and on
> connection failures; treat 401 as fatal-but-ambiguous and log `error.type`;
> and treat 5xx as *possibly* permanent, capping retries. Always guard against
> an error body that has no `error` field.

That is good advice, and this stage is largely its implementation. But the
gateway this repo was probed against never sent a 429, never sent a
`Retry-After`, and never dropped a stream on its own. Everywhere else in `docs/`
a claim rests on recorded bytes; this one rests on the RFC plus a local test
server. The distinction is not a formality — if the gateway's real `Retry-After`
turns out to be in milliseconds, or to appear on a status this table calls
fatal, nothing here would have caught it.

### Spread the retries out completely, not partially

```go
return time.Duration(rnd() * float64(exp))
```

That is a uniform random draw from zero up to the current backoff — sometimes
called full jitter. The more common version keeps half the delay fixed and
randomises the other half.

The difference matters here for a specific reason. Stage 07 spawns subagents
that share one HTTP client and one endpoint, so a hiccup at the provider fails
several calls within the same millisecond. If each of them waits *roughly* the
same time, they arrive together again, fail together again, and back off
together — the retry policy has synchronised its own clients into a burst aimed
at a service that is already struggling. Drawing from the full range breaks the
convoy on the first attempt.

## Where to send it instead

```sh
agent --provider primary --fallback backup,local
```

A list of providers, tried in order, with three properties chosen on purpose.

**Every rung is built and its key checked at startup**, before the first
request. A fallback that is constructed on demand fails on demand, and the
moment it is needed is the only moment it exists for. A typo in `--fallback`
should cost you a startup error, not a dead session in the middle of an outage.

**It never climbs back.** Once the agent moves to the second provider it stays
there for the session. Climbing back would mean answering "is the first one
healthy again", and that question cannot be answered without spending a real
call to ask. So a fallback is a downgrade you keep — which is exactly why every
switch emits an event. A session quietly served by the cheaper model for an hour
is the failure this design accepts, and it is only survivable if it is visible.

**Subagents share the ladder by pointer.** "This endpoint is refusing calls" is
a fact about the endpoint, not about the agent that discovered it; a child
should not have to teach its parent. That is the only place concurrency touches
this stage, and it produces the one line in the file that needs explaining:

```go
func (l *ladder) advance(from int) bool {
    if l.cur > from { return true } // a sibling already moved us
    ...
}
```

With two siblings the guard would be unnecessary — both failed on the same rung
and both write the same new value. The case it exists for has three
participants, and it is a *rewind*. A fails on rung 0 and moves to rung 1. C
fails on rung 1 and moves to rung 2. Then B — still holding the rung 0 it read
before any of that happened — asks to fall back. Without the guard it writes
`cur = 1`, and the next call goes to a provider two siblings have already given
up on.

For completeness, three things the ladder deliberately is not: not a load
balancer (nothing spreads traffic, the order never changes), not a circuit
breaker (see "never climbs back"), and not shared-nothing (see the pointer).

## What a broken stream costs

The gateway never dropped a stream on its own, so this failure had to be
manufactured. A throwaway reverse proxy — 121 lines around
`httputil.ReverseProxy`, not part of any stage — forwards the request upstream,
lets the model generate normally, and then cuts the connection part-way through
the body: `panic(http.ErrAbortHandler)` after 354 bytes, with a
`Content-Length` header that promised more.

The result is the asymmetry that makes this failure different from every other
one in the table. **The provider sees a completed generation and bills for it.
The client sees a broken stream and never receives the usage frame.**

```
  call failed (attempt 1, retry): the stream broke: unexpected EOF
  retrying in 313ms (attempt 2) — the stream broke: unexpected EOF

  ┌─ call 1 · tool_calls
  │ in 963    █░░░░░░░░░░░░░░░░░░░  full 3 · write 0 · read 960  100% cached
  ...
  ── session ──────────────────────
  cost: $0.000155
  1 retry
  retried attempts re-sent ≥963 prompt tokens (≥$0.000030)
```

That last line is a number no other agent reports, and it cannot come from the
API. Usage arrives at the *end* of a stream, and this stream did not end. So it
is inferred at the one moment a real figure for this prompt exists — the attempt
that finally worked — and printed as a lower bound with a `≥`.

The bound is honest rather than cautious. A cold call pays the cache **write**
price on its first attempt and the much cheaper **read** price on the retry, so
copying the successful attempt's split back onto the first attempt undercharges
it. The agent knows the figure is low and says so in the only way a number can.

There is also a consolation in that panel worth noticing: `full 3 · read 960 ·
100% cached`. The broken attempt was not entirely wasted — it warmed the prompt
cache, and the retry read it back. A broken stream is expensive the first time
and cheap every time after.

### Counting attempts, not waits

There is a subtlety in that counter which is easy to get backwards, and getting
it backwards produces a number that looks plausible.

Suppose instead of a broken stream you inject two 503s. The natural
implementation counts retries and multiplies by the prompt size, and it reports
this:

```
  cost: $0.000276
  retried attempts re-sent ≥1926 prompt tokens (≥$0.000301)
```

The re-billing is larger than the entire session. It is larger because it is
fiction: **a 503 is refused before generation, so the provider billed nothing
for those attempts.** A refused connection is free. A rejected status is free.
Only a stream that opened and then died has cost anything.

This is why `Phase` lives on the event and not only inside `CallError`. `Status`
cannot stand in for it — a connect failure and a broken stream both carry status
0. So the panel keeps two separate counters: every wait, and only those attempts
that actually reached the model. The same session then reports

```
  cost: $0.000287
  2 retries
```

Retries, and no re-bill. There is a test named
`TestARefusedRequestIsNotReBilled` whose only job is to keep it that way.

The general form of this is a lesson stage 04 and stage 05 both arrived at from
different directions: **an instrument that reports a plausible wrong number is
worse than one that reports nothing**, because the plausible number is the one
people quote.

## What a fallback costs

A prompt cache is per provider, per model and per prefix. Moving to the second
provider therefore starts cold by construction — not because anything went
wrong, but because that provider has never seen these bytes.

Here is the same 963-token prompt, warm and on a provider's first sight of it:

| | full price | cache read | cost of the prompt |
|---|---|---|---|
| warm | 3 | 960 | **$0.0000297** |
| first sight of this prefix | 963 | 0 | **$0.000289** |

Those two figures come from two different runs rather than adjacent turns of
one session. The cold one is the first call after the fallback shown earlier;
it is cold precisely because that provider had not seen this prefix — which is
the state a fallback produces, every time.

**9.7× for identical bytes.** Moving one rung discards the provider, the model
and the cached prefix at once. The turn you rescued cost you about ten prompts'
worth of cache discount, and it keeps costing that until the new provider's
cache warms — which, in a session that only had a few turns left, may be never.

None of this is an argument against falling back. It is an argument for the
event. The cost basis changed in the middle of the session, so the panel
re-prices from the moment of the switch rather than from the configuration it
started with. Without that, the second provider's tokens are billed at the first
provider's rates, and you get a cost report that is confidently wrong.

A useful side effect: a trace now records **which endpoint produced it**, and at
what prices. Until this stage you could read every byte of an archived session
and still not be able to reconstruct what it cost. `--replay` on a machine with
no `providers.json` now shows real money.

## Compaction is a model call too

Stage 05's summariser makes its own request, so it needs its own policy:

```go
res, err := retryLoop(bus, 0, pol.forCompaction(), newLadder(rung{p: p}), ...)
```

A one-rung ladder, deliberately. This call may be retried and may not be failed
over — switching the whole session's provider as a side effect of a
summarisation hiccup is not a recovery, it is a surprise, and the prices would
change underneath a user who was told the agent was "compacting".

And a shorter leash than the session's, whatever the session's is:

```go
if p.attempts > 2 { p.attempts = 2 }
if p.budget > 5*time.Second { p.budget = 5 * time.Second }
```

Compaction already has a safe failure — the agent carries on uncompacted and
says so — which makes giving up early cheap. Retrying hard is expensive twice
over: every attempt re-sends the entire transcript at full price, and it does so
while the turn that needed the space is still waiting.

## Three events, not one

```
call_error   what broke, and what we decided about it
retry        that we are waiting, how long, and whose number that is
provider     who serves calls from here on, and at what prices
```

They answer three different questions, which is why they are three events and
not one — the same argument stage 05 made about its compaction triple.

The important naming decision is that `call_error` is deliberately **not**
`error`. An `error` is terminal: the session telling a human it has failed. A
`call_error` is an attempt failing with a decision attached, and most of them
are followed by a success. Emitting those as errors teaches people to ignore the
word, which is how a real one gets missed.

In the trace viewer the verdict sits on the row, because when you read a trace
you are always working backwards from a symptom, and the question is never "what
broke" on its own. It is "what did it do about it":

```
   1    0.00s  provider         flaky (openai · mimo-v2.5) · session start
   4    0.31s  request          openai · 1 messages · 0 cache marks · 3.2kB
   5   37.15s  call_error       RETRY attempt 1 · the stream broke: unexpected EOF
   6   37.15s  retry            wait 313ms · attempt 2 · the stream broke: unexpected EOF
   7   37.46s  request          openai · 1 messages · 0 cache marks · 3.2kB
   8   43.88s  first_token      TTFT 6414ms
  20   44.26s  usage            prompt 963 (full 3 · write 0 · read 960) · out 41
```

Two `request` events and one `usage`. That asymmetry *is* the re-billing, and it
is visible without doing any arithmetic.

## What this stage does not do

- **No deadline on a model call.** `http.Client{Timeout: 10 * time.Minute}` is
  the only clock, and it covers the entire body read: a slow-but-alive stream at
  minute ten dies mid-generation, and nothing can cancel a call in flight.
  `BuildRequest` returns a `*http.Request` with no context attached, so the
  *interface* is the barrier. Stage 10 is where that changes.
- **A retryable failure is assumed safe to repeat.** It is, for a specific
  reason: a failed model call ran no tools, so repeating it changes nothing in
  the world. But that is a property of this agent's shape rather than of
  retrying, and it stops holding the day a tool call is dispatched before the
  stream completes.
- **The re-billing figure is an estimate**, labelled `≥` everywhere it appears,
  and it can only ever be a bound because the API cannot be asked.
- **Nothing feeds a partial result back to the model.** Whatever plan it was
  halfway through is gone, and half a tool call is worse than none. The partial
  is kept for the accounting, not for the conversation.
- **The provider list never climbs back**, so a long session can finish on the
  last rung of its ladder without anyone noticing except through the event.
- **The success test is `!= http.StatusOK`, not a 2xx range.** A 202 would be
  classified as a failure. No endpoint in this repo's evidence returns one, so
  it stays a latent row in the table rather than a fixed bug.

## Exercises

1. **Break the leash and watch it cost you.** Point `--provider` at a URL that
   always returns 500, with `--retry 8 --retry-budget 2m`. Then delete the
   `leash()` clause and run it again. Time both. The second number is what "5xx
   is transient" buys you.

2. **Add a 402.** `insufficient_quota` is the failure a hobby project meets
   first. Decide its verdict, and work out why it is not the same as 401. Write
   the row, then break the code on purpose to confirm the row is load-bearing.

3. **Make the fallback climb back.** After N successful calls on rung 1, send
   one call to rung 0 and promote it if it works. Then measure what that probe
   costs you in cache misses and decide whether you still want it. You have just
   built a circuit breaker, and that is the bill for one.

4. **Feed the partial back.** On a stream break, the partial sometimes contains
   *complete* tool calls — the wire notes recorded one complete `tool_use` next
   to one truncated one. Send them anyway rather than discarding, then find a
   case where doing so is wrong. It is not hard to find, which is why the
   default is to discard.

5. **Make `Retry-After` observed rather than specified.** Find an endpoint that
   really sends one, capture the bytes, and add the section to `wire-notes.md`.
   This is the one exercise here that improves the repo's evidence rather than
   its code.

## What you can answer now

**Why can a failed call not be classified by its HTTP status?**
Because on a real gateway one status covers unrelated causes. 401 is both a
revoked key (stop) and an unknown model (try elsewhere); 500 is both a provider
outage (wait) and a malformed request body (stop, it is your bug). The status
narrows the possibilities and does not decide.

**What is the first thing to look at instead?**
The phase — where in the call it broke. That answers "was anything generated",
which determines whether a retry is free or is a second invoice.

**Why are there exactly three verdicts?**
Because an agent has exactly three moves after a failed call: send the same
bytes again later, send them to a different provider, or stop. Any richer
classification collapses into one of those before it reaches the code that acts.

**Why is an unrecognised failure fatal rather than retryable?**
Because retrying an unclassified failure just repeats it while hiding it. Being
fatal makes the missing table row announce itself the first time it happens, in
an event that carries the status and the provider's own error type.

**Why match `error.type` with a substring rather than an equality check?**
Because the observed values (`ModelError`, `AuthError`) do not match either
protocol's documented spelling (`not_found_error`, `invalid_request_error`). An
equality test is correct against the docs and wrong against the wire.

**Why should retries be spread over the full backoff window rather than half?**
Because subagents share one endpoint, so a provider hiccup fails several calls
in the same millisecond. Half-randomised waits keep them clustered and they
collide on every attempt; drawing from the whole range separates them
immediately.

**Why is a `Retry-After` header trusted over the computed backoff?**
Because it is the only number in the calculation that came from something that
knows when capacity returns. It still gets guarded against negative values and
past dates, and clamped, because "trusted" is not "unbounded".

**What does falling back cost?**
About 9.7× on the prompt, measured: the prompt cache is per provider, per model
and per prefix, so rung 1 always starts cold. It also changes the cost basis
mid-session, which is why the switch is an event the panel re-prices from.

**Why does the re-billing counter count attempts that reached the model rather
than retries?**
Because refused connections and rejected statuses are free — nothing was
generated, so nothing was billed. Counting all retries produced a re-bill figure
larger than the entire session, which is a plausible wrong number, and those are
worse than none.

**Why is `call_error` not just `error`?**
Because most `call_error`s are followed by a success. Reporting them as errors
teaches the reader to ignore the word, and then a real error goes unnoticed.

## Questions to think about

These do not have answers in the repo. They are the ones where the answer
depends on what you are building.

1. This stage assumes a retried call is safe to repeat, because a failed model
   call ran no tools. Sketch an agent where that assumption breaks. What would
   have to be true of the *result* of a call for a retry to be dangerous, and
   what would you have to record to know?

2. The provider list never climbs back, and the justification is that testing
   the first provider costs a real call. Is there a source of that information
   that does not cost a call? What would you be trusting if you used it?

3. `413` is fatal because only compaction changes the size of a request. That
   makes the verdict a fact about this agent's architecture rather than about
   HTTP. Which other rows in the table are like that, and what happens to them
   in an agent that can also drop tool definitions or lower `max_tokens`?

4. The re-billing figure is a lower bound because usage only arrives at the end
   of a stream. If you could change one thing about the protocol to make it
   exact, what would it be — and what would a provider's reason be for not
   having done that already?

5. Everything in this chapter classifies failures of the *transport*. A model
   that returns a confident, well-formed, completely wrong answer is a failure
   too, and none of this machinery sees it. Where in the loop would that
   judgment have to live, and what could it possibly be keyed on?
