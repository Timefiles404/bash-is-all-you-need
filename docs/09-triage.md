# 阶段 09：分诊

到现在为止，模型调用一失败，这个回合就结束了。Agent 把 Go 递给它的
那个 error 值原样打印出来，然后停下。

只有你自己在用、端点也归你管的时候，这样活得下去。换成别人来用，立刻
就活不下去了，因为大多数失败根本不是什么终点。限流会过去。网关会重启。
代理会在回答说到一半时掐断连接。见到这些就放弃的 Agent，一小时要放弃
好几次，而每放弃一次，用户就丢掉一段本来跑得好好的会话。

这一章讲的是怎么把失败变成决策。能选的决策只有三种：

- **等**一会儿，把同样的字节再发一次；
- **发到别处去**，交给第二个供应商；
- **停下来**，告诉人到底出了什么事。

`triage.go` 里的每一行，都是为了在这三条里挑出一条。这件事为什么要占掉
一整个文件、而不是一句 `if`，就是下一节要讲的。

**动手之前。** 你需要阶段 02 的事件总线，因为这一阶段要往上面加三种新
事件；需要阶段 03 的两个协议适配器，因为同一个失败，不管是哪个协议产
出的，都得分得出来；还需要阶段 04 的 prompt 缓存，因为换到第二个供应商
的代价，就是一份你再也没有的缓存。

**你会做出什么。** 一个失败类型，装得下足够用来做决定的信息；一张表，
把观察到的失败映射到那三个决策上；一段等待，会退避，而且有预算上限；
还有一串供应商，可以逐级往下掉。大约四百行，几乎全在同一个新文件里。

## 我们从哪里出发

阶段 08 的错误处理，全部在这里：

```go
res, err := a.call(turn, msgs)
if err != nil {
    a.bus.Error("%v", err)
    return msgs
}
```

这里面有三处不对，而人们注意到的只有第一处。

**没有重试。** 明摆着，也是三处里最好修的一处。

**状态码活不下来。** `a.call` 的结尾是 `fmt.Errorf("http %d: %s", ...)`，
把一个数字变成了一句话。调用方想知道这到底是不是 429，就只剩一条路：

```go
strings.Contains(err.Error(), "429")
```

真有人这么写。它一直好用，直到哪天某条消息正文里因为别的原因带上了 429
这个数字——从那天起它就开始给出错的答案，而且一声不响。把错误格式化成
字符串，丢掉的恰好是这里最要紧的东西：你要拿来分支的那个东西，正是你亲
手毁掉的那个。

**部分结果被扔掉了。** 看看两个适配器的结尾：

```go
if err != nil {
    // 没有 KindResponseEnd：响应不是结束了，是断了。
    return res, err
}
```

非 `nil` 的结果*同时*带着非 `nil` 的错误，这是故意的，从阶段 02 起就有
注释写着。在这一阶段之前，每一阶段都把第一个返回值接了下来，却从来没看
过它一眼。那些 token 是模型生成出来的，也就是说它们已经算到你账上了，
而到现在为止，Agent 里没有任何东西知道它们存在。

同样的毛病还有第四份，藏在阶段 05 里。压缩例程自己发 HTTP POST，而它的
错误路径根本不去读响应体——所以压缩一旦失败，报得出来的永远只有
`http 500`，后面一个字都没有。同一个失败被两条代码路径分出两种结论，
这样的两条路径，你没法给它们写一份策略；所以这一阶段的一部分工作，就是
把第二条删掉。

## 两条看着对、其实不对的规则

几乎每个人最先写下的都是这两条。对着这个仓库当初开发时用的那个网关，
两条都是错的，而且错的方向正好相反。

> **"401 就是 key 不对，所以停。"**

*模型名*写错，这里回的也是 401。不是 404——是 401，JSON 的形状和一把被
吊销的 key 一模一样。区别只有 body 深处的一个字段：key 不对是
`AuthError`，模型不存在是 `ModelError`。

对其中一种，停是对的；对另一种，停就是白扔掉一个还能用的会话——因为这
个供应商没有的模型，*下一个*供应商很可能有。

> **"5xx 是瞬态的，所以带退避重试。"**

请求体畸形，这里回的是 500。body 写成了另一个协议的形状，回的也是 500。
两种都是客户端的 bug——是你自己代码里的 bug——而只认状态码的策略会一直
重试下去。重试永远不会成功，因为问题就出在那些字节上，而那些字节不会
变；它也永远不会停，因为 500 在重试名单上。

这两条都不是把状态码读得更仔细就能修好的。修好它们靠的是同一件事：把
失败本身带够，够到能拿来做决定。这就是这个文件和 `fmt.Errorf` 之间的
全部区别。

---

## 一次失败究竟由什么组成

要做决定，你得先知道四件事，而状态码一件都不占。它当然也记着——就在这一
节末尾那个 struct 里——但上一节讲的就是它为什么不能是你拿来分支的那个东西。

**在哪儿断的。** 模型调用有四个可能失败的地方，而它们互相替代不了：

```go
const (
    phaseBuild   callPhase = "build"   // 请求都还没渲染出来就挂了
    phaseConnect callPhase = "connect" // 没有响应：DNS、被拒、TLS、reset
    phaseStatus  callPhase = "status"  // 响应到了，而且不是 200
    phaseStream  callPhase = "stream"  // 200，然后 body 断了
)
```

分类器*先*看环节，后看状态码，因为环节回答的是那个统辖其余一切的问题：
**到底有没有生成过东西？**

请求根本没到过模型——连接被拒，或者状态码被驳回——那就什么都没生成，什
么都没计费，重试是免费的。流开起来又断掉，那模型自始至终都在生成：供应
商看到的是一次完成的请求，这笔钱会开进你的账单，而重试是第二笔。

**供应商管它叫什么。** 两个协议都会在错误体里回一个 `type` 字段。上面
那两个 401 就是靠它分开的，所以这一阶段收到什么就记什么，从不做归一化。
归一化会把证据丢掉，而这个字段存在的全部意义，就是驱动那一个决定。

**body 到底说了什么。** 不是它的摘要——是前 8 KiB，逐字保留。这个字段
摆在前两个旁边最像多余的，可它挣到位置的次数最多。线上记录里记下过一次
400，回来的东西连错误信封都没有：只是请求的 24 字节回显，
`{"model":"qwen3.7-plus"}`。对这条响应，`type` 和 `message` 都不存在，
原始 body 是世上仅有的证据。

这个情形也决定了 Agent 该怎么措辞。打印 `http 400: `，冒号后面空着，
读起来像是 Agent 自己的 bug。而打印

```
http 400 with no error envelope: {"model":"qwen3.7-plus"}
```

把这个"没有"点名说了出来，并且指向服务器——那正是读的人该看的地方。

**已经生成出来的东西。** 就是上面那段说的部分结果，留着，好让记账用得
上。

合起来：

```go
type CallError struct {
    Phase      callPhase
    Status     int           // 没有响应时是 0
    Type       string        // 供应商的 error.type，逐字保留
    Message    string
    Body       string        // 前 8 KiB，逐字保留
    RetryAfter time.Duration // 服务器要求的时长，没要求就是 0
    Partial    *CallResult   // 流断掉那一刻适配器手里有的东西
    Err        error         // 这样 errors.Is 还能用
}
```

最后那个字段值得单说一句。包住原来的错误、而不是替换掉它，意味着从外面
看 `errors.Is(err, context.Canceled)` 照样能用——所以这个类型只往上加信
息，不拿走任何东西。

## 三种决策

```go
TriageRetry     // 同样的字节，晚一点再发
TriageFallback  // 同样的字节，发到别处
TriageFatal     // 停下来，说清为什么
```

下面这张表里的每一行都来自 `docs/wire-notes.md`，而某一行如果*不是*观察
到的行为，它会自己说明。这也就是 `triage_test.go` 里那张表——测试和文档
是同一份清单，所以它们不可能各说各话。

| 观察到的 | 显而易见的规则 | 它其实是什么 | 裁决 |
|---|---|---|---|
| `401` + `AuthError` | 致命 | 对 | **致命** |
| `401` + `ModelError` | 致命——同一个状态码！ | *模型*的问题；换个端点可能就有 | **降级** |
| `401`，没有信封 | 在 `error.type` 上崩掉 | 没东西可分类 | **致命** |
| `404` | 降级 | 对 | **降级** |
| `429` | 重试 | *这里没观察到*；RFC 9110 | **重试** |
| `413` | 重试 | 问题在字节本身；只有压缩能改它们 | **致命** |
| `400` / `422` | 按 5xx 的路子重试 | 是我们的错 | **致命** |
| 畸形 body 之后的 `500` | 瞬态 | **穿着服务器状态码的客户端 bug** | 重试，牵绳拴短 |
| `503` | 瞬态 | 对 | 重试，牵绳放满 |
| 连接被拒 | 重试 | 什么都没生成，什么都没计费 | **重试** |
| 流断了，没有 type | 重试 | 传输死了 | **重试** |
| 流里的 `overloaded_error` | 重试 | 对 | **重试** |
| 流里的 `invalid_request_error` | 重试——它是流错误 | 它来是因为我们发出去的东西 | **致命** |
| 任何未分类的东西 | 重试 | 未知 | **致命** |

这张表里有三行值得慢慢读。

**`error.type` 用的是子串匹配，不是相等判断。** 观察到的值是
`ModelError` 和 `AuthError`——首字母大写的词直接连在一起。而两份协议规范
记下的都是小写加下划线：`not_found_error`、`invalid_request_error`。照着
其中任一份写出来的相等判断，对着文档是对的，对着线上是错的。子串匹配两
种拼法都扛得住，网关下次再发明第三种，它也扛得住。

**`413`——请求体过大——是致命，不是可重试。** 它看着像拥塞，其实不是。
请求就是太大了，而这个 Agent 里唯一能改变请求大小的东西是压缩。重试只会
把同样那些超大的字节再发一遍。

**认不出来的一律致命，不是重试。** 这一行是大家凭直觉最容易写反的，理由
听上去也挺像样：未知的失败也许只是暂时的。可未分类的失败拿去重试，不过
是把同一个失败重复几遍，而重试还顺手把它藏了起来。在未知这一档上直接失
败，缺的那一行才会在第一次出现时自己冒出来——它出现在一个带着状态码和逐
字保留的 `error.type` 的事件里，而这两样东西正好就是你补那一行需要的。

### 再加一条规则：每种失败能试几次

```go
func (e *CallError) leash() int {
    if e.Phase == phaseStatus && e.Status >= 500 && e.Status != http.StatusServiceUnavailable {
        return 2
    }
    return 0 // 策略给的全额
}
```

`503` 是服务真的在告诉你它满了，所以额度全给。光秃秃的 `500` 一共只给两
次尝试，因为在这个网关上，500 是*我们自己*搞错的可能性，不低于对方宕机
——线上记录里就记下过两次：一次是畸形的 body，还有一次是把 OpenAI 形状的
body POST 到了 Anthropic 路由上。

两次尝试，够扛过一次瞬间的抽风，又远不够把永久性的客户端 bug 藏在重试循
环后面。全部推理就这一句：挑那个能最快把两种情况分开的数。

## 该等多久

立刻就发的重试不叫重试，那叫第二次失败。标准做法的形状是：先等一小会
儿，再等久一点，再更久一点。而有两个细节，最后比这个形状更要紧。

### 服务器给了数字，就用它给的

两个协议都可能回一个 `Retry-After` 头，而 RFC 9110 允许两种写法：一个纯
粹的秒数，或者一个 HTTP 日期。`parseRetryAfter` 两种都读，而服务器给的
数字直接压过算出来的退避——整个函数里，只有它来自真正知道容量什么时候回
来的那一方。

把它当成规范来读、而不是当成承诺来读，就多出两道保护：

```go
if secs <= 0 { return 0 }                    // "-5" 不是一次负数的睡眠
if d := t.Sub(now); d > 0 { return d }       // 过去的时间点意思是"现在"
```

少了第一道，服务器本意是"立刻"的那个头，会当成负数时长流进
`time.Sleep`，而它立即返回——正好在服务器要求退避的那一刻，把退避*关掉*
了。少了第二道，几秒钟的时钟偏差会造成同样的事。而服务器有权说"一个小
时"，所以这个值会被夹住：请求的形状照办，长度不照办。

这同时也是这一阶段里立论最不牢的一段代码，而这话值得直说。拿
`429|Retry-After|timeout|502|503|504|408` 去搜 `wire-notes.md` 全部 731
行，正好命中一次，而那一次不是抓下来的字节——是线上记录自己写下的建议：

> 要点：永远不要按 HTTP 状态码给这些错误分类。429 和连接失败要重试；
> 401 当成致命但含糊，并记下 `error.type`；5xx 当成*可能*是永久的，
> 给重试设上限。永远要防着没有 `error` 字段的错误体。

建议是好建议，这一阶段基本上就是它的实现。可这个仓库探过的那个网关，从
来没发过 429，从来没发过 `Retry-After`，也从来没自己断过一次流。`docs/`
里其他每一处论断都踩在记录下来的字节上，这一处踩的是 RFC，加上一台本地
测试服务器。这个区别不是形式主义——万一这个网关真发的 `Retry-After` 是
以毫秒为单位的，又或者它出现在这张表判为致命的某个状态码上，这里没有任
何东西会发现。

### 把重试彻底摊开，不是摊一半

```go
return time.Duration(rnd() * float64(exp))
```

这是从零到当前退避时长之间均匀地取一个随机数——有时候管它叫全抖动。更常
见的那个版本是把一半的等待固定住，另一半随机。

这个区别在这里要紧，理由很具体。阶段 07 派出去的子 Agent 共用一个 HTTP
客户端、一个端点，所以供应商那边打个嗝，好几个调用就在同一毫秒里一起失
败。要是它们各自等的时间*大致*相同，就会再一起到达、再一起失败、再一起
退避——重试策略把自己的客户端同步成了一波齐射，枪口对着一个已经在挣扎的
服务。从整个区间里取数，第一次尝试就把这个车队打散了。

## 换个地方发

```sh
agent --provider primary --fallback backup,local
```

一串供应商，按顺序试下去，有三条性质是特意选的。

**每一级都在启动时就构建好、key 也验过**，早于第一个请求。按需构造的降
级目标就会按需失败，而它被需要的那一刻，正是它唯一为之存在的那一刻。
`--fallback` 里打错一个字母，代价应该是一次启动报错，而不是宕机当中一段
死掉的会话。

**它永远不往回爬。** Agent 一旦挪到第二个供应商，这个会话剩下的时间就都
待在那儿。要往回爬，就得回答"第一个是不是又好了"，而这个问题不花一次真
调用去问就答不出来。所以降级是一次你会一直留着的降级——正因如此，每一次
切换都要发一个事件。会话被便宜的模型悄悄伺候一个小时，就是这个设计接受
下来的那种失败；而它只有在看得见的时候才活得下去。

**子 Agent 按指针共用这把梯子。** "这个端点在拒绝调用"是关于端点本身的
事实，不是关于发现它的那个 Agent 的；子 Agent 不该还要回头去教它的父
Agent。这是并发在这一阶段唯一露面的地方，而它产出了这个文件里唯一一行需
要解释的代码：

```go
func (l *ladder) advance(from int) bool {
    if l.cur > from { return true } // 已经有兄弟把我们挪走了
    ...
}
```

只有两个兄弟的话，这道保护是多余的——它们在同一级上失败，写下的是同一个
新值。它真正为之存在的情形有三个参与者，而且那是一次*回退*。A 在第 0 级
失败，挪到第 1 级。C 在第 1 级失败，挪到第 2 级。这时 B——手里还捏着这一
切发生之前读到的第 0 级——来要求降级。没有这道保护，它会写下 `cur = 1`，
于是下一个调用被送去一个供应商，而那个供应商，两个兄弟都已经放弃了。

为了说全，这把梯子故意不是的三样东西：不是负载均衡器（没有任何东西在分
摊流量，顺序也永远不变），不是熔断器（见"永远不往回爬"），也不是无共享
的（见那个指针）。

## 断掉的流要花多少钱

那个网关从来没自己断过流，所以这个失败只能造出来。一个用完就扔的反向代
理——围着 `httputil.ReverseProxy` 写的 121 行，不属于任何一个阶段——把请
求转发给上游，让模型正常生成，然后在 body 传到一半时把连接切断：354 字
节之后 `panic(http.ErrAbortHandler)`，而 `Content-Length` 头承诺的还
更多。

结果就是那个不对称，也正是它让这个失败和表里其他每一个都不一样。**供应
商看到的是一次完成的生成，并且照此计费。客户端看到的是一个断掉的流，永
远收不到那个 usage 帧。**

```
  call failed (attempt 1, retry): the stream broke: unexpected EOF
  retrying in 313ms (attempt 2) — the stream broke: unexpected EOF

  ┌─ call 1 · tool_calls
  │ in 963    █░░░░░░░░░░░░░░░░░░░  full 3 · write 0 · read 960  100% cached
  ...
  ── session ──────────────────────
  cost: $0.000155
  1 retry
  retried attempts re-sent ≥963 prompt tokens (≥$0.000030)
```

最后那一行是别的 Agent 都不报的数字，而它也不可能来自 API：usage 在流的
*末尾*才到，而这个流没有末尾。所以它是在这个 prompt 唯一存在真实数字的
那一刻推算出来的——最后终于成功的那次尝试——再当成一个下界打印出来，带着
`≥`。

这个界是诚实，不是保守。冷调用第一次尝试付的是缓存**写**的价钱，重试付
的是便宜得多的**读**，所以把成功那次尝试的拆分照抄回第一次尝试，就把它
算少了。Agent 知道这个数偏低，并且用一个数字唯一能表达的方式把这件事说
了出来。

那个面板里还有一点安慰值得注意：`full 3 · read 960 · 100% cached`。断掉
的那次尝试并没有完全白费——它把 prompt 缓存热起来了，重试又把它读了回
来。断掉的流第一次很贵，之后每一次都便宜。

### 数的是尝试，不是等待

那个计数器里有个微妙的地方，很容易搞反，而搞反之后得到的是一个看着挺像
样的数字。

假设注入的不是断流，而是两个 503。最自然的实现是数重试次数，再乘上
prompt 的大小，于是它报出来的是：

```
  cost: $0.000276
  retried attempts re-sent ≥1926 prompt tokens (≥$0.000301)
```

这个重复计费比整个会话都大。它更大是因为它是虚构的：**503 是在生成之前
就被驳回的，供应商没有为那些尝试计过一分钱。** 被拒的连接是免费的。被驳
回的状态码是免费的。只有开起来又死掉的流，才真的花过钱。

所以 `Phase` 才挂在事件上，而不是只待在 `CallError` 里面。`Status` 顶替
不了它——连接失败和流断裂带的状态都是 0。于是面板分开记两个计数器：每一
次等待，以及只有那些真的到过模型的尝试。同一个会话现在报出来的是

```
  cost: $0.000287
  2 retries
```

有重试，没有重复计费。有个测试叫 `TestARefusedRequestIsNotReBilled`，唯
一的职责就是让它一直这样。

这件事更一般的形式，是阶段 04 和阶段 05 从不同方向走到的同一条教训：
**仪表报出一个貌似合理的错数字，比什么都不报更糟**，因为貌似合理的那个
数字，正是人们会拿去引用的那个。

## 一次降级要花多少钱

prompt 缓存是按供应商、按模型、按前缀分的。所以挪到第二个供应商，在构造
上就必然从冷开始——不是因为哪里出了岔子，而是因为那个供应商从没见过这些
字节。

下面是同一个 963 token 的 prompt，一次是热的，一次是供应商第一次见到
它：

| | 全价 | 缓存读 | prompt 的成本 |
|---|---|---|---|
| 热的 | 3 | 960 | **$0.0000297** |
| 第一次见到这段前缀 | 963 | 0 | **$0.000289** |

这两个数字来自两次不同的运行，不是同一个会话里相邻的两个回合。冷的那个
是前面那次降级之后的第一次调用；它冷，正是因为那个供应商还没见过这段前
缀——而这恰好就是每一次降级都会造出来的状态。

**一样的字节，9.7 倍。** 往下挪一级，把供应商、模型、缓存前缀一次性全丢
掉。你救回来的那个回合，代价是大约十个 prompt 的缓存折扣，而且会一直这
么付下去，直到新供应商的缓存热起来——在一个只剩几个回合的会话上，那可能
永远不会发生。

这些都不是反对降级的论证，是支持那个事件的论证。成本基准在会话中途变
了，所以面板是从切换那一刻开始重新定价的，不是照启动时的配置。没有它，
第二个供应商的 token 会按第一个供应商的价钱计费，你拿到的就是一份自信满
满却算错了的成本报告。

还有个有用的副作用：trace 现在会记下**是哪个端点产出了它**，以及在什么
价钱下产出的。在这一阶段之前，你可以把一份存档会话的每个字节都读完，还
是重建不出它花了多少钱。现在在一台没有 `providers.json` 的机器上跑
`--replay`，看到的是真钱。

## 压缩调用也是一次模型调用

阶段 05 的摘要器自己发请求，所以它需要自己的一份策略：

```go
res, err := retryLoop(bus, 0, pol.forCompaction(), newLadder(rung{p: p}), ...)
```

只有一级的梯子，这是故意的。这个调用可以重试，但不可以降级——摘要打了个
嗝，就顺手把整个会话的供应商换掉，那不叫恢复，那叫惊吓；而且价钱会在用
户脚底下变掉，而他被告知的只是 Agent"正在压缩"。

牵绳也比会话的短，不管会话的是多少：

```go
if p.attempts > 2 { p.attempts = 2 }
if p.budget > 5*time.Second { p.budget = 5 * time.Second }
```

压缩本来就有一种安全的失败方式——Agent 不压缩接着跑，并且把这件事说出来
——所以早点放弃代价很小。死命重试则要贵两遍：每一次尝试都按全价把整份记
录重发一遍，而且是在那个需要空间的回合还等着的时候干这件事。

## 三个事件，不是一个

```
call_error   什么坏了，以及我们对它做了什么决定
retry        我们正在等，等多久，以及那个数字是谁给的
provider     从这里往后由谁来服务调用，按什么价钱
```

它们回答的是三个不同的问题，所以才是三个事件而不是一个——和阶段 05 对它
那套压缩三件套讲的是同一个论证。

命名上要紧的那个决定，是 `call_error` 故意**不**叫 `error`。`error` 是
终结性的：会话在告诉人它失败了。`call_error` 是一次带着决定的尝试失败，
而它们后面大多跟着一次成功。把这些当成 error 发出去，只会训练人忽略这个
词，而真正的那一个就是这么被漏掉的。

在 trace 查看器里，裁决就写在那一行上，因为读 trace 的时候你总是从一个
症状往回倒推，而问题从来不只是"什么坏了"，而是"它对此做了什么"：

```
   1    0.00s  provider         flaky (openai · mimo-v2.5) · session start
   4    0.31s  request          openai · 1 messages · 0 cache marks · 3.2kB
   5   37.15s  call_error       RETRY attempt 1 · the stream broke: unexpected EOF
   6   37.15s  retry            wait 313ms · attempt 2 · the stream broke: unexpected EOF
   7   37.46s  request          openai · 1 messages · 0 cache marks · 3.2kB
   8   43.88s  first_token      TTFT 6414ms
  20   44.26s  usage            prompt 963 (full 3 · write 0 · read 960) · out 41
```

两个 `request` 事件，一个 `usage`。这个不对称*就是*那笔重复计费，不用算
术就看得见。

## 这一阶段没做到的

- **模型调用上没有期限。** `http.Client{Timeout: 10 * time.Minute}` 是
  唯一的钟，而它盖住的是整个 body 的读取：一个慢但还活着的流，到第十分
  钟会死在生成中途，而且没有任何东西能取消一个正在飞的调用。
  `BuildRequest` 返回的是不带 context 的 `*http.Request`，所以拦路的是
  *接口*本身。阶段 10 就是它改掉的地方。
- **可重试的失败被假定成可以放心重发。** 它确实可以，理由很具体：失败的
  模型调用一个工具都没跑过，所以重来一遍不会改变世界上的任何东西。但这
  是这个 Agent 的形状带来的性质，不是重试本身的性质；等哪天工具调用在流
  走完之前就被派发出去，它就不再成立了。
- **重复计费那个数字是估算**，出现的每一处都标着 `≥`，而它永远只能是一
  个界，因为没法去问 API。
- **没有任何东西把部分结果喂回给模型。** 它做到一半的那个计划没了，而半
  个工具调用比没有更糟。留下部分结果是为了记账，不是为了对话。
- **供应商清单永远不往回爬**，所以一个长会话可能就在梯子最后一级上收尾，
  除了那个事件，没人会注意到。
- **成功判定用的是 `!= http.StatusOK`，不是 2xx 区间。** 202 会被分类成
  失败。这个仓库的证据里没有哪个端点返回过它，所以它仍然是表里潜伏着的
  一行，而不是一个已经修掉的 bug。

## 练习

1. **把牵绳弄断，看它让你付多少钱。** 把 `--provider` 指到一个永远返回
   500 的 URL，加上 `--retry 8 --retry-budget 2m`，然后把 `leash()` 那
   个子句删掉再跑一遍。两次都计时。第二个数字，就是"5xx 是瞬态的"这句
   话买来的东西。

2. **加一个 402。** `insufficient_quota` 是每个业余项目最先撞上的那个失
   败。它该判哪个裁决，为什么和 401 不一样？先写出那一行，再故意把代码
   弄坏，确认这一行是承重墙。

3. **让降级能爬回去。** 在第 1 级上成功 N 次调用之后，往第 0 级发一个调
   用，通了就把它提回来。然后测一下这个探测在缓存未命中上花掉多少，再
   决定你还要不要它。你刚做出来的就是熔断器，而这就是熔断器的账单。

4. **把部分结果喂回去。** 流断掉的时候，部分结果里有时含有*完整*的工具
   调用——线上记录里记过一个完整的 `tool_use` 旁边跟着一个被截断的。别
   丢，照发出去，然后找一个这么做是错的场景。不难找，而这就是默认丢掉
   的原因。

5. **让 `Retry-After` 从"照规范写的"变成"观察到的"。** 找到任何一个真会
   发它的端点，把字节抓下来，把那一节加进 `wire-notes.md`。这是这里唯一
   一个练习，改进的是仓库的证据，不是它的代码。

## 读完这一章，你能回答什么

**为什么不能按 HTTP 状态码给失败的调用分类？**
因为在真实的网关上，同一个状态码盖着互不相干的原因。401 既是被吊销的
key（停），也是不存在的模型（换个地方试）；500 既是供应商宕机（等），
也是畸形的请求体（停，那是你自己的 bug）。状态码只能缩小范围，做不了
决定。

**那该先看什么？**
看环节——调用是在哪一步断的。它回答的是"有没有生成过东西"，而这决定了重
试是免费的，还是第二张账单。

**为什么裁决正好只有三种？**
因为一次调用失败之后，Agent 能走的路正好三条：把同样的字节晚点再发一
次，发给另一个供应商，或者停下来。再细的分类，在抵达真正动手的那段代码
之前，都会塌回这三条里的一条。

**为什么认不出来的失败判成致命，而不是可重试？**
因为把未分类的失败拿去重试，只是把它重复一遍，同时还把它藏起来。判成致
命，缺的那一行才会在第一次出现时自己冒出来，就在那个带着状态码和供应商
自己的 error type 的事件里。

**为什么 `error.type` 用子串匹配，而不是相等判断？**
因为观察到的值（`ModelError`、`AuthError`）和两个协议文档里的拼法
（`not_found_error`、`invalid_request_error`）都对不上。相等判断对着文
档是对的，对着线上是错的。

**为什么重试要摊在整个退避窗口上，而不是一半？**
因为子 Agent 共用一个端点，供应商打个嗝，好几个调用就在同一毫秒里失败。
只随机一半的等待会让它们继续挤成一团，每一次尝试都再撞一次；从整个区间
里取数，当场就把它们分开了。

**为什么 `Retry-After` 头比算出来的退避更值得信？**
因为在整个计算里，只有它来自真正知道容量什么时候回来的那一方。它照样要
防着负数和过去的日期，照样要被夹住，因为"值得信"不等于"没有上限"。

**降级要花多少钱？**
prompt 上大约 9.7 倍，这是实测出来的：prompt 缓存按供应商、按模型、按前
缀分，所以第 1 级永远是从冷开始。它还会在会话中途改掉成本基准，所以这次
切换是一个事件，面板要从它那一刻起重新定价。

**为什么重复计费的计数器数的是到过模型的尝试，而不是重试次数？**
因为被拒的连接和被驳回的状态码都是免费的——什么都没生成，就什么都没计
费。把所有重试都数进去，算出来的重复计费比整个会话还大，那是一个貌似合
理的错数字，而这种数字比不报更糟。

**为什么 `call_error` 不干脆叫 `error`？**
因为大多数 `call_error` 后面跟着的是一次成功。把它们当成 error 报出去，
只会训练读的人忽略这个词，然后真正的 error 就没人注意了。

## 思考题

这些题在仓库里没有答案。它们的答案取决于你在做的是什么东西。

1. 这一阶段假定重试的调用可以放心重发，理由是失败的模型调用一个工具都
   没跑过。设想一个让这条假定失效的 Agent。要让重试变得危险，一次调用
   的*结果*得满足什么条件？而你得记下什么，才能知道自己撞上了这种
   情况？

2. 供应商清单永远不往回爬，理由是试探第一个供应商要花掉一次真调用。有
   没有哪种信息来源，不用花掉一次调用就能拿到？如果你用了它，你其实是
   在信任什么？

3. `413` 判为致命，是因为只有压缩能改变请求的大小。这就让这条裁决变成了
   关于这个 Agent 架构的事实，而不是关于 HTTP 的。表里还有哪些行是这样
   的？换成一个还能砍掉工具定义、或者调低 `max_tokens` 的 Agent，它们会
   变成什么？

4. 重复计费那个数字是个下界，因为 usage 只在流的末尾才到。如果只让你改
   协议里的一样东西，把这个数字变精确，你会改哪一样？而供应商到今天还
   没这么做，理由又可能是什么？

5. 这一章分类的全是*传输*的失败。模型返回一个自信满满、格式漂亮、彻头
   彻尾错误的答案，那也是一次失败，而这套机器一点都看不见。这个判断该
   住在主循环的哪个位置？它又能拿什么当依据？
