# 十几行里的三个决定

agent 能做的每一件事都从这个函数走过去。它的注释先说了它不做什么:

```go stages/00-loop/main.go:207-212
// runBash executes one command and returns everything the model should see.
//
// Note what it does NOT do: no timeout, so a dev server hangs the agent
// forever; no output cap, so `find /` floods the context window. Both are
// stage 01. Note also that a non-zero exit is not an error here — it is an
// observation, and the model is the one who should react to it.
```

这一关把 `exec.Command` 换成了 [fakeExec](#file:exec.go),四条命令的结果是写死的,
好让你只盯着返回值的形状。真实代码里 `cmd.CombinedOutput()` 一次就把两股输出拼好
了;这一关把它们分开,所以[第一个决定](#hole:1)才真的是一个决定。

# 你答应过模型什么

工具的描述跟着请求一起发出去,模型是照着它来理解结果的:

```go stages/00-loop/main.go:107-108
	t.Function.Name = "bash"
	t.Function.Description = "Execute a bash command and return its combined stdout and stderr."
```

`combined stdout and stderr`。想一下:一条命令出了错,话通常写在哪一股上。模型看不到
那一股的时候,它手上还剩什么。

第四条命令 [python stats.py](#line:exec.go:26) 的 traceback 就在 stderr 上。
docs/00-loop.md 记的那次真实运行里,模型正是靠这段 traceback 找到 bug 的。

# 非零退出不是异常

一条退出码非零的命令并没有弄坏你的程序。它产出了信息,而该对这条信息作出反应的是
模型,不是你。在 `runBash` 里把错误 `return` 出去,agent 会正好停在它开始有用的
那一刻。

> 你的职责是如实地把这台机器报告给模型,而不是替模型挡着它。

这里有一处不显眼的地方,值得对着 [exec.go](#file:exec.go) 看。

[grep 那条](#line:exec.go:23)退出码是 1,并且什么都没输出 —— grep 没找到东西的时候
就是这样。[mkdir 那条](#line:exec.go:20)成功了,也什么都没输出。

如果回给模型的只有输出,这两条在它眼里长得一模一样:一片空白。[第二个空](#hole:2)
决定它们还分不分得开,而它其实问了两件事 —— 失败这件事本身要不要出现在结果里,以及
它是补在输出后面,还是把输出整个换掉。第四条命令能帮你判断第二件:traceback 和
「命令失败了」,模型两样都要。

# 空输出

一个空字符串回到对话里,和这条消息不存在没什么区别。模型看到一片空白,最合理的反应
是把同一条命令再跑一次。[第三个空](#hole:3)是为了让「跑过了,没有输出」变成一句它
读得懂的话。

`runBash` 的返回值是模型对这台机器的全部观察。它能分辨的东西,就是这个函数决定让它
分辨的东西 —— 四条命令跑完,输出里能看出几种不同的结局,是这三个选择一起定下的。
