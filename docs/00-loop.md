# 阶段 00：主循环

**你会做出什么**：一个能翻代码、跑命令、改文件、再回头验证自己成果的
coding Agent。

**代价**：一个文件，346 行 Go——去掉整行注释还剩 253 行，而这个文件的注释
写得很密——标准库以外一个依赖都没有。

这个比例就是第一课。Agent 本身不是什么大工程。这个仓库里所有的硬骨头
都在这一阶段**之后**，而且没有一块是为了让 Agent 更聪明。

---

## 按这个顺序读

`stages/00-loop/main.go`，三个函数：

1. **`main()`** —— 主循环。先读它，其余全是它调用的细节。
2. **`callModel()`** —— 一次 HTTP POST。这里没有 SDK，而 SDK 底下也就是
   这么点东西。
3. **`runBash()`** —— 十四行。Agent 能做的一切都得从这里过。

## 循环长什么样

```
用户输入一个任务
  └─ 把 {role:"user"} append 到 messages
     └─ 循环：
        ├─ 带上整个 message 数组 POST /chat/completions
        ├─ 把 assistant 的回复 append 到 messages
        ├─ 打印 [tokens: prompt=… completion=…]
        ├─ 有文本？→ 打印出来，不管这一轮是不是同时还要了工具
        ├─ 没有 tool_calls？→ 退出循环
        └─ 对每个 tool_call：
             跑掉那条命令
             把 {role:"tool", tool_call_id, content: output} append 上去
           → 回到开头
```

两条不变式撑着整个循环，而且都是承重墙：

**消息数组只增不删。** 不改、不删、不重排。这段对话**就是** Agent 的记忆，
每个请求都把它整个再发一遍。阶段 05 是我们第一次动这条规矩，破它是要
交学费的。

**每个工具调用都得有结果回去。** 模型要了三条命令你只回两条，下一个
请求直接不合法。命令跑挂了也一样——失败**本身**就是那个结果，下面细说。

---

## 错误是观察，不是异常

`runBash` 里最常见的新手错误就这一个：

```go
func runBash(shell, command string) (string, error) {   // ← 第一步就错了
    out, err := cmd.CombinedOutput()
    if err != nil {
        return "", err                                   // ← 然后就有了这一句
    }
```

真正的签名只返回一个 `string`，这就是那个决定。没有地方放 error，因为退出码非
零本来就不是一个 error。

退出码非零，不代表你的程序坏了。它产出了信息，而该对这份信息作出反应的
是模型，不是你。看下面那次真实运行：`python stats.py` 以 1 退出，吐出
一段 `ZeroDivisionError` 的 traceback，我们把 traceback 原样递回去，模型
靠它定位到了 bug。要是那一行返回了 Go 的 error，Agent 就正好停在它刚开始
有用的那一刻。

这个直觉一路往上都成立：你的活是把世界如实报给模型，不是替模型把世界
挡住。

## 实验：看着账单涨起来

开一个临时目录，塞一个它必须自己找出来的 bug，然后跑。

```sh
go build -o agent ./stages/00-loop
mkdir -p sandbox && cd sandbox
# ... 往这里放一段坏掉的代码 ...
export AGENT_BASE_URL=... AGENT_API_KEY=... AGENT_MODEL=...
../agent
> 这个目录的代码里有个 bug。找出来、修掉、再验证一遍。
```

下面是一次真实运行的 token 账，六个回合（找 bug → 读文件 → 跑一遍 →
打补丁 → 再读 → 验证）：

| 回合 | 它干了什么 | prompt token |
|---:|---|---:|
| 1 | `ls -la` | 429 |
| 2 | `cat README.md; cat stats.py` | 613 |
| 3 | `python stats.py` → traceback | 737 |
| 4 | `sed -i ...` 打补丁 | 932 |
| 5 | `cat stats.py` | 1079 |
| 6 | `python stats.py` → 干净了 | 1192 |

把右边那列加起来：**计费 4982 个 token**，而这段对话最终只有
**1192 个 token**。做出来的东西值 1192，我们付了 4.2 倍。

这不是代码里的 bug，这就是"每回合重发整个历史"的字面含义，而且它是
平方级的：一个 40 回合的会话，最早那几个回合要付四十遍钱。任何一个
认真的 Agent 都得给出对策。我们的对策在**阶段 04**——同一个实验跑两遍，
一遍开缓存，一遍加 `--break-cache`，差多少就有数了。

这张表留着。后面整个仓库都拿它当基准线。

## 故意没做的那些

下面每一条都是阶段 01 的题目。别急着看补丁，先想办法把它们一个个踩出来
——踩坑的印象比补丁深得多。

| 缺什么 | 怎么把它踩出来 |
|---|---|
| 输出截断 | 让它 `find /`，或者读一个大文件，看上下文窗口被噪音填满。 |
| 命令超时 | 让它起一个开发服务器，然后 Agent 就永远挂在那儿了。 |
| 进程树清理 | 就算有超时，被杀掉的 shell 照样能留下一堆孤儿子进程。 |
| 权限闸 | 没有任何东西挡得住 `rm -rf`。所以才要你用临时目录。 |
| 流式输出 | 模型说话的整个过程，你只能盯着一个空终端。 |
| `finish_reason` | 我们只判断"有没有工具调用"。`length`（撞到 `max_tokens`）会被当成正常说完，一声不响。 |

`maxTurns` 这道保险丝是唯一提前进来的保命功能。少了它，一个卡在重试
循环里的模型能趁你读这个文件的工夫把你的 key 烧掉。

## 线上观察

真实 API 干过的事，`main.go` 里的类型不得不为它们让路：

- **带工具调用的那一回合，`content` 回来是 `null`**，不是 `""`。Go 的
  `json.Unmarshal` 碰到 null 什么也不做，所以一个普通 `string` 字段能扛
  过去——换一门对 null 更严格的语言，这里就炸了。
- **`tool_calls[].function.arguments` 是 JSON *字符串*，不是对象。**
  必须解析它，永远不要拿字符串去匹配。
- **会思考的模型还会多给一个 `reasoning_content`。** 这一阶段直接丢掉；
  阶段 02 会把它画出来，阶段 03 讲它怎么对应到 Anthropic 协议的
  `thinking` 块。

## 练习

1. **把 tool_call 的配对弄坏。** 故意少 append 一条 `role:"tool"` 消息，
   然后读 API 回的错误。这一下学到的协议知识比读文档多。
2. **把系统提示词删掉。** 看 Agent 怎么退化——它会开始让**你**去跑命令。
   所谓"Agent 效果"，大半就住在那个字符串里。
3. **把 `callModel` 里的 `MaxTokens: 4096` 改成 100。** 这时 `finish_reason` 会回 `length`，
   Agent 说到一半被截断，还一声不响。阶段 01 修的就是这个。
4. **换个模型指过去。** 任何 OpenAI 兼容的端点都行，本地 Ollama 也算。
   小模型会产出不合法的工具调用——那不是你的代码坏了，而且值得早点
   见一次。

## 读完这一章，你能回答什么

**一个能干活的 coding Agent，为什么几百行就够了？**
因为这个循环本身就这么小：把对话发出去，把回来的命令跑掉，把结果
append 上去，再来一遍。底下没有 SDK——`callModel()` 就是一次 HTTP
POST——而翻代码、改文件、回头验证，一个工具全包了。这个仓库里的硬
骨头都在这一阶段之后，而且没有一块是为了让 Agent 更聪明。

**命令以非零退出，为什么不返回 error？**
因为跑挂的命令并没有弄坏你的程序，它产出了信息，而该对这份信息作出
反应的是模型。本章那次运行里，`python stats.py` 以 1 退出，带回一段
`ZeroDivisionError` traceback，我们把它原样递了回去，模型靠它定位到
了 bug。要是那里返回 Go 的 error，Agent 就正好停在它刚开始有用的那
一刻。

**为什么每个工具调用都必须有结果回去？**
因为协议把它们配成对：模型要了三条命令你只回两条，下一个请求就不合
法。跑挂的和跑通的一视同仁，因为失败本身就是那个结果。练习 1 存在的
意义，就是让你故意把这个配对弄坏一次，再去读 API 怎么说。

**消息数组为什么只准增、不准删？**
因为这段对话就是 Agent 的全部记忆。不改、不删，每个请求都把它整个再
发一遍；Agent 知道自己见过什么、做过什么，记着这件事的只有这一个地
方。阶段 05 是这条规矩第一次被打破，破它是要交学费的。

**一场对话最终只有 1192 个 token，4982 个计费 token 是从哪来的？**
把那六个回合的 prompt 那一列加起来就是。每个回合都要把它前面的东西
重发一遍，于是早期回合在后面每个回合上都要再付一次钱——加起来是做出
来那个东西的 4.2 倍。对话的最终大小是你手上剩下的，那一列的和才是账
单上的数。

**这笔钱为什么涨得比对话本身还快？**
因为重发的次数是跟着回合数一起长的：四十个回合的会话，第一个回合要
付四十遍钱。六个回合 4.2 倍还算温和，而只要会话还在继续，这个比值就
一直往上爬。任何一个认真的 Agent 都得给出对策，这个仓库的对策在阶段
04。

**`maxTurns` 凭什么是唯一提前进来的保命功能？**
因为少了它，一个卡在重试循环里的模型会一直调 API，只要你不去关那个
进程。截断、超时、权限闸，各自挡的是一条坏命令；`maxTurns` 挡的是一
个完全照代码行事、却哪儿也没去的 Agent——而这正是你还在读代码的时候
最容易撞上的那种失败。

**`tool_calls[].function.arguments` 为什么必须解析，而不能当字符串
匹配？**
因为这个字段是 JSON *字符串*，而字符串里装的又是 JSON——你要的值隔着
第二层编码，还带着自己那套转义。再反序列化一次，拿到的是有类型的结
构体；拿原始字符串去匹配，拿到的东西只在你碰巧试过的那几个例子上能
跑，跑不跑得通全看模型这回碰巧怎么排参数。

**`content` 回来是 `null`，为什么这里没出事？**
因为带工具调用的那一回合，API 发回的是 `null` 而不是 `""`，而 Go 的
`json.Unmarshal` 碰到 null 什么也不做，一个普通 `string` 字段就停在
零值上。这是运气，不是设计——正因为是运气才要写下来：换一门对 null
更严格的语言，炸的就是这个字段。

**在 `max_tokens` 处被切断的回复，为什么看着像一个说完的回合？**
因为这个循环对每个回复只问一个问题——有没有工具调用——而说到一半被
截断的回复通常一个都没有。`finish_reason` 从头到尾没人读，于是
`length` 和"模型话说完了"长得一模一样。阶段 01 修的就是这个。

## 思考题

这些题在仓库里没有答案——它们是那种随你要做的东西而给出不同答案的
决定。

1. 回合是在模型不再要工具的时候结束的，于是"做完了"和"放弃了"成了
   同一个事件。还有什么可以用来结束一个回合？Agent 又得看什么，才分
   得清这两者？

2. 让这个 Agent 表现得体的东西，大半住在系统提示词里，不在代码里。
   假设你想要某种行为——比如宣布修好之前必须先跑一遍测试——你凭什么
   判断它该放进那个字符串，还是该放进宿主？又要靠什么才能发现自己选
   错了？

3. `maxTurns` 保的是回合数，可你花出去的是 token，而一个回合能花多
   少没有上限。换成你，保险丝会装在哪个量上？这根保险丝又得放在什么
   位置，才能在钱花光之前把这次运行停下来，而不是花光之后？

4. 历史只增不删，阶段 04 和阶段 05 各给了一种对策。在读它们之前先自
   己想一遍：五十个回合的历史，你会先扔掉哪一部分？又怎么发现自己扔
   掉的东西模型其实还要用？

5. 这里没有任何东西限制 Agent 能跑什么，给出的建议是用临时目录——而
   临时目录一碰到真活就不管用了。换成你，真正要限的是什么？这道限制
   落在 prompt 里、落在工具里，还是落在工具启动的那个进程里？
