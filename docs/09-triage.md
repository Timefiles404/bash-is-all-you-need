# 阶段 09：分诊

就一个想法：

> **错误是决策，不是字符串。**

模型调用刚失败的那一刻，Agent 能走的路只有三条：等一会儿，把同样的字节
再发一次；发到别处去；停下来，说清为什么。`triage.go` 里的每一行代码，
都是为了把一次失败归进这三条之一。

听起来像个小小的 `if`。它之所以占掉一整个文件，是因为人人都会最先写下
的那两条规则，**在这个仓库当初对着写的那个端点上都是错的**，而且错的
方向正好相反：

```
"401 就是 key 不对，所以停。"
    模型名写错，这里回的也是 401，信封形状和一把被吊销的 key
    一模一样。对其中一种，停是对的；对另一种，停就是白扔掉一个
    还能用的会话。

"5xx 是瞬态的，所以带退避重试。"
    请求体畸形，这里回的是 500。那是客户端自己的 bug，而只认
    状态码的策略会一直重试下去：它永远不会成功，也永远不会
    停。
```

这两条都不是把状态码读得更仔细就能修好的。修好它们靠的是同一件事：把
失败本身带够，够到能拿来做决定——这就是 struct 和 `fmt.Errorf` 的区别。

## 阶段 08 落在地上的东西

在这一阶段之前，Agent 的错误处理一共六行：

```go
res, err := a.call(turn, msgs)
if err != nil {
    a.bus.Error("%v", err)
    return msgs
}
```

这六行里有三处不对，而"没有重试"只是其中一处。

**状态码活不下来。** `a.call` 返回的是 `fmt.Errorf("http %d: %s", ...)`，
调用方想知道这到底是不是 429，只剩
`strings.Contains(err.Error(), "429")` 一条路。真有人这么写。等到哪天
某条消息正文里恰好带着这个数字，它就错了。

**部分结果被丢掉了。** 两个适配器的结尾都是

```go
if err != nil {
    // 没有 KindResponseEnd：响应不是结束了，是断了。
    return res, err
}
```

——非 nil 的结果*同时*带着非 nil 的错误，这是故意的，从阶段 02 起就有
注释写着。到这一阶段之前，每一阶段都把那个值接住了，却从来没看过一眼。
那些 token 已经生成出来了。生成出来的 token 是要计费的。

**压缩自己还有一份更糟的拷贝。** 阶段 05 的摘要器自己发 POST，而它的
错误路径根本不读响应体：压缩失败了，能报出来的永远只有 `http 500`，
别的一个字都没有。同一个失败，两条路径分出两种结论——这样的两条路径，
你没法给它们写一份策略。

## 环节在前，状态码在后

```go
const (
    phaseBuild   callPhase = "build"   // 请求都还没渲染出来就挂了
    phaseConnect callPhase = "connect" // 没有响应：DNS、被拒、TLS、reset
    phaseStatus  callPhase = "status"  // 响应到了，而且不是 200
    phaseStream  callPhase = "stream"  // 200，然后 body 断了
)
```

分类器先看环节，后看状态码，因为环节回答的是那个决定其余一切的问题：
**到底有没有生成过东西？** 什么都没生成，重试就是免费的。生成过东西，
第一次尝试就已经在账单上了，重试是第二笔。

`CallError` 装的就是做决定所需的那些东西：

```go
type CallError struct {
    Phase      callPhase
    Status     int           // 没有响应时是 0
    Type       string        // 供应商的 error.type，逐字保留
    Message    string
    Body       string        // 前 8 KiB，逐字保留
    RetryAfter time.Duration // 服务器要求的时长，没要求就是 0
    Partial    *CallResult   // 流断掉那一刻适配器手里有的东西
    Err        error         // 这样 errors.Is 还能用
}
```

`Body` 摆在 `Type` 和 `Message` 旁边像是多余的，可它挣到位置的次数最多。
§D11 记下过一次 400，回来的东西**连错误信封都没有**——只是请求的 24
字节回显，`{"model":"qwen3.7-plus"}`。对这条响应，`Type` 和 `Message`
全是空的，原始 body 是唯一的证据。所以消息里把这个"没有"点名说出来，
而不是打印 `http 400: ` 却让冒号后面空着：空尾巴读起来像 Agent 自己的
bug，而"`http 400 with no error envelope: {"model":"qwen3.7-plus"}`"
指向的是服务器。

`Type` 从来不做归一化。状态码分不出模型名写错和 key 被吊销的时候，靠
的就是这个字段，归一化它等于把驱动那个决定的证据本身丢掉。

## 那张表

每一行都能追回 `docs/wire-notes.md`，而某一行如果*不是*观察到的行为，
它会自己说明。这就是 `triage_test.go` 里那张表，两张是同一张：

| 观察到的 | 显而易见的规则 | 它其实是什么 | 裁决 |
|---|---|---|---|
| `401` + `AuthError` | 致命 | 对 | **致命** |
| `401` + `ModelError` | 致命——同一个状态码！ | *模型*的问题；换个端点可能就有 | **降级** |
| `401`，没有信封 | 在 `error.type` 上崩掉 | 没东西可分类 | **致命** |
| `404` | 降级 | 对 | **降级** |
| `429` | 重试 | *这里没观察到*；RFC 9110 | **重试** |
| `413` | 重试 | 问题在字节本身；只有压缩能改它们 | **致命** |
| `400` / `422` | 按 5xx 的路子重试 | 是我们的错 | **致命** |
| 畸形 body 之后的 `500` | 瞬态 | **穿着服务器状态码的客户端 bug** | 重试，牵绳拴短 |
| `503` | 瞬态 | 对 | 重试，牵绳放满 |
| 连接被拒 | 重试 | 什么都没生成，什么都没计费 | **重试** |
| 流断了，没有 type | 重试 | 传输死了 | **重试** |
| 流里的 `overloaded_error` | 重试 | 对 | **重试** |
| 流里的 `invalid_request_error` | 重试——它是流错误 | 它来是因为我们发出去的东西 | **致命** |
| 任何未分类的东西 | 重试 | 未知 | **致命** |

有两行值得单独拎出来说。

**`error.type` 是子串匹配，不是相等判断。** §D11 观察到的是 `ModelError`
和 `AuthError`，PascalCase，而两份协议规范写的都是 snake_case
（`not_found_error`、`invalid_request_error`）。拿任何一种拼法去做相等
判断，对着文档是对的，对着线上是错的。

**未分类是致命，不是重试。** 未分类的失败拿去重试，就是把同一个失败
重复一遍。它发出的 `call_error` 事件带着状态码和逐字保留的
`error.type`，缺的那一行就是靠它找出来的。

### 牵绳

多一条规则，就一个理由：

```go
func (e *CallError) leash() int {
    if e.Phase == phaseStatus && e.Status >= 500 && e.Status != http.StatusServiceUnavailable {
        return 2
    }
    return 0 // 策略给的全额
}
```

`503` 是真的容量信号，额度全给。光秃秃的 `500` 一共只给两次尝试，因为
在这个端点上，它是*我们自己*配错的可能性不低于对方宕机——§D11 拿到 500
的场合有两个：一个畸形的 body，*还有*把 OpenAI 形状的 body POST 到
Anthropic 路由上。两次尝试够扛过一次抽风，又远不够把永久性的错误藏在
重试循环后面。

## Retry-After，以及这个仓库证明不了的那件事

`parseRetryAfter` 把 RFC 9110 允许的两种写法都读了：delta-seconds 和
HTTP-date。服务器给的数字直接压过算出来的退避时间，因为这个函数里只有
它来自真正知道容量什么时候回来的那个人。

它同时也是**这一阶段里立论最不牢的一段代码，而这话值得大声说出来。** 拿
`429|Retry-After|timeout|502|503|504|408` 去 grep `wire-notes.md` 全部
731 行，正好命中一次，而那一次不是抓下来的字节——是 §D11 自己写下的
规范性结论：

> 要点：永远不要按 HTTP 状态码给这些错误分类。429 和连接失败要重试；
> 401 当成致命但含糊，并记下 `error.type`；5xx 当成*可能*是永久的，
> 给重试设上限。永远要防着没有 `error` 字段的错误体。

建议是好建议，阶段 09 基本上就是它的实现——可这个仓库探过的那个网关，
从来没真发过 429，从来没发过 `Retry-After`，也从来没断过一次流。这个
仓库的证据里，`Retry-After` 一次都没被记录下来。`docs/` 里其他每一个
论断都踩在字节上，这一个踩的是 RFC，加上 `triage_test.go` 里的一台本地
服务器。仓库别处写"观察到"的地方，这里写的是"照规范写的"。

把它当规范来读、而不是当愿望来读，就多出两道保护：

```go
if secs <= 0 { return 0 }                    // "-5" 不是一次负数的睡眠
if d := t.Sub(now); d > 0 { return d }       // 过去的时间点意思是"现在"
```

少了它们，服务器本意是"立刻"的那个头，会当成负数时长流进 `time.Sleep`，
而它立即返回——正好在服务器要求退避的那一刻把退避关掉。服务器也有权说
"一个小时"，所以这个值会被夹住：请求的形状照办，长度不照办。

### 全抖动，不是半抖动

```go
return time.Duration(rnd() * float64(exp))
```

从 `[0, exp)` 里均匀取一个数，不是更常见的 `exp/2 + rand(exp/2)`。这个
区别在这里格外要紧：阶段 07 派出去的子 Agent 共用一个 `http.Client`、
一个端点，供应商打个嗝，好几个调用就在同一毫秒里一起失败。半抖动会让
这些调用继续挤成一团，每一次尝试都再撞一次。把自己的客户端同步起来的
重试策略，就是一台负载发生器，枪口对着那个已经在挣扎的服务。

## 梯子

```sh
agent --provider primary --fallback backup,local
```

每一级都在**启动时**就构建好、key 也验过，早于第一个请求。按需构造的
降级目标就会按需失败，而它被需要的那一刻，正是它唯一为之存在的那一刻；
`--fallback` 里打错一个字母，代价应该是一次启动报错，而不是宕机当中一
个死掉的会话。

它故意不是的三样东西：

- **不是负载均衡器。** 没有任何东西在分摊流量，顺序也永远不变。
- **不是熔断器。** 它永远不往回爬，因为"主供应商是不是又好了"这个问题，
  不花一次真调用去问就答不出来。降级是一次你会一直留着的降级——所以
  每一次切换都要发一个事件。会话被便宜的模型悄悄伺候了一个小时，就是
  这个设计为了简单而换来的那种失败；而它只有在看得见的时候才活得下来。
- **不是无共享。** 子 Agent 按指针共用这把梯子，因为"这个端点在拒绝
  调用"是关于端点本身的事实。发现这件事的子 Agent，不该还要回头去教
  它的父 Agent。

最后这一条是并发唯一露面的地方，而它产出了这个文件里唯一一行微妙的代
码：

```go
func (l *ladder) advance(from int) bool {
    if l.cur > from { return true } // 已经有兄弟把我们挪走了
    ...
}
```

对两个在同一级上失败的兄弟来说，`cur = from + 1` 本来就是幂等的：两边
写的是同一个值。真正需要这道保护的情形有三个参与者，而且它是一次
**回退**。A 在第 0 级失败，挪到 1。C 在 1 上失败，挪到 2。这时 B——手
里还捏着这一切发生之前读到的第 0 级——来要求降级，没有这道保护，它就
会写下 `cur = 1`，把下一个调用送给一个供应商——而那个供应商，两个兄弟
都已经放弃了。

## 一次真实运行：断掉的流要花多少钱

这次测量纠正了代码，而这次纠正比功能本身更有意思。

那个网关从来没对我们断过流，所以这个失败只能自己造。一个用完就扔的
反向代理——围着 `httputil.ReverseProxy` 写的 121 行，不属于任何一个
阶段，因为 `triage_test.go` 用 `httptest` 已经可复现地覆盖了同样那些
分支——把请求转发给上游，让模型正常生成，然后在 body 传到一半时把连接
切断（354 字节之后 `panic(http.ErrAbortHandler)`，而 `Content-Length`
承诺的还更多）。**供应商看到的是一次完成的生成，并且照此计费。客户端
看到的是一个断掉的流，永远收不到那个 usage 帧。**

```
  call failed (attempt 1, retry): the stream broke: unexpected EOF
  retrying in 313ms (attempt 2) — the stream broke: unexpected EOF

  ┌─ call 1 · tool_calls
  │ in 963    █░░░░░░░░░░░░░░░░░░░  full 3 · write 0 · read 960  100% cached
  ...
  ── session ──────────────────────
  cost: $0.000155
  1 retry
  retried attempts re-sent ≥963 prompt tokens (≥$0.000030)
```

最后那一行是别的 Agent 都不报的数字，而它也不可能来自 API：usage 在流
的*末尾*才到，而这个流没有末尾。所以它是在这个 prompt 唯一存在真实数字
的那一刻推出来的——最后终于成功的那次尝试——而且是当成一个界打印出来的，
带着 `≥`：冷调用第一次尝试付的是缓存**写**，重试付的是更便宜的**读**，
照抄成功那次尝试的拆分，就把第一次算少了。

那个面板里还有一点安慰值得注意：`full 3 · read 960 · 100% cached`。
**断掉的那次尝试并没有白费——它把缓存热起来了**，重试把它读了回来。
一个断掉的流第一次很贵，之后每一次都便宜。

### 这次运行在我自己的面板里找出的 bug

这一阶段第一次实跑用的是*另一种*故障：注入两个 503。面板说的是

```
  cost: $0.000276
  retried attempts re-sent ≥1926 prompt tokens (≥$0.000301)
```

这是胡说八道。重复计费的数字比整个会话都大，而它之所以更大，是因为它
是虚构的：**那些请求在生成之前就被拒了，供应商一分钱都没为它们计费。**
status 环节的 503 和一次被拒的连接都是免费的。只有开了又死掉的流，才真
的花过钱。

所以 `Phase` 才挂在事件上，而不是只待在 `CallError` 里面。`Status`
顶替不了它：一次连接失败和一次流断裂，带的状态都是 0。面板现在记两个
计数器——每一次等待，以及只有那些真的到过模型的尝试——同一个会话现在
报出来的是：

```
  cost: $0.000287
  2 retries
```

有重试，没有重复计费。`TestARefusedRequestIsNotReBilled` 存在，就是为
了让它一直这样。

更一般的教训，是阶段 04 和阶段 05 从不同方向落到的同一条：仪表报出一个
貌似合理的错数字，比什么都不报更糟，因为貌似合理的那个数字，正是人们会
拿去引用的那个。

## 一次降级要花多少钱

prompt 缓存是按供应商、按模型、按前缀分的，所以一次降级**在构造上**就
必然是冷的。同一个 963 token 的 prompt，一次是供应商第一次见到它，一次
是它已经热了：

| | full | 缓存读 | prompt 的成本 |
|---|---|---|---|
| 热的 | 3 | 960 | **$0.0000297** |
| 第一次见到这段前缀 | 963 | 0 | **$0.000289** |

（这两个数字来自两次不同的运行，不是同一个会话里相邻的两个回合。冷的
那个是上面那次降级之后的第一次调用；它冷是因为那个供应商还没见过这段
前缀——而这恰好就是每一次降级都会造出来的状态。）

**一样的字节，9.7 倍。** 挪到第 1 级，把供应商、模型、前缀一次性全丢
掉。你救回来的那个回合，代价是十个 prompt 的缓存折扣，而且会一直这么
付下去，直到新供应商的缓存热起来——在一个只剩几个回合的会话上，那可能
永远不会发生。

这不是反对降级的论证，这是支持那个事件的论证：成本基准在会话中途变了，
而面板是照 `KindProvider` 事件重新定价的，不是照启动时的配置。没有它，
第二个供应商的 token 会按第一个供应商的价钱计费——一份自信满满却算错了
的成本报告，比一份承认自己不知道的更糟。

还有个副作用值得要：trace 现在会记下**是哪个端点产出了它**，以及在什么
价钱下产出的。在这一阶段之前，你可以把一个存档会话的每个字节都读完，
还是重建不出它的成本。现在在一台没有 `providers.json` 的机器上跑
`--replay`，看到的是真钱。

## 压缩调用也是一次模型调用

```go
res, err := retryLoop(bus, 0, pol.forCompaction(), newLadder(rung{p: p}), ...)
```

只有一级的梯子，这是故意的：这个调用可以重试，但不可以降级。一次摘要
打嗝就把整个会话的供应商换掉，那不叫恢复，那叫惊吓——而且价钱会在用户
脚底下变掉，而他被告知的只是"正在压缩"。

牵绳也更短，不管会话的策略是什么：

```go
if p.attempts > 2 { p.attempts = 2 }
if p.budget > 5*time.Second { p.budget = 5 * time.Second }
```

压缩本来就有一种安全的失败方式——Agent 不压缩继续跑，并且把这件事说
出来——所以早点放弃代价很小，而死命重试代价极大：每一次尝试都按全价把
整份记录重发一遍，而且是在那个需要空间的回合还等着的时候干这件事。

## 三个事件，不是一个

```
call_error   什么坏了，以及我们对它做了什么决定
retry        我们正在等，等多久，以及那个数字是谁给的
provider     从这里往后由谁来服务调用，按什么价钱
```

和阶段 05 那套压缩三件套是同一个论证：它们回答的是不同的问题。
`call_error` 故意**不**叫 `error`。`error` 是终结性的——是会话在告诉人
它失败了。`call_error` 是一次带着决定的尝试失败，而它们后面大多跟着一次
成功。把它们当成 error 发出去，只会训练人忽略这个词，而真正的那一个就是
这么被漏掉的。

composer 把裁决直接显示在那一行上，因为在一份 trace 里你总是从一个症
状往回读，而问题从来不只是"什么坏了"——而是"它对此做了什么"：

```
   1    0.00s  provider         flaky (openai · mimo-v2.5) · session start
   4    0.31s  request          openai · 1 messages · 0 cache marks · 3.2kB
   5   37.15s  call_error       RETRY attempt 1 · the stream broke: unexpected EOF
   6   37.15s  retry            wait 313ms · attempt 2 · the stream broke: unexpected EOF
   7   37.46s  request          openai · 1 messages · 0 cache marks · 3.2kB
   8   43.88s  first_token      TTFT 6414ms
  20   44.26s  usage            prompt 963 (full 3 · write 0 · read 960) · out 41
```

两个 `request` 事件，一个 `usage`。这个不对称*就是*那笔重复计费，不用
算术就看得见。

## 诚实的限制

- **模型调用上没有截止时间。** `http.Client{Timeout: 10 * time.Minute}`
  是唯一的钟，而它盖住的是整个 body 的读取：一个慢但还活着的流，到第
  十分钟会死在生成中途，而且没有任何东西能取消一个正在飞的调用。
  `BuildRequest` 返回的是不带 context 的 `*http.Request`，所以拦路的是
  *接口*本身。这件事要到阶段 10 才变。
- **可重试的失败被假定是幂等的。** 它确实是，理由是失败的模型调用没跑
  过任何工具——但这条理由是这个 Agent 的形状带来的性质，不是重试本身的
  性质，等哪天工具调用在流完成之前就被派发出去，它就不再成立了。
- **重复计费那个数字是估算**，它出现的每一处都标着 `≥`，而它永远只能
  是一个界，因为没法去问 API。
- **没有任何东西把部分结果喂回给模型。** 它做到一半的那个计划没了，而
  半个工具调用比没有更糟。留下部分结果是为了记账，不是为了对话。
- **梯子永远不往回爬**，一个长会话可以就在第 2 级上收尾，除了那个事
  件，没人会注意到。
- **`!= http.StatusOK`，不是 2xx 区间。** 202 会被分类成失败。这个仓库
  的证据里没有哪个端点返回过它；它仍然是表里潜伏着的一行。

测试：49 个变异体打在 `triage.go`、`render.go`、`events.go` 和
`replay.go` 上——每个分类器分支、每道保护、每个 json tag——49 个全部被
抓住。有一个变异体在运行器里被记成*等价*，而不是拿去测试
（`cur = from + 1` 对 `cur = l.cur + 1`，在它们上面那道保护之下可证明
相等），这才是收尾一份变异报告的诚实做法。

## 练习

1. **把牵绳弄断，看它让你付多少钱。** 把 `--provider` 指到一个永远返回
   500 的 URL，加上 `--retry 8 --retry-budget 2m`，然后把 `leash()` 那
   个子句删掉再跑一遍。两次都计时。第二次就是"5xx 是瞬态的"这句话买来
   的东西。

2. **加一个 402。** `insufficient_quota` 是每个业余项目最先撞上的那个
   失败。它该判哪个裁决，为什么和 401 不一样？先写出那一行，再写出那
   个变异体，证明这一行是承重墙。

3. **让降级能爬回去。** 加一个半开探测：在第 1 级上成功了 N 次调用之
   后，往第 0 级发一个调用，能通就把它提回来。然后测一下这个探测在缓
   存未命中上花掉多少，再决定你还要不要它。（这就是熔断器，而这就是
   熔断器的账单。）

4. **把部分结果喂回去。** 流断掉的时候，部分结果里有时含有*完整*的工
   具调用——§A3c 记录过一个完整的 `tool_use` 旁边跟着一个被截断的。别
   丢，照发出去，然后找一个这么做是错的场景。不难找，而这就是默认丢掉
   的原因。

5. **让 `Retry-After` 从"照规范写的"变成"观察到的"。** 找到任何一个真
   会发它的端点，把字节抓下来，把那一节加进 `wire-notes.md`。这是这里
   唯一一个练习，改进的是仓库的证据，不是它的代码。
