# 阶段 05：长生

Agent 的记忆有三层视野，三层都得有：

```
单次请求内   messages 数组               阶段 00–04
单个会话内   上下文压缩，数组长过窗口时
跨会话       一份文件
```

第三层一段话讲完。第二层占掉本章剩下的全部，而它停下来的地方，你多半
没料到：**上下文压缩没省钱。**同样的工作，在一次对照实验里，它多花了
25%。这不是实现里的 bug，它改变的是上下文压缩这件事的用途。

---

## 长期记忆就是一份文件

工作目录下的 `AGENTS.md` 和 `MEMORY.md`，启动时读进来，接到系统提示词
后面。后面那份由 Agent 自己写，用的是它手里早就有的工具：

```sh
printf '\n- the test suite needs CGO_ENABLED=1 or three packages fail to link\n' >> MEMORY.md
```

整个特性就这些。没有存储层，没有 embedding，没有检索步骤，也没有拿
相似度搜索去搜一堆 `grep` 本来就能搞定的语料。

分界线是**作者**，不是内容。`AGENTS.md` 是人写给 Agent 的——约定、构建
命令、哪些地方别碰。`MEMORY.md` 是 Agent 写给未来的自己的。分开放的
好处是：人可以只看 Agent 决定记住了什么，不必在自己写的指令里翻来翻去；
发现记错了一条，拿编辑器删掉就行。会往人类那份文件里写字的 Agent，
迟早要跟它吵起来。

选文件而不选别的，带出三件事，最后一件才是有意思的那件。

**文件可以 grep、可以 diff、可以审、可以进版本库、可以手改。**这五个
性质向量索引都没有，换掉的是你本来不需要的那次相似度搜索。

**机制简单，不等于策略问题跟着消失。**完全交给模型自己拿主意，记忆
基本不会被写下来——当前这个回合里没有任何东西为此给它奖励。凡是真能
攒出有用记忆的 Agent，都有显式的触发点。这里的触发点是 `/remember`，
而系统提示词里还压着一条规则，它决定这份文件半年以后还值不值得读：

> 记录你学到了什么，不要记录你做了什么。

知识库和日记，差别就在这一句。

**记忆是上下文注入，而注入进去的上下文会被当真。**看看第一次真跑起来
是什么样。Agent 在 `sandbox/s05` 里启动，手上是仓库那份 `AGENTS.md` 的
副本——那份文件描述的是**仓库**，里面提到 `docs/wire-notes.md` 这种路径。
接着让它数 `wire-notes.md` 有多少行，而那个文件就躺在工作目录里，它跑
的是：

```
  $ wc -l docs/wire-notes.md
  │ wc: docs/wire-notes.md: No such file or directory
```

没有任何东西出故障。记忆文件里写着 `docs/`，模型宁可信系统提示词里的
一句话，也不信自己脚下站着的目录。这是正确行为，同时也就是风险：
**记忆文件不是笔记，它是模型还没去看就会照着做的断言。**所以那几个
便宜的缓解手段值得做——每行都标日期，过时的那行才认得出来、删得掉；
记忆只写在它成立的范围里；文件短到人真的会去读。

**这个会话写下的记忆，要到下一个会话才看得见**——这是缓存上的决定，
不是漏掉了。记忆住在系统提示词里，会话中途重读文件就等于重写前缀，
阶段 04 挣到的东西全部作废。拿一个回合的延迟换一整个会话的缓存命中，
这笔账划得来。值得知道的是：这是你自己做的取舍。

## 上下文可以放在哪儿

本章有一半跟上下文压缩无关——就是眼下这一半，也是你每天都会用到的那一半。

每一块注入的上下文都只有两种，区别不在它装了什么，而在**它的值多久变
一次**：

| | 去哪儿 | 代价 |
|---|---|---|
| **整个会话都稳定**——记忆文件、cwd、操作系统、shell | 系统提示词，缓存断点之前 | 它那些 token，只付一次，会话跑多久都一样 |
| **易变**——时钟、git HEAD、工作树脏不脏 | 消息创建的那一刻冻结进这条消息 | 它那些 token，每回合付一次，永久 |

第二行是大家会搞错的地方，而且错的方向恰好是烧钱那个方向。直觉会让人
想让易变上下文保持**新鲜**——每个请求都重算一次时间戳，好让模型永远知道
现在几点。那正是阶段 04 的 `--break-cache` 实验，量出来 3.4 倍。

解法是承认"新鲜"和"在前缀里"这两件事没法同时要——而新鲜是那个几乎可以
白送掉的：

> **注入一次就冻住。已经在前缀里的东西，永远不要重算。**

用户按下 Enter 那一刻取的快照，对它所属的那个回合是准的，之后就原样
留在历史里不动——字节稳定的前缀说的正是这件事。模型每回合都拿到新信息，
**同时**缓存还活着，因为每个回合的快照是各自一行、各自永久，而不是同
一行反复改值。下面是真实对话中间的一份快照，取到它之后又过了三个回合：

```
  [3] user
  │ <now>2026-08-27 04:38:53 +0800</now>
  │ <git branch="main" dirty="3">Stage 04: the cache</git>
  │
  │ 2. sed -n '91,180p' wire-notes.md
```

另外看一眼 `cwd` 落在哪一边。它是稳定的——因为 shell 不持久，命令里的
`cd` 动不了它（阶段 00）。给 Agent 一个持久 shell，cwd 立刻变成易变的，
得挪到另一行去。执行模型一改，直接传导到缓存布局。

## 不带分词器数 token

上下文压缩得在**发出去之前**知道 prompt 有多大。常见建议是自带分词器。
对这件事那是错的工具：它是个按模型分版本的大依赖，在工具 schema 和消息
外壳的框架开销上跟服务端算不到一块去，而且它告诉你的东西没有一样是你
拿不到的——因为**每个响应里都已经带着你刚发出去那个 prompt 的精确
token 数。**

所以改成量。记下你发了多少字符，记下服务端说那是多少 token，把比值
留着，每次调用都更新一遍。

```go
func (a *agent) runTurn(msgs []Msg) []Msg {
    sentChars := convChars(msgs) + base
    res, err := a.call(turn, msgs)
    ...
    a.comp.est.observe(sentChars, res.Usage.Prompt())
}
```

微妙的地方，也是它之所以成立的地方：**这个估算不需要准，它需要一致。**
它被问到的问题永远只有一个——"是不是快撞墙了"；而它拿来校准的，正是
后面要它换算的那同一个字符数。系统性偏差——JSON 外壳、工具 schema、
系统提示词——被吸进比值里，而不是攒成误差。真会把它搞坏的做法是：量
一样东西，估另一样。

仪表盘把实时比值打在上下文水位线旁边，你可以看着它稳下来：

```
  └ context 5893 / 12000 (49.1%) · ≈3.7 B/tok
```

那个会话开头是 3.3，随着对话从系统提示词转向 Markdown 爬到了 3.7——同
一个会话内漂了 11%，而且只往一个方向漂。任何固定除数都会在某一头出错；
量出来的那个，两头都不错。

### 它真的管用吗？

一次真实运行里的三次上下文压缩。每一次都对自己刚产出的那段对话预测它
有多大；紧接着的下一个调用，报回它实际计了多少：

```
  predicted ~3556   billed 2842   +25.1%
  predicted ~3823   billed 3624    +5.5%
  predicted ~3332   billed 3256    +2.3%
```

第一个很难看，但理由比数字值钱：那时估算器手上只有七个样本，全是在
prompt 大部分还是系统提示词的时候采的，而现在问它的是一段已经基本变成
Markdown 的对话。再过两次上下文压缩它就收敛了，之后一直待在 6% 以内。

合成测试把它钉得更死。对手是个假供应商，按 `chars/2.9` 计费，另外还
加一份 700 token 的外壳开销，而这份开销估算器从来直接看不到。十轮校准
之后，它预测 **21,708 个 token，实际计费 21,389——差 1.5%**，而除数和
开销这两样，从来没人告诉过它。

对阈值判断来说，6% 属于免费精度。把阈值定在 70% 而不是 78%，你就用一
份本来也想留的余量，把这点误差的账付了。

## 哪些地方允许切

这一节会在真实 Agent 里长出真实的 bug，而这个 bug 的形状，正是它难找
的原因。

上下文压缩把 `msgs[:cut]` 换成一份摘要。不是每个 `cut` 都合法：

**1. `msgs[cut]` 里不能有工具结果。**跟它配对的那个工具调用在
`msgs[cut-1]`，而这条正要被删掉。调用没了的工具结果就是孤立工具结果，
两边协议都不收——OpenAI 回 *"messages with role 'tool' must be a
response to a preceding message with tool_calls"*，Anthropic 报的是
没料到的 `tool_use_id`。

**2. `msgs[cut]` 必须是 assistant 消息。**摘要是以用户消息的身份注进去
的，所以在另一条用户消息前面切，就会切出连着的两条用户消息。有的端点
把它们合并，有的直接拒，而会合并的那些，合并方式彼此还不一样。

两条并成一条，能装进脑子：

> **对话只能切在 assistant 回合的正前面。**

现在说它为什么难找。上下文压缩发生在回合 14。畸形请求在回合 15 才发出
去。报错指名的是请求构建那一段。栈里没有一处提到压缩器，而能重现它的
那段对话已经不存在了——因为它被压缩掉了。**bug 离它的症状一百行远，还
晚一个回合。**

所以守住它的是不变式，不是测试用例。`validConversation` 是照协议的
规则写的，特意**不**照切割逻辑写；属性测试断言两者在每个下标上都一致：

```go
for i := range msgs {
    if canCutBefore(msgs, i) {
        got := validConversation(append([]Msg{summaryMsg("s")}, msgs[i:]...))
        // 必须是 ""
    }
}
```

检查要是跟代码出自同一套假设，那它永远会同意代码。从另一头写起的那个
不会，而这就是它全部的价值。对这一对做变异测试，四种破坏它的手法全被
抓住了，包括最要命的那一种——把工具结果那道检查删掉，只要切点碰巧落在
安全的位置，整套测试照样全绿。

### 下限

上下文压缩有个下限，掉到下限以下，你面对的就是另一个问题了：

```
cannot compact: the newest message alone is ~11400 tokens against a keep budget
of 3000 — lower --max-output or use a command that filters
```

一条消息本身就比整个保留预算还大，压缩绕不过它。那是输出大小的问题
——阶段 01 的截断上限，或者换条命令：要它过滤，别把结果整个倒出来。

那段代码的第一版，对第二种完全不同的情况打的是同一句话：预算刚好只
装得下一条消息——这时该改的是 `--keep`，不是 `--max-output`。**错误信息
是一句关于因果的断言。**这一点搞错，你不只是没帮上忙，你是在误导：
读者去改你点名的那个设置，改了没用，于是他断定诊断是对的、局面没救了。
现在它把这两种情况分开了。

## 摘要

摘要器有自己的系统提示词，一个工具都不给，拿到的是**摊平**的记录，不
是消息数组。

摊平是不显然的那个选择。把真数组递进去看着更忠实，实际表现更差：给
模型一段对话，它就会去**接着说**——把最后那个问题再答一遍，或者发出
下一个工具调用。摊平把任务从"对话"改成了"读这份文档"。它顺带还让长
工具输出能在计费之前先被截掉，也让这次调用完全不带工具定义——于是工具
调用不只是不被鼓励，而是根本不可能。

挑选标准是值得抄走的那部分：

> **留下那些重新发现要花掉工具调用的东西。**

这是经济判断，不是语义判断，而且模型执行它比执行"留下重要的东西"容易
太多。一条 grep 了三次才找到的文件路径，值一行。Agent 自己的一段叙述
一文不值，因为重新生成它不花钱。

长工具输出是从**中间**剪的，不是从头剪。构建日志把错误放在末尾，栈
踪迹把原因放在末尾。两头都留住，就留住了命令开口说的和它最后得出的；
丢掉的是重复的中段——而长就长在那儿。

### 读一份真实摘要读出来的 bug

第一版逐字产出了这个：

```
4. STATE
- Not done: Chunks 2–8 were never run.
```

它是假的，而且假在只有上线才会露出来的那个点上。写下这份摘要的那一刻，
块 2 **是**跑过的——它的调用和输出就在那四条被**保留**下来的消息里，而
摘要器根本没看到它们。于是模型收到的是一段断言某件事从没发生过的文字，
正下方紧挨着的就是它发生过的证据。

摘要器拿到的是一段前缀，任务是写摘要，而它答起来的口气像是看过了整个
会话。提示词里没有一句话告诉它不是这样。一句话就修好了：

> 你读到的只是这个会话**较早**的那一部分。更近的消息会被原样保留，紧
> 接在你的摘要后面出现，而你看不到它们。所以，永远不要用
> "never done" 或 "not started" 去陈述整个会话——要说
> "as of the end of this transcript"。

同样的任务，同样的模型，下一次运行：

```
4. STATE — Chunk 1 has been read (twice). Chunks 2–8 remain outstanding
           as of the end of this transcript.
```

这里的普遍教训跟摘要没关系。**只看到系统一部分的组件，会去描述整个
系统，除非你告诉它它正在看的是什么**——而且两种情况下它听起来一样自信。

## 来自一次真实运行

一个任务，三种策略，三条臂的输入是字节相同的：十条用户消息，从 trace
上核对过。

```sh
agent --yolo --window 12000 --compact-at 0.5  --keep 0.25   # tight
agent --yolo --window 12000 --compact-at 0.85 --keep 0.35   # roomy
agent --yolo --window 12000 --no-compact                    # none
```

| 臂 | 压缩次数 | 发出的 prompt | 全价 | 缓存读 | 输出 | 缓存读按 0.1 折算 | 墙上时钟 |
|---|---:|---:|---:|---:|---:|---:|---:|
| tight | 3 | 92,553 | 30,601 | 61,952 | 3,673 | **36,796** | 105s |
| roomy | 1 | 102,315 | 21,739 | 80,576 | 2,004 | **29,797** | 69s |
| none | 0 | 121,850 | 12,858 | 108,992 | 865 | **23,757** | 58s |

把第三列和第四列对着看。**发出 token 最多的那条臂，付钱最少**，因为它
从来没破自己的缓存：`none` 整段 prompt 花费里有 89% 是十分之一价格的
缓存读。

`roomy` 和 `none` 跑的是**同样的八条命令**——一点混杂都没有——而上下文
压缩的代价是：

- **全价等价 token 多 25%**
- **输出 token 多 132%**（摘要是输出，而输出是贵的那一侧）
- **墙上时钟多 19%**

`tight` 更糟，还有一条附注必须跟着它：它多跑了三条命令（`ls -la`、
`cat task.txt`，还有一个重复的块）。这三条全都发生**在它第一次上下文
压缩之前**，所以不是压缩造成的——那是普通的模型方差——不过它们确实把
这一行往上抬了几个百分点。干净的对比是 `roomy`/`none` 这一对。

### 缓存悬崖

在 tight 这条臂里面，逐个调用看：

```
  #   kind     prompt   full   read  cached%
  6              5174   1654   3520     68%
  7              5258    138   5120     97%
  8 COMPACT      3310   3310      0      0%      ← 做摘要的那次调用
  9              2842   2330    512     18%      ← 压缩之后的第一次调用
 10              2927    111   2816     96%
 ...
 14              5701    133   5568     98%
 15 COMPACT      3383   3383      0      0%
 16              3624   3112    512     14%
 17              3709    125   3584     97%
```

**上下文压缩是一次跨两个调用的缓存断电**，在那张表里它发生了三次。
摘要调用天生就是冷 prompt——系统提示词不一样，用户消息是一次性的，没
什么可匹配。它后面那个调用之所以冷，是因为前缀刚被重写过。第三个调用
就回到 95% 以上了。

所以 Agent 选在**引发**它的那一刻打这条警告，而不是等它显形的时候：

```
  ≡ compacted: 15 → 5 messages · ~7714 → ~3556 tokens (-54%) · 6976ms
  ! the prompt prefix was rewritten — every cache entry from before this point
    is now unreachable, and the next call is a full-price miss
```

没有那一行，下一个调用上的红条看着像退步，而不是像后果。

### 抖动

`tight` 压了三次，`roomy` 只压了一次。算一下：

```
headroom = (threshold − keepRatio) × window
tight:  (0.50 − 0.25) × 12,000 = 3,000 tokens
roomy:  (0.85 − 0.35) × 12,000 = 6,000 tokens
```

在 `--max-output 8000` 下，一条工具结果大约 2,200 token。所以 `tight`
在两次压缩之间只剩**一个回合**的余地，而每次压缩都要付：整段历史的一
次全价读，加一次跨两个调用的缓存断电，再加大约七秒。

> 决定你多久压一次的不是阈值，是**阈值和保留比率之间的那段距离**——用
> 你自己实际的工具输出，按回合数来量。

## 那么上下文压缩到底*为了*什么？

不是为了省钱。这一点是量出来的，不是猜的：每一条轴都变差了——全价
token 更多，输出 token 多得多，墙上时钟更长，还外加一份天生有损的摘要。

> **上下文压缩是保命机制，不是优化手段。**你之所以压缩，是因为另一条
> 路是 400 加会话直接死掉，不是因为它更便宜。

这就把通常的设计建议反过来了。如果上下文压缩只会让你多付钱，那目标
就是**越晚压、越少压越好**——不是停在舒服的 70%，而是压在还负得起责任
的最后一刻，压完之后能留多少余量就留多少。而最便宜的压缩是那次从来
没跑的压缩——这一下就把阶段 01 的输出上限、还有"能 `grep` 就别
`cat`"的习惯，从礼貌变成了上下文窗口的功能。

反方意见，公平地说出来：这些会话一个都没接近真实的 131k 窗口。在真
**会**撞墙的那种会话上，上下文压缩的成本是拿去跟无穷大比的，那它按
定义就赢。这里的数字并没有说压缩不好。它们说的是：**它不免费，它不是
一种节省，而大多数教程里的默认阈值，是照着错的目标定的。**

## 练习

1. **把三条臂重现一遍。**绝对数字会不一样；"缓存读按 0.1 折算"这一列
   的排序才是结论。
2. **找出你自己的余量。**同一个任务在好几组 `(threshold, keep)` 下各
   跑一次，把压缩次数对总成本画出来。拐点就是你的工具输出大小。
3. **故意破掉切点的不变式。**删掉 `canCutBefore` 里的工具结果检查，跑
   一个带并行工具调用的会话，看 API 拒掉一个请求——而压缩器在栈里离它
   八丈远。
4. **让估算器说谎。**拿 `convChars` 校准，却拿 `len(requestBody)` 去
   估，看比值怎么变成一句废话——这就是"要一致，不要准"的证据。
5. **删掉那句限定范围的话**——就在 `summarySystem` 里——然后读三份摘要。
   数一数有几份对着自己看不见的东西下了断言。
6. **把易变那一块搬进系统提示词**，再比一比缓存读那一列。你已经从另
   一个方向重新推出了阶段 04 的臂 C。
7. **给 Agent 一个真实任务，做两遍，分在两个会话里**，中间夹一次
   `/remember`。然后读 `MEMORY.md`，问一句：有哪一行本来能省下一次
   工具调用？这个问题就是记忆系统的全部设计要求。
