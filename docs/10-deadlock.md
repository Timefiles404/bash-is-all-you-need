# 阶段 10：死锁

阶段 09 结尾把自己的一条限制写了下来，并且点名这一阶段来修它：

> **模型调用上没有期限。** `http.Client{Timeout: 10 * time.Minute}` 是
> 唯一的钟，而它盖住的是整个 body 的读取：一个慢但还活着的流，到第十
> 分钟会死在生成中途，而且没有任何东西能取消一个正在飞的调用。
> `BuildRequest` 返回的是不带 context 的 `*http.Request`，所以拦路的是
> *接口*本身。阶段 10 就是它改掉的地方。

这里面有一半是机械劳动。Go 里取消正在进行的工作有个约定：把
`context.Context` 一路传进每一个会阻塞的函数——这个值身上只带一件东西，
"现在停"的信号。把它穿过这个 Agent，要动很多文件，动完之后你不需要再想
它。

另一半才是这一章的题目：**一个超时对流式响应来说，形状就是错的。**这个
数不管定成多少都不对，而看清这一点要花掉前两节。再往后讲的是拿什么来替
它——那几个数从哪儿来，怎么量一个数才不至于骗到自己，以及其中某一个响了
之后必须发生什么。

**动手之前**：你需要阶段 07 的子 Agent，因为这一阶段名字里那个等待，正
是父 Agent 等子 Agent 的那个；需要阶段 09 的分诊，因为这里会来三种新的
失败模式，得交给那一阶段搭好的机器去分类；还需要阶段 01 的进程组，因为
取消一条命令和杀掉一个进程不是一回事。

**你会做出什么**：一次模型调用上三个各自独立的钟；一条能把慢的流和死的
流分开的看门狗；一套让每个钟自报家门、说清是谁响了的办法；还有一个仪
表，把看门狗真正拿来比的那个量打印出来。新增一个文件，三百行上下，外加
给程序里每一处会阻塞的地方补上 context 参数。

## 出发点

阶段 09 里的整套时间策略，就是这一行：

```go
httpc: &http.Client{Timeout: 10 * time.Minute}
```

`http.Client.Timeout` 管的是整个请求：DNS 查询、TCP 连接、TLS 握手、把
请求发出去、收到响应头，以及把响应 body 读到底。问题出在最后一项。在流
式端点上，body 不是先到齐再结束的——它一帧一帧地来，模型生成多久它就来
多久，读取要等到模型不说话了才结束。

所以流式调用上的 client 超时根本不是超时。它是给模型能说多久设的上限。

程序的其余部分也是同一副样子，理由也一样：里面没有任何东西能被叫停。阶
段 09 那两个会阻塞的函数签名都不收 context——

```go
BuildRequest(system string, msgs []Msg, tools []Tool, maxTokens int) (*http.Request, []byte, error)
func runBash(shell, command string, timeout time.Duration) execResult
```

——所以正在飞的请求取消不了，正在跑的命令也取消不了；而两次重试之间的退
避是 `time.Sleep`，那更是打断不了。想让一次等待提前结束，这个 Agent 只
有一条路：把进程杀掉。

## 为什么一个数怎么定都不对

先把管线放一边，只看那个数。一个超时盖在流式调用上，等于同时被问了两个
毫不相干的问题：

```
一次健康的生成能花多久？      分钟级，而且原则上没有
                              上界——答得长本身不是
                              故障

一条**死**连接能装活多久？    毫秒级；根本没有任何
                              理由去等
```

定成十分钟，一条在第三秒无声死掉的流，就把这个回合扣押了剩下的
597 秒——先是空白的终端，然后报错。

定成十秒，每一个长答案都会被从句子中间掐断。这比听起来严重，因为掐断之
前生成的那些 token 是真的生成过了：供应商服务了这次请求，也会照单开票。
阶段 09 在会话面板上加的那行重复计费，就是为了给这个错误标出价钱。

中间的任何一个数也都不对，因为这两个问题没有共同的答案。它们需要各自的
钟。

## 三个钟

```
  dial ── TLS ── 响应头 ───┬── 字节 ── 字节 ─────── 字节 ── [DONE]
                           │        ↑           ↑
  ├──── connect ───────────┤        └── 间隔 ───┘
  │                        │
  └──────────────── total ─┴─────────────────────────────────────┘
```

| 钟 | flag | 管什么 |
|---|---|---|
| connect | `--connect-timeout 30s` | 响应头必须在这之内到。这时候什么都还没生成，所以这是唯一一种重试免费的失败。 |
| idle | `--stall-timeout 45s` | 管的是**字节之间的间隔**，不是总时长。它是唯一能把慢的流和死的流分开的钟。 |
| total | `--call-timeout 15m` | 整个调用的兜底。它不是策略——它防的是某个供应商每过一个空闲窗口就挤出一个字节，永远不停。 |

三个钟都可以设成零，设成零就是把那个钟关掉。零是真的设定，不是占位：产
出 `docs/wire-notes.md` 的那些线上探针，跑的时候三个钟全是关的——被半路
掐断的探针，什么都证明不了。

connect 这个钟是 `http.Transport.ResponseHeaderTimeout`：它到响应头就
停，不碰 body。而 client 自己的 `Timeout` 现在是**零**——这一阶段存在的
理由就是把它改成零：

```go
httpc := &http.Client{
    Transport: &http.Transport{
        Proxy:                 http.ProxyFromEnvironment,
        ResponseHeaderTimeout: dl.connect,
    },
}
```

有一个测试，唯一的职责就是把这个字段摁在零上。因为将来某次看起来很合理
的改动，只要往那儿填回一个值，就等于一声不响地把"模型能说多久"的上限又
装了回去。

total 这个钟是套在单次尝试外面的 `context.WithTimeoutCause`。十五分钟早
就超出任何人的耐心了，所以它不是在规定用户该等多久。它在那儿，是因为供
应商要是每隔四十秒吐一个字节、永远不停，idle 那个钟根本碰不到。

中间那个钟是承重墙，也是这件事之所以难的全部理由。**一条活着的流和一个
挂死的 socket，从外面看一模一样。**两边都没有字节在到。把它们分开的只有
一件事：其中一条将来还会再吐出一个字节。而关于这一点，你能拿到的证据永
远只有一样——它已经静了多久。空闲超时是在赌：静到这个长度就等于死了。下
一节整节都在找这个长度：长到让这个赌注变得安全。

## 空闲窗口该定多少，怎么测出来

阶段 09 已经确认过：关于超时，这个仓库没有任何记录下来的证据。拿
`429|Retry-After|timeout|502|503|504|408` 去搜 `wire-notes.md` 全部 731
行，只搜到一处，而那一处是线上记录自己给的建议，不是抓下来的字节。所以
空闲窗口这个数，得先量出来，才站得住脚。

量它有三种办法。其中两种便宜、看着没毛病，给出的答案是错的。三种都值得
走一遍，因为前两种为什么会错，比第三种量出来的那个数更有用。

### 方法一：在 trace 里量事件之间的间隔

手上有阶段 02 那个 trace 文件的人，都会先想到这个，而且理由很正当：
trace 里每个事件都带时间戳；trace 存在的意义，本来就是让关于一次会话的
问题事后能回答，不用重新跑一遍；而相邻两个流式事件之间的间隔，看起来正
好就是看门狗盯着的那个量。一行新代码都不用写。

拿三个真实会话量了一遍，它报出来的最大间隔到了 **9099 ms** 和
**11067 ms**。

这两个数都是编出来的，而且在你相信它们之前，有办法看出来。那几个会话里
有一个，本来就是带着 `--stall-timeout 5s` 跑的，而且跑完了，干干净净。
一道五秒的闸从头到尾没响过，测量却说这里静了九秒——它和一次真跑对不上。
测量和运行打架的时候，真发生过的是那次运行。

毛病在过滤器上。写这段分析，就得列出哪些事件种类算"流还活着"，而凭记忆
列出来的清单一定会漏。这一份列了 `text_delta` 和 `usage`，漏掉了
`reasoning_delta` 和 `tool_args_delta`——而这两种事件在那个会话里分别有
**223** 个和 **310** 个。那段"九秒的静默"，从头到尾都在流一个 thinking
块。

这类失败值得起个名字，因为它会反复出现：**建立在流的过滤视图上的测量，
会把过滤器漏掉的东西一起继承下来，而漏掉的东西不会在结果里留下窟窿。**
少了一种事件，数据不会缺失，只会变成更长的一段间隔——而更长的间隔读起来
像是个发现。修法是把种类清单从 `events.go` 里抄出来，别再凭脑子列。这条
修法直接把你带到第二种办法。

### 方法二：从到首 token 的耗时倒推

这次事件种类是从源文件里抄的——11 次调用，993 个间隔：

| | p50 | p90 | p99 | max |
|---|---:|---:|---:|---:|
| 流帧之间的间隔 | 30 ms | 62 ms | 294 ms | **804 ms** |
| 到首 token 的耗时 | 2159 ms | 3309 ms | — | **16448 ms** |

上面那行让人放心：整个样本里，流一旦开始就没有一次静过整整一秒——照这一
行看，空闲窗口定得很小也安全。

下面那行不让人放心。"到首 token 的耗时"常写成 TTFT，指的是请求发出去之
后，等第一段生成出来的文字回来所花的时间。这里它最长到了 16.4 秒，是流
中间最宽间隔的二十倍。

跟着往下的结论看起来无可辩驳：看门狗是从 body 被打开那一刻起表的，所以
它的第一个窗口必须盖住模型全部的思考时间，那时候一点内容都还没有。于是
空闲窗口的尺寸根本不是由流中间那些间隔定的，是由 TTFT 定的，而且至少得
是 16.4 秒再加一点余量。

推理没问题，前提是错的。**TTFT 量的是内容什么时候出现。而看门狗盯的不是
内容，是 socket 上的读。**这是两个不同的量，在 trace 上怎么算也算不出彼
此，因为 trace 里只有适配器选择变成事件的那些帧。

所以方法二栽在和方法一同一个地方，只是衣服穿得体面些。两种办法量的都是
trace 看得见的东西，而期限拿去比的，是 trace 看不见的东西。

### 方法三：到它发生的地方去量

那个真正的量只存在于一个地方：读 socket 的那段代码。所以阶段 10 就在那
儿量它。

`stallReader` 包住响应 body。每一次读出了字节，就把当前时间盖到 guard
上；guard 一路维护这些时间戳之间间隔的最大值：

```go
func (s *stallReader) Read(p []byte) (int, error) {
    n, err := s.rc.Read(p)
    if n > 0 && s.guard.mark(s.now()) && s.bus != nil {
        s.bus.Emit(Event{Kind: KindIdleMax, Turn: s.turn,
            Millis: s.guard.idleMax().Milliseconds()})
    }
    return n, err
}
```

那个条件里有两处是刻意的。判断用的是 `n > 0`，不是 `err == nil`，因为一
次读允许同时返回数据和 `io.EOF`，而这样的读和别的读一样是活着的证明。还
有，每刷新一次最大值就发一个事件出去，而不是等到最后一并报告——因为卡住
的流根本走不到最后。你最想看到那个间隔的调用，恰恰是活不到报告的那一次。

这个数最后落在每次调用的面板上，紧挨着 TTFT：

```
  ┌─ call 1 · tool_calls
  │ in 1743   ████████████████████  full 1743 · write 0 · read 0
  │ out 38     TTFT 4156ms · total 5830ms · 22.7 tok/s · idle max 1119ms
```

`idle max 1119ms`——而这次调用的 TTFT 是 4156 ms。模型在想的时候，socket
并**不**安静：字节一直在到，比第一个 token 早得多。方法二的结论，被打印
出这个数的第一次调用当场推翻。

14 次调用的分布：

| | 最小 | 中位 | 最大 |
|---|---:|---:|---:|
| 每次调用里最宽的字节级静默 | 72 ms | 252 ms | **5001 ms** |

45 秒这个默认值，相对这里观测到过的最宽静默留了 **9 倍余量**。

同一组样本也直接了结了 TTFT 那个理论。这 14 次调用里，TTFT 最高只到
4157 ms，而字节级最宽的静默是 5001 ms。socket 在*流中间*静得比第一个
token 之前更久。这两个量不只是不同——它们的大小关系，也不是 trace 让人以
为的那样。

把第三种办法和前两种分开的那条规则，短到可以带走：**去量期限真正拿来比
的那个量，别量一个和它相关的量。**要是没有任何东西记录那个量，那么造一
台仪表就是这份活本身——而且不是可选项，因为那两种便宜办法并没有安安静静
地失败。它们给出的是自信的数字，而且错得方向相反。

### 那五秒的静默大概是什么

产出 5001 ms 这个数的那次调用值得细读，因为两台仪表对它的说法差了将近四
倍：

```
idle max     650 ms      ← 运行中的最大值，字节级
idle max    5000 ms
idle max    5001 ms
事件间隔   18509 ms      ← 内容帧，同一次调用的同一段
```

内容流上一段 18.5 秒的静默，被几段几乎正好五秒的字节级间隔切开。模型在
思考的时候，那个 socket 上大约每五秒就有东西到，而不管那是什么，它不产
生任何事件。

最自然的解读是 keep-alive：服务器发过来的一个字节，或者一行空行，除了不
让这条连接看起来像死了以外没有别的用处。真是这样的话，空闲这个钟量的根
本不是"模型停止生成了"，而是"供应商不再发 keep-alive 了"——那么五秒以上
的任何值都安全，余量大得离谱；五秒以下的任何值，会把每一次停下来思考的
调用都杀掉。

**这个仓库不下这个结论，因为那些字节没有进入证据。**两次 `curl` 探针追
过它们——一次的 prompt 要求模型长时间安静地想，一次带上工具定义和一条难
到需要斟酌的命令——两次都一路不停地流：152 行和 1134 行，超过一秒的间隔
**零**个，注释行**零**行。Server-sent events——也就是 SSE，两套协议都在
用的那种流式格式——允许出现以 `:` 开头的行，这种行不带任何数据，存在的唯
一目的就是填满静默。keep-alive 长什么样，这是最显而易见的候选，而两次探
针一行都没抓到。

所以：效果被仪表记下来了，原因哪儿都没记。在它被记下来之前，五秒这个节
奏是推断。阶段 09 处理 `Retry-After` 的位置和这里一模一样——而能分清哪些
断言是这一类、哪些背后有抓下来的字节撑着，比其中任何一个具体的数都值
钱。

## 检测卡住，又不输掉竞态

实现空闲超时最显而易见的写法，是拿一个 `time.Timer`，每次读都 reset 一
下。它也是错的，而且错在最难查、因此最贵的那个方向上。

`Reset` 和它想拦住的那次触发之间有竞态。定时器到点了，运行时已经把它的
函数排进队列，而那个本该拦住它的 `Reset` 晚了一微秒才落地。字节明明到
了，这次调用却被判成卡住。

这个竞态的窗口极小，而这正是它坏的地方。每次调用都触发的 bug，第一次跑
就会被抓到。很少触发、只在压力下、只在繁忙的流上、只在生产环境里触发的
bug，看起来就像供应商在抽风——然后你会花掉一个下午去读人家的状态页。

拿时间戳去比就不可能输掉这个竞态，因为 reader 是在 watcher 读它*之前*写
下时间的：已经到了的字节，下一次检查一定看得见。

```go
case now, ok := <-tick:
    if !ok {
        return
    }
    if now.Sub(time.Unix(0, g.last.Load())) >= idle {
        cancel(errStalled)
        return
    }
```

这笔交易的代价是发现得晚：watcher 只在 ticker 响的时候才看一眼。tick 特
意取窗口的四分之一，这就把"晚"卡住了上限——卡住会在 `idle` 和
`idle × 1.25` 之间被发现，而且**永远不会早于 `idle`**。

晚是安全的方向，早不是。响晚了，代价是在一次本来就已经死掉的调用上多花
了不到一个窗口；响早了，杀掉的是一次活着的调用，产生的失败和供应商出问
题分不出来。`TestStallGuardFiresOnlyAfterTheWholeIdleWindow` 专门钉住
"永远不会早于"这一半，因为一次善意的简化弄坏的正是这一半。

### 每一样东西都跑在测试自己控制的钟上

`watch` 把 tick 当成 channel 收，`stallReader` 把 `now` 当成函数收，理由
和阶段 09 注入 `sleep`、`rnd` 一样。自己拥有钟的组件，不睡就没法测；而
一套满是 sleep 的测试跑得慢，在负载高的机器上还会飘，并且恰好在你最在乎
的那条边界上悄悄测不了。在这里，"四十五秒过去了"只是往 channel 里推一个
值：一分钱不要，而且测试说它什么时候发生，它就什么时候发生。

`guardBody`——把这些零件围着真实的响应 body 接起来的那个函数——偏偏
**不**收可注入的钟，这个不对称是故意的。它自己造一个真的 `time.Ticker`，
所以在它底下塞一个假的 `now`，会让 reader 盖在一条时间线上、watcher 拿
另一条去比，于是一条完全健康的流会在第一个 tick 上被判死。零件是在受控
的钟上测的；那个真的去盯 socket 的函数，从构造上就在真钟上。

### 看门狗得有人负责

```go
stream, _, stopGuard := guardBody(ctx, resp.Body, dl.idle, cancel, bus, turn)
defer stopGuard()
```

`guardBody` 起一个 goroutine，同时把结束它的那个函数返回出来；调用方
defer 掉它，于是每一条出口都会执行到——包括成功那条。没人负责停的看门狗
是一处泄漏，而且泄漏量随调用次数增长，阶段 07 的子 Agent 会把这个次数弄
得很大。这个停止函数还会取消 context——body 根本走不到 EOF 的时候，靠的
就是它来结束 `watch`。

## 这道保护要花多少

每一次在飞的调用一个 goroutine、一个 ticker。tick 取空闲窗口的四分之一
——一个窗口醒四次，在 45 秒的默认值下就是一分钟五次出头。取四分之一的理
由就在这里：够密，发现的时刻不会比期限晚太多；够疏，一次长调用不至于变
成空转。发现最多晚四分之一个窗口。总线上多
一种事件，只在刷新最大值的时候才发——健康的流上，这种事件会在开头附近出
现几次，然后就没有了。

有一样东西它故意不省：把 `--stall-timeout 0` 设上，关掉的是看门狗，
**不是**仪表。`guardBody` 照样包住 body，照样量，照样报告最宽的那段间
隔。关掉一个期限，不该顺手把那个本来会告诉你该定多少的东西也关掉。

---

## 原因比期限更要紧

三个钟到点的方式是同一个——取消这次调用的 context——所以等错误浮上来的时
候，它们已经彼此分不开了。每一个都是 `context.Canceled`。而它们需要三个
不同的决定。

于是每个钟都**带着原因**取消，分类器读的是原因，不是错误。原因一共四
个，而第四个才是漏掉就会变成 bug 的那一个：

```
interrupted    致命，而且是绝不许重试、也绝不许降级的那一个
stalled        重试——一条死掉的连接，花了整个空闲窗口才证明自己死了
call timeout   致命——它是活着的，只是太慢，所以同一个请求下一次还是
               会太慢，而每一次尝试都要为切断之前已经生成的那些
               token 付钱
parent gone    致命——这个回合，或者整个程序，正在关闭
```

第四个是人按下了 Ctrl-C。阶段 09 把一次失败的调用分成重试、降级、停。
中断如果只是以"错误"的身份到达，就会被重试三次，然后切到第二个供应商
去——这是 Agent 对**停**的回答：换个地方把同一件活再干一遍，在冷掉的
prompt 缓存上，按阶段 09 量出来的 9.7 倍价钱。所以这个会话的信号处理是
手写的，没有用 `signal.NotifyContext`：短的那个写法取消时给的是
`context.Canceled`，而这恰恰是分诊唯一分不出来、会当成卡住的东西。

所以 `triageCause` 跑在状态码那张表**之前**，不是之后：

```go
func (e *CallError) triage() Triage {
    if v, _, ok := triageCause(e.cause); ok {
        return v
    }
    switch e.Phase {
    // ...
```

这个程序自己结束掉的调用，不构成关于供应商的证据，所以下面那一整套对它
没有管辖权。`TestCauseBeatsTheStatusClassifier` 把这个顺序钉住，而且这不
是纸上谈兵：一次被取消的调用身上完全可能还挂着一个 503——那是垂死的请求
最后看到的东西——而先看状态码的分类器，会去重试一次 Ctrl-C。

留意一下**没有**必须改的东西。三种新的失败模式进来，那张分类表把三种全
吸收了，也没有多出第四种裁决。这是现有条件下最好的证据，说明阶段 09 给
它的决定选对了形状。

## 这个名字的来历

不是锁序死锁——这里没有哪两个 goroutine 各拿着对方想要的资源。这一阶段
拿掉的东西更朴素，也常见得多：**一个没人能结束的等待。**

阶段 07 把子 Agent 铺开，再用 `wg.Wait()` 收回来。在这之前，这一串等待
从上到下每一层都没有上界。父 Agent 等子 Agent。每个子 Agent 等一次模型
调用。而那次模型调用等在一个 socket 上，只有十分钟的封顶，还没有任何办
法取消它。这棵树里任何一处的 TCP 连接安静下来，整棵树就卡在那儿，而
Ctrl-C 落在一个根本没在听的父 Agent 身上。

一个 context 一次把每一层都修好，所以这是一个想法，不是五个：子 Agent
的调用变得可取消，于是子 Agent 返回，于是 `wg.Wait()` 返回，于是这个回
合结束。**`dispatch()` 里一行都没改。**那个负责铺开和收拢的函数，完全不
需要知道期限是什么东西。
`TestACancelledParentDoesNotWaitOnItsChildrenForever` 就是这句话的断言
版。

同样的推理用在命令上会挑错工具，而这条路值得走一遍，因为那个显而易见的
答案实在太显而易见了。Go 就是为这件事准备了 `exec.CommandContext`：把
context 交给它，context 一结束它就把进程杀掉。它杀的是 `cmd.Process`，
别的一个都不管——阶段 01 为了包住整棵进程树，在每个操作系统上各写了一个
平台文件，就这么被扔掉了。shell 死了；被 shell 丢到后台的每个进程都还活
着，换了个父进程，继续跑。

所以 context 是进到 `runBash` 本来就有的那个 `select` 里，复用那儿早就
写好的进程组 kill：

```go
select {
case waitErr = <-done:
case <-ctx.Done():
    cancelled = true
    stop()          // g.kill()，然后最多等 5s 收尸
case <-time.After(timeout):
    timedOut = true
    stop()
}
```

那棵树的死法和超时那条路一模一样，而且只有一条 kill 路径，不是两条。

两种退出仍然分得清，因为它们对模型来说意思不同。下面这两行是 `render`
能产出的状态行：

```
[TIMED OUT after <d> — the process tree was killed]
[CANCELLED after <d> — the session is stopping and the process tree was killed]
```

超时说的是这一条命令，而且它带着建议：换个更窄的试试。取消说的是整个会
话。下一条命令不存在了，这时候给建议，等于给模型一条它执行不了的指令，
所以这一行故意一个建议都不给。

### 重试退避也是一种等待

阶段 09 用 `time.Sleep` 睡，而它打断不了。按默认值算，那是最多八秒——一
个已经被叫停的程序，在这八秒里什么都不做。用户看到的是卡死，回答它的是
第二次 Ctrl-C，而那一下会在 trace 落盘之前把进程杀掉。刚出过问题的那次
会话，同时也就成了没有记录的那次会话。`waitFor` 是一次可以被取消截断的
睡眠，而且它把原因返回出来，所以退避期间的中断，报出来就是中断本身，不
是那个引发了这次等待的 HTTP 503。

接着信号处理器把自己注销掉，所以第二次 Ctrl-C 不是第一次的加量版。第一
下是请 Agent 收摊：杀掉命令、关掉 trace、把账单打出来。要是收摊这件事本
身卡住了，用户就需要另一条出路，而这条出路不能依赖那段已经卡住的代码。
中断没被接管时的默认行为，也就是结束进程，正好就是这一条。

## 一次真实运行

阶段 10 的 Agent，跑在阶段 00 那个临时目录上——找出 bug、修掉、再验证一
遍：

```
  ── session ──────────────────────
  7 calls · 10 commands
  prompt tokens billed: 23232  (full 4736 · write 0 · read 18496)
  output tokens: 1053
  re-send ratio: 5.1x (billed 23232 for a final context of 4526)
```

这块面板上没有一点新东西，而这正是重点：三个钟全程都上着膛，一个都没
响。变了的是仪表。每次调用那几行现在报的是余量，不是指望，而且报的正是
期限拿来比的那个量。

## 这一阶段没做到的

- **没有现场的 Ctrl-C 演示。** 中断这条路是有测试盖住的——梯子不往前
  挪、退避被截断、进程树死掉——但没有一份录下来的会话能拿给你看，因为把
  一个信号可移植地脚本化进终端会话，那是另一章的题目。
- **keep-alive 没有证据。** 上面说过了，值得再说一遍：五秒这个节奏是从
  仪表上推断出来的，不是 `wire-notes.md` 里的字节。哪天供应商不再填这些
  静默，45 秒的空闲窗口就会开始杀掉那些思考停顿到 46 秒的调用，而这里没
  有任何东西会提前警告你。
- **这几个期限传不到子 Agent。** `newChild` 会把供应商梯子、重试策略和
  HTTP 客户端都复制过去，唯独不复制 `deadlines` 那个 struct——而零值的
  `deadlines` 意味着三个钟全是关的，因为 `guardBody` 和 `waitFor` 都把
  `<= 0` 读成"不要看门狗"。子 Agent 的调用仍然是可取消的，所以 Ctrl-C
  和正在死掉的父 Agent 照样够得着它；子 Agent 缺的是卡住检测，还有那道
  总的兜底。修法在阶段 11，一行。
- **Windows 上取消路径的那次杀是多余的。** `runBash` 里 defer 了
  `g.Close()`，而 Windows 的 Job Object 带着
  `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`——所以关掉最后一个句柄，就会在退
  出函数的路上把整棵树杀掉，不管取消那条分支有没有先杀过一遍。在 Unix
  上 `Close()` 是 `return nil`，那次杀是承重墙。把取消路径上的那次杀删
  掉，在 Windows 上 `go test` 和 `go test -race` 都过，而在 Linux 上会
  漏掉一棵进程树——所以盖住它的那个测试，保护的正是这台机器跑不了的那个
  平台。
- **`--connect-timeout` 其实不是一个钟。** `ResponseHeaderTimeout` 是请
  求写完之后才开始算的，所以 DNS 和 dial 落在它外面，只受操作系统管。加
  一个 `net.Dialer` 的超时就能把这个口子堵上，而这一阶段没花掉那一行。
- **总期限是按尝试算的，不是按回合算的。** 15 分钟的调用重试三次就是 45
  分钟。阶段 09 那个重试*预算*管的是尝试之间的等待，不是尝试本身，所以
  这两个数合起来，得不出任何人能预测的结果。
- **没有任何东西能单独取消一次压缩。** 它继承回合的 context，所以在一次
  摘要调用中间按 Ctrl-C，停掉的是整个会话，不只是那次压缩。不压缩继续跑
  才是更友好的答案。

## 练习

1. **把 `--stall-timeout 200ms` 设上去，看它吃掉健康的调用。** 观测到
   的静默中位数是 252 ms，所以这个值大概会在一半的调用上响。然后读面
   板：`idle max` 会告诉你该设多少——这就是把它打出来的理由。
2. **把 `--stall-timeout 0` 设上，然后在流到一半的时候把网线拔掉。**
   钟关了，所以这次调用会一直等在 socket 上，等到操作系统放弃——在
   Linux 上那是好几分钟的 TCP 重传，而这个回合没了。
3. **让总期限变成可重试的。** 把 `errCallTimeout` 改成 `TriageRetry`，
   再用 `--call-timeout 20s` 跑一次长生成。算算三次尝试花了多少钱，然
   后注意面板没法告诉你完整的账单——usage 在流的末尾才到，而这些流不会
   有末尾。
4. **改用 `exec.CommandContext` 试试。** 把 `runBash` 里那个
   `<-ctx.Done()` 分支换成它，然后取消一条把子进程丢到后台的命令。
   shell 死了，孙子进程没死——这是阶段 01 那一章从另一条路走了回来。
5. **把 keep-alive 抓下来。** 找任何一个端点，让它在流中间安静下来，把
   填补那段静默的东西记下来，然后往 `wire-notes.md` 里加一节。这个练习
   改进的是仓库的证据，不是它的代码；而这也是这一章唯一一处没有证据的
   断言。

## 读完这一章，你能回答什么

**为什么一个超时保护不了流式的模型调用？**
因为 `http.Client.Timeout` 盖住的是 body 的读取，而在流上，body 的读取
要一直持续到模型说完。这就让这个数变成了"模型能说多久"的上限，而不是一
道防连接断掉的闸。定十分钟，死掉的 socket 能把整个回合扣住 597 秒；定十
秒，长答案会在你已经为生成出来的 token 付过钱之后被掐断。

**三个钟分别是什么，哪一个是承重的？**
connect 是 `--connect-timeout 30s`，响应头必须到；idle 是
`--stall-timeout 45s`，字节之间的间隔；total 是 `--call-timeout 15m`，
单次尝试的兜底。承重的是 idle 那个钟：只有它能把慢的流和死的流分开。

**为什么空闲窗口不能从 trace 里量出来？**
因为 trace 里只有适配器变成事件的那些帧，而期限拿来比的是 socket 上两次
读之间的间隔。事件之间的间隔报出过 9099 ms 和 11067 ms 两段从没发生过的
静默，原因只有一个：过滤器漏了 `reasoning_delta` 和 `tool_args_delta`。

**为什么不能拿到首 token 的耗时去定空闲窗口的尺寸？**
因为 TTFT 量的是生成出来的内容什么时候出现，而这道保护盯的是字节什么时
候到。这是两个量：在同一组样本上，TTFT 最高到 4157 ms，字节级最宽的静默
是 5001 ms——socket 在流中间静得比第一个 token 之前更久。

**这个仓库观测到过的最宽字节级静默是多少，默认值留了多少余量？**
5001 ms，来自 14 次调用；这些调用各自的最大值从 72 ms 起，中位数是
252 ms。45 秒的默认值，相对见过的最宽那一段留了 9 倍余量。

**五秒一拍的 keep-alive，证据是什么？**
只有仪表，别无其他：几乎正好 5000 ms 的字节级间隔，横跨内容流上
18509 ms 的静默。两次 `curl` 探针没能把造成它的字节抓下来——152 行和
1134 行，没有超过一秒的间隔，没有 SSE 注释行——所以这个节奏是推断，而这
一章也是这么写的。

**为什么用时间戳加 ticker，而不是去 reset 一个 `time.Timer`？**
因为 `Reset` 和它想拦住的那次触发之间有竞态：定时器到点，它的函数已经排
进队列，reset 落地晚了，于是字节明明到了，调用却被判成卡住。reader 是在
watcher 读之前写下时间戳的，这个竞态不可能发生。代价是发现最多晚一个
tick，而 tick 是窗口的四分之一。

**为什么这道保护宁可响晚，也不能响早？**
因为响晚了，只是在一次本来就已经死掉的调用上多花不到一个窗口；响早了，
杀掉的是活着的调用，产生的失败看起来和供应商出问题一模一样。所以钉住的
断言是"永远不会早于 `idle`"，不是"接近 `idle`"。

**为什么被取消的调用需要带上原因？**
因为三个钟和中断处理器取消的是同一个 context，等错误浮上来的时候，每一
个都是 `context.Canceled`。原因是唯一还知道哪个钟响了的东西，而这四个原
因需要三个不同的决定——卡住要重试，总超时要停，中断要停而且不许降级。

**标题里的死锁是什么？**
一个没人能结束的等待。父 Agent 等在 `wg.Wait()` 上，每个子 Agent 等一次
模型调用，而那次调用等在一个取消不了的 socket 上——所以一条安静下来的连
接就冻住了整棵树，连 Ctrl-C 也冻在里面。穿进去一个 context，每一层同时
结束，而 `dispatch()` 一行都不用改。

## 思考题

这些题在仓库里没有答案。答案取决于你在造什么。

1. 空闲窗口是一个数，管着所有供应商、所有模型、所有 prompt。要做到按供
   应商分别设定，需要什么？如果改成从观测到的流量里学出来，你怎么防止
   某一个真的很慢的供应商，把 Agent 教成对死掉的 socket 也很有耐心？

2. 卡住要重试，总超时是致命的，而这两种都掐断了一次正在计费的生成。这
   个分法假定部分响应一文不值。设想一种 Agent，在它那儿部分响应是有用
   的，然后想清楚这两个裁决里哪一个会变。

3. 总期限是按尝试算的，所以 15 分钟的调用重试三次就是 45 分钟。设计一
   个按回合封顶的版本。谁必须知道还剩多少预算？预算快花光的时候，重试
   策略该怎么变？

4. 这道保护证明一条连接死了的办法，是等到足够久，久到静默本身成为证
   据。你手上还有别的信号，能更早地把挂死的 socket 和慢的 socket 分开
   吗？要是用了它，你等于在信任什么？

5. 这一章里的每个钟都是客户端在执行。供应商也可以执行自己的钟，有些确
   实在执行。如果服务器按自己的期限切断流，而且在关闭之前就在流里说明
   了这件事，这一阶段里哪些东西你会删掉，哪些你还是会留着？
