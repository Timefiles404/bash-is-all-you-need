# 阶段 10：死锁

阶段 09 结尾把自己的一条限制写了下来，并且点名这一阶段来修它：

> **模型调用上没有期限。** `http.Client{Timeout: 10 * time.Minute}` 是
> 唯一的钟，而它盖住的是整个 body 的读取：一个慢但还活着的流，到第十
> 分钟会死在生成中途，而且没有任何东西能取消一个正在飞的调用。
> `BuildRequest` 返回的是不带 context 的 `*http.Request`，所以拦路的是
> *接口*本身。阶段 10 就是它改掉的地方。

把 `context.Context` 穿过整张调用图，是无聊的那一半。值得写一章的那
一半是：**一个超时对流来说形状就是错的**。这一章大半篇幅是我在跟自己
的测量吵架——吵这个数到底该定多少，吵了三次，因为前两次的答案都错了。

---

## 为什么一个数怎么定都不对

`http.Client.Timeout` 管的是 dial、TLS、响应头，加上整个 body 的读取。
在流式端点上，body 的读取要一直持续到模型说完，所以这仅有的一个数，
同时被问了两个不相干的问题：

```
一次健康的生成能花多久？      分钟级，而且原则上没有
                              上界——答得长本身不是
                              故障

一条**死**连接能装活多久？    毫秒级；根本没有任何
                              理由去等
```

定成十分钟，一条在第三秒无声死掉的流，就把这个回合扣押了剩下的 597
秒。定成十秒，每一个长答案都会被从句子中间掐断——而掐断之前的东西全
都生成过了，也全都计过费了。阶段 09 那行重复计费的数字，就是为了给
这个错误标出价钱。

所以：三个钟。

```
  dial ── TLS ── 响应头 ───┬── 字节 ── 字节 ─────── 字节 ── [DONE]
                           │        ↑           ↑
  ├──── connect ───────────┤        └── 间隔 ───┘
  │                        │
  └──────────────── total ─┴─────────────────────────────────────┘
```

| 钟 | flag | 管什么 |
|---|---|---|
| connect | `--connect-timeout 30s` | 响应头必须在这之内到。这时候什么都还没生成，所以这是唯一一种重试免费的失败。 |
| idle | `--stall-timeout 45s` | 管的是**字节之间的间隔**，不是总时长。它是唯一能把慢的流和死的流分开的钟。 |
| total | `--call-timeout 15m` | 整个调用的兜底。它不是策略——它防的是某个供应商每过一个空闲窗口就挤出一个字节，永远不停。 |

connect 这个钟是 `http.Transport.ResponseHeaderTimeout`：它到响应头就
停，不碰 body。而 client 自己的 `Timeout` 现在是**零**——这才是真正改
掉的东西：那个位置上任何非零的值，都是给模型能说多久设的上限。

中间那个钟是承重墙，也是这件事之所以难的全部理由。一条活着的流和一个
挂死的 socket，从外面看一模一样：两边都没有字节在到。把它们分开的只有
一件事——其中一条还会再吐出一个字节。而关于这一点，你能拿到的证据永远
只有一样：它已经静了多久。

## 这个数，定了三次

空闲窗口就是默认值里的一个数。阶段 09 承认过，整个 `wire-notes.md` 里
关于超时没有任何证据，所以这个数只能自己测。定这个数用了三次，前两次
都错了。

### 第 1 次：在 trace 里量间隔

trace 里每个事件都带时间戳，所以相邻两个流式事件之间的间隔，看起来正
好就是看门狗盯着的那个量。拿三个真实会话量了一遍，报出来的最大间隔到
了 **9099 ms** 和 **11067 ms**。

这是编出来的数。而戳破它的是一次**跑**，不是一次复查：那几个会话里有
一个，本来就是带着 `--stall-timeout 5s` 跑完的，而且跑得干干净净。那
道 5 秒的闸从头到尾没响过，9 秒的间隔就不存在。和一次真跑矛盾的测量，
是测量错了。

bug 在事件过滤器上。它列了 `text_delta` 和 `usage`，漏了
`reasoning_delta` 和 `tool_args_delta`——而这两种事件在那个会话里分别有
**223** 个和 **310** 个。那段"9 秒的静默"，从头到尾都在流一个 thinking
块。

### 第 2 次：老老实实重新量一遍

这次事件种类是从 `events.go` 里抄的，不是从脑子里想的——11 次调用，
993 个间隔：

| | p50 | p90 | p99 | max |
|---|---:|---:|---:|---:|
| 流帧之间的间隔 | 30 ms | 62 ms | 294 ms | **804 ms** |
| 到首 token 的耗时 | 2159 ms | 3309 ms | — | **16448 ms** |

流一旦开始，就没有一次静过整整一秒。但等*第一*帧最长等到了 16.4 秒，
是流中间最宽间隔的 20 倍。结论看起来明摆着：看门狗是从 body 被打开那
一刻起表的，所以它的第一个窗口必须盖住模型整个思考的时间——空闲窗口
其实是由 TTFT 定尺寸的。

这也是错的。

### 第 3 次：把这个数打出来，别再推了

期限真正拿来比的那个量，是 **socket 上两次读之间**的间隔。这个量在
trace 上怎么算都算不出来，因为 trace 里只有适配器选择发出来的那些帧。
所以阶段 10 就在它发生的地方量它——在包住 body 的那个 reader 里——再把
它印到面板上，紧挨着 TTFT：

```
  ┌─ call 1 · tool_calls
  │ in 1743   ████████████████████  full 1743 · write 0 · read 0
  │ out 38     TTFT 4156ms · total 5830ms · 22.7 tok/s · idle max 1119ms
```

`idle max 1119ms`——而这次调用的 TTFT 是 4156 ms。模型在想的时候，
socket 并**不**安静：第一个字节到得比第一个 token 早得多。第 2 次的结
论，被仪表打印出来的第一个数当场推翻。

14 次调用的分布：

| | 最小 | 中位 | 最大 |
|---|---:|---:|---:|
| 每次调用里最宽的字节级静默 | 72 ms | 252 ms | **5001 ms** |

45 秒这个默认值，相对观测到过的最坏静默留了 **9 倍余量**。

再看这组样本对第 2 次那个理论说了什么：这 14 次调用里，TTFT 最高只到
4157 ms，而字节级最宽的静默是 5001 ms。socket 在*流中间*静得比第一个
token 之前更久。这两个量之间的关系，不是 trace 让它看起来的那样。

### 那 5001 ms 到底是什么

产出这个数的那次调用值得读一读，因为两个钟给出的答案差了四倍：

```
idle max     650 ms      ← 运行中的最大值，字节级
idle max    5000 ms
idle max    5001 ms
事件间隔   18509 ms      ← 内容帧，同一次调用的同一段
```

内容流上一段 18.5 秒的静默，被几个几乎正好五秒的字节级间隔切开。模型
在思考的时候，那个 socket 上大约每五秒就有东西到，而它不产生任何事件。

最自然的解读是 keep-alive，五秒一拍。真是这样的话，空闲这个钟量的其实
是*"供应商不再发 keep-alive 了"*——五秒以上的任何值都安全，余量大得离
谱；五秒以下的任何值，会把每一个会思考的模型都杀掉。

**我没能把那些帧抓下来，所以这个仓库不把它当成结论。** 两次 `curl` 探
针追过这件事——一次的 prompt 要求它长时间安静地想，一次带上工具定义和
一条难到需要斟酌的命令——两次都一路不停地流：152 行和 1134 行，超过一
秒的间隔**零**个，SSE 注释行**零**行。效果是仪表记下来的；造成它的字
节不在 `wire-notes.md` 里，而在它们进去之前，五秒这个数是推断，不是证
据。阶段 09 的 `Retry-After` 处境和这里一模一样。

## 原因比期限更要紧

三个钟到点，做的都是同一件事：取消同一个 context。所以等错误浮上来的
时候，它们已经彼此分不开了——每一个都是 `context.Canceled`——而它们需
要三个不同的决定。于是每一个都**带着原因**取消，分类器读的是原因，不
是错误。

第四个原因才是漏掉就会变成 bug 的那个：

```
interrupted    致命，而且是绝不许重试、也绝不许降级的那一个
stalled        重试——一条死掉的连接，花了整个空闲窗口才证明自己死了
call timeout   致命——它是活着的，只是太慢，所以同一个请求下一次还是
               会太慢，而每一次尝试都要为切断之前已经生成的那些
               token 付钱
parent gone    致命——这个回合，或者整个程序，正在关闭
```

阶段 09 把一次失败的调用分成重试 / 降级 / 停。一次只是"错误"的中断，
会被重试三次，然后切到第二个供应商去：Agent 对**停**的回答，是换个地
方把活再干一遍，在一个冷的 prompt 缓存上，按阶段 09 量出来的 9.7 倍价
钱。`triageCause` 跑在状态码那张表之前，就为这一个理由，而
`TestCauseBeatsTheStatusClassifier` 把它钉住——一次被取消的调用，身上
完全可能还挂着一个 503，那是垂死的请求最后看到的东西。

让人舒服的是**没有**必须改的东西。三种新的失败模式进来，那张分类表把
它们全吸收了，也没有多出第四种裁决。这是阶段 09 选对了形状的最好证据。

## 这个名字的来历

不是锁序死锁。这一阶段拿掉的东西更朴素，也常见得多：**一个没人能结束
的等待。**

阶段 07 把子 Agent 铺开，再用 `wg.Wait()` 收回来。在这之前，这一串等
待从上到下每一层都没有上界——父 Agent 等子 Agent，每个子 Agent 等一次
模型调用，而那次模型调用等在一个 socket 上，只有十分钟的封顶，还没有
任何办法取消它。一条安静下来的 TCP 连接，整棵树就卡在那儿，而 Ctrl-C
落在一个根本没在听的父 Agent 身上。

一个 context 一次把每一层都修好，所以这是一个想法，不是五个：子 Agent
的调用变得可取消，于是子 Agent 返回，于是 `wg.Wait()` 返回，于是这个
回合结束。**`dispatch()` 里一行都没改。**
`TestACancelledParentDoesNotWaitOnItsChildrenForever` 就是这句话的断
言版。

同样的推理用在命令上，会挑错工具。`exec.CommandContext` 是那个显而易
见的答案，而它只给 `cmd.Process` 发信号，别的一个都不管——阶段 01 为了
进程组包围，在每个操作系统上都写了一个平台文件，就这么被扔掉了。所以
context 是进到 `runBash` 本来就有的那个 `select` 里，复用 `g.kill()`，
那棵树的死法和超时那条路一模一样。两种退出仍然分得清，因为它们对模型
来说意思不同——下面这两行是 `render` 能产出的状态行，不是抓下来的截屏：

```
[TIMED OUT after <d> — the process tree was killed]
[CANCELLED after <d> — the session is stopping and the process tree was killed]
```

超时说的是这一条命令，它的意思是"换个更窄的试试"。取消说的是整个会
话：下一条命令不存在了，这时候给建议，等于给模型一条它执行不了的指令。

## 为什么用时间戳，不用 `timer.Reset`

检测卡住最显而易见的写法，是每次读都 reset 一个 `time.Timer`。它也是
错的，而且是最难查出来、因此最贵的那种错：`Reset` 和它想要拦住的那次
触发之间有竞态。定时器到点了，它的函数已经排进队列，而那个本该拦住它
的 `Reset` 晚了一微秒才落地。字节明明到了，这次调用却被判成卡住。

这个窗口极小，而这正是它坏的地方——它很少响，只在压力下响，而且看起
来像供应商在抽风。

拿时间戳去比，就不可能输掉这个竞态，因为 reader 是在 watcher 读它*之
前*写下时间的。代价是发现得晚，最多晚一个 tick，而 tick 是窗口的四分
之一：卡住会在 `idle` 和 `idle × 1.25` 之间被发现，永远不会早于 `idle`。
`TestStallGuardFiresOnlyAfterTheWholeIdleWindow` 钉住的是"永远不会早
于"这一半，也正是一次善意的简化会弄坏的那一半。

这一阶段的每个测试都跑在注入的钟上——`watch` 把 tick 当成 channel 收，
`stallReader` 把 `now` 当成函数收——理由和阶段 09 注入 `sleep`、`rnd`
一样。一个自己拥有钟的组件，不睡就没法测；而一套满是 sleep 的测试，是
一套人会不再跑的测试。在这里，"四十分钟一直不安静的流"一分钱都不要。

值得一提的是 `guardBody` 偏偏**不**收可注入的钟，这个不对称是故意的：
它自己造一个真的 ticker，所以假的 `now` 会让 reader 盖在一条时间线上、
watcher 拿另一条去比，于是一条完全健康的流会在第一个 tick 上被判死。
零件是在假钟上测的；那个真的去盯 socket 的函数，从构造上就在真钟上。

这里没有一点新东西，而这正是重点：三个钟全程都开着，一个都没响。变了
的是仪表——它现在报的是余量，不是希望。

## 这一阶段没做到的

- **没有现场的 Ctrl-C 演示。** 中断这条路是有测试盖住的——梯子不往前
  挪、退避被截断、进程树死掉——但没有一份录下来的会话能拿给你看，因为
  把一个信号可移植地脚本化进终端会话，那是另一章的题目。
- **keep-alive 没有证据。** 上面说过了，值得再说一遍：五秒这个节奏是
  从仪表上推断出来的，不是 `wire-notes.md` 里的字节。哪天供应商不再填
  这些静默，45 秒的空闲窗口就会开始杀掉那些思考停顿到 46 秒的调用，而
  这里没有任何东西会提前警告你。
- **Windows 上取消路径的那次杀是多余的。** `runBash` 里 defer 了
  `g.Close()`，而 Windows 的 Job Object 带着
  `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`——所以关掉最后一个句柄，就会在
  退出函数的路上把整棵树杀掉，不管取消那条分支有没有先杀过一遍。在
  Unix 上 `Close()` 是 `return nil`，那次杀是承重墙。这是变异测试找出
  来的：把取消路径上的那次杀删掉，在这台机器上 `go test` 和
  `go test -race` 都过，而在 Linux 上会漏掉一棵进程树。这个测试留着，
  因为它保护的那个平台，正是这台机器跑不了的那个。
- **`--connect-timeout` 其实不是一个钟。** `ResponseHeaderTimeout` 是
  请求写完之后才开始算的，所以 DNS 和 dial 落在它外面，只受操作系统
  管。加一个 `net.Dialer` 的超时就能把这个口子堵上，而这一阶段没花掉
  那一行。
- **总期限是按尝试算的，不是按回合算的。** 一个 15 分钟的调用重试三次
  就是 45 分钟。阶段 09 那个重试*预算*管的是尝试之间的等待，不是尝试
  本身，所以这两个数合起来，得不出任何人能预测的结果。
- **没有任何东西能单独取消一次压缩。** 它继承回合的 context，所以在一
  次摘要调用中间按 Ctrl-C，停掉的是整个会话，不只是那次压缩。不压缩继
  续跑才是更友好的答案。

## 练习

1. **把 `--stall-timeout 200ms` 设上去，看它吃掉健康的调用。** 观测到
   的静默中位数是 252 ms，所以这个值大概会在一半的调用上响。然后读面
   板：`idle max` 会告诉你该设多少——这就是把它打出来的理由。
2. **把 `--stall-timeout 0` 设上，然后在流到一半的时候把网线拔掉。**
   钟关了，所以这次调用会一直等在 socket 上，等到操作系统放弃——在
   Linux 上那是好几分钟的 TCP 重传，而这个回合没了。
3. **让总期限变成可重试的。** 把 `errCallTimeout` 改成 `TriageRetry`，
   再用 `--call-timeout 20s` 跑一次长生成。算算三次尝试花了多少钱，然
   后注意面板没法告诉你完整的账单——usage 在流的末尾才到，而这些流不会
   有末尾。
4. **改用 `exec.CommandContext` 试试。** 把 `runBash` 里那个
   `<-ctx.Done()` 分支换成它，然后取消一条把子进程丢到后台的命令。
   shell 死了，孙子进程没死——这是阶段 01 那一章从另一条路走了回来。
5. **把 keep-alive 抓下来。** 找任何一个端点，让它在流中间安静下来，把
   填补那段静默的东西记下来，然后往 `wire-notes.md` 里加一节。这个练习
   改进的是仓库的证据，不是它的代码；而这也是这一章唯一一处没有证据的
   断言。
