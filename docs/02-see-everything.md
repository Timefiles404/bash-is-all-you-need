# 阶段 02：看见一切

阶段 00 和 01 已经做出了能干活的 Agent。这一章讲的是另一件事：你看不见
它在干什么。

听起来像在抱怨日志不够多。不是。阶段 01 打印得不少。真正的毛病是：它对
自己知道的事，**只**做了打印这一件——一行字滚出终端，那个事实就没了。
你没法重放它、没法 diff、没法汇总，也没法把它交给别人。

所以这一章只做一处结构上的改动，然后把它带出来的后果一条条收下来。

---

## 唯一的那处改动

> **Agent 核心什么都不打印，它只发出事件。你能看见的一切，都是订阅者。**

```
Agent 核心 ──emit──▶ Bus ──┬──▶ renderer     （终端，带仪表）
                           └──▶ TraceWriter  （session.jsonl，一行一个事件）

重放：  session.jsonl ──▶ Replay ──▶ 同一个 renderer，不联网，不要 API key
```

这一阶段剩下的东西，几乎都是从这一句里掉出来的：

| 你得到什么 | 因为 |
|---|---|
| 每个会话都有一份永久记录 | trace 文件不过是又一个订阅者 |
| 不用 API key 也能重放 | 把 trace 喂回同一个 renderer |
| `--plain` 与阶段 06 的 TUI 二选一 | 换的是订阅者，不是把代码分叉 |
| 断言行为的测试 | 断言的是事件序列，不是刮下来的 stdout |
| 请求检查器 | 请求的字节本来就是事件 |

能带走的那条经验不是"上事件总线"，而是：**可观测性是开头就定下的形状，
不是收尾时补上的日志。**阶段 01 里每一句 `fmt.Printf` 都是这么一处地方：
某个事实唯一的记录，就是屏幕上的一个字符。

总线**同步分发，而且在锁里面**。这比每个订阅者一条 channel 慢，慢是故意
的：顺序因此是全序的，对谁都一样，trace 文件和你的终端不可能对"谁先发生"
各说一套。只要一份 trace 有可能跟你亲眼所见对不上，它就不算证据。

## 仪表面板

下面是真实会话里的一次调用：

```
  ┌─ call 5 · stop
  │ in 1066   ███████████████████   full 106 · write 0 · read 960
  │ out 117    TTFT 2943ms · total 4533ms · 73.6 tok/s
  │ $0.000201    session $0.000856 over 5 calls
  └ context 1066 / 131072 (0.8%)
```

四行，每一行都在回答一个问题，而这些问题大多数 Agent 都答不上来。

### `in 1066`——没有哪个 API 字段会告诉你 1066

人们问"我的上下文现在多大"，问的就是这个数，而**它不在 API 返回的任何
单个字段里。**

Anthropic 风格的协议里，`input_tokens` 只是**没命中缓存的那部分余量**。
跑了一小时的 Agent 可以老老实实报 `input_tokens: 18`，而它实际发出去的
是 18,000。真实的 prompt 大小是 `input + cache_write + cache_read`——
`Usage.Prompt()` 算的就是这个，这一行显示的也是这个。

OpenAI 风格的协议里，这笔账是**反着记的**：`prompt_tokens` 是全量，
`cached_tokens` 套在它**里面**。所以归一化要做减法：

```go
Input     = prompt_tokens - cached_tokens   // 按全价计费
CacheRead = cached_tokens
```

要是直接把 `prompt_tokens` 抄过去，506 个 token 的 prompt，`Prompt()` 会
报 698。留意这个 bug 什么时候是隐形的：**误差恰好等于缓存命中的大小**——
冷请求上它是零，测试里看着完美，而你的缓存做得越好，它错得越离谱。

### 那根柱子——三种颜色，因为你在按三种价钱付账

```
███████████████████        红 = 全价 · 黄 = 缓存写（~1.25x） · 绿 = 缓存读（~0.1x）
```

三个数字摆成一张表，读是读得懂。柱子不用读，扫一眼就进眼睛了，而真正值
得留意的，是**回合之间比例的变化**。绿色一没了，就是有东西把你的缓存作
废了——这件事你要在它发生的那个回合看见，不是到月底账单上看见。阶段 04
整章就在讲怎么让那根柱子一直是绿的。

### `TTFT 2943ms · total 4533ms · 73.6 tok/s`

TTFT 和吞吐量分开报，因为**它们坏起来的原因不一样**。第一个 token 来得
慢，是排队、是缓存冷、是 prompt 太长。吞吐量慢，那是模型自己的事。把两
者平均成一个数，你什么也做不了——看下面那个会话的第一次调用：TTFT 13 秒，
第二次只要 1.2 秒。那是冷启动，一平均就看不见了。

### `$0.000201`——或者破折号

不传 `--price-in` / `--price-out`，这一行就写着
`cost — (set --price-* to price this run)`。

**编出来的零比没有数字更糟**，因为零正是人们会拿去引用的那个数。Agent
不知道你的价钱，于是它拒绝替你编。

## 会话小结，和阶段 04 生来就要搬的那个数

```
  5 calls · 5 commands
  prompt tokens billed: 3941  (full 869 · write 0 · read 3072)
  output tokens: 419
  cost: $0.000856
  re-send ratio: 3.7x (billed 3941 for a final context of 1066)
```

记住最后一行。阶段 00 的文档把这个比值记成 **4.2x，而当时什么都看不见**。
这里是 3.7x——但现在你还能看见：**3941 个 token 里有 3072 个是缓存读**，
价钱大约是十分之一。重发这笔税确实存在；只是其中大部分本来就便宜，而在
这一章之前，没人能告诉你这件事。

## trace

每行一个 JSON 对象：

```json
{"seq":1,"t":"2026-08-27T03:15:34.33+08:00","kind":"user_message","text":"run python stats.py…"}
{"seq":2,"t":"2026-08-27T03:15:34.34+08:00","kind":"turn_start","turn":1}
{"seq":3,"t":"2026-08-27T03:15:34.34+08:00","kind":"request","turn":1,"request":{"model":"mimo-v2.5",…}}
```

那个五回合的会话，196 个事件，40KB。

**JSONL 不是审美选择，它是崩溃契约。**JSON 数组要有个右括号收尾，而被杀
掉的进程永远写不出那个括号——于是记录崩溃的那份文件，会**因为**崩溃而
没法解析。按行分隔的意思是：每写完一行就独立有效，最后一行写了一半，损
失的是一个事件，不是全部。`ReadTrace` 把截断的尾巴当成被杀会话的**正常**
形状，把它前面的东西全捞回来，再把"发生了什么"当成流里的一个事件报出去，
而不是报成 error：报成 error，调用方就会被引着把解释崩溃的那 195 个事件
顺手一起扔了。

**"每行都刷"的意思是不带缓冲，而且明确不是 `fsync`。**一个事件写一次，
代价是几微秒进页缓存，这已经扛得住 SIGKILL、panic 和 `os.Exit`。`fsync`
还能多扛一次断电，代价是 0.1–10ms——**而且是每一个文本增量都要付，还是
在总线的锁里面付**。三个数量级，换来的是防住一种罕见得多的失败。知道这
条线画在哪儿，比听人说一句"我们会刷盘"有用。

**"别堵住总线"不等于"别做 I/O"。**顺手的解法是写一个异步 writer，可队
列满了以后只有两种行为：堵住生产者（你本来要避开的那件事），或者丢事件
（一份靠省略说谎的 trace，而且恰好是在你最想记下来的负载下说谎）。真正
的规矩是**不许有无界等待**——不 fsync，不联网，不在跨 channel 发送时握
着锁。`trace.go` 里一个 goroutine 都没有，这是故意的。

**`bufio.Scanner` 是给读 trace 的人挖的坑。**它把单个 token 限死在
64KB，超了就让**整次**读取以 `ErrTooLong` 失败——而 trace 里最值钱的那
一行，请求体，正是在第三十个回合前后越过 64KB 的那一行。
`bufio.Reader.ReadBytes` 没有上限，它会把没有换行符的最后一行连同
`io.EOF` 一起交回来，而这**就是**截断信号。

**向前兼容大半是"不去做什么"。**`ReadTrace` 从不拿 `events.go` 里的常量
去校验 `kind`。一校验，后面每加一种 kind，都会让加它之后写下的文件在重
放时无声地坏掉。

## 重放

```sh
agent --replay session.jsonl              # 原始节奏
agent --replay session.jsonl --speed 0    # 一瞬间跑完
agent --replay session.jsonl --step       # 每个事件按一次回车
```

不要 API key。不联网。不用 shell。把环境清干净再跑：

```
trace · 196 events · 5 turns · 5 commands · 25.34s
tokens · prompt 3941 (full 869 · write 0 · read 3072) · output 419
replay · instant
```

……会话一模一样地重现了，因为 renderer 从来没有过自己的时钟。**它打印的
每一个数字，都是搭着某个事件到达的。**哪天你发现自己想在 `render.go` 里
写 `time.Now()`，那说明你要的那个数该放进事件里。

这才让这个仓库能当教材：手上没有任何凭证的学生也能研究一次真实会话，而
你可以拿着别人发来的文件，去调他那一次运行。

时间上有个细节值得知道：记录下来的间隔会**先截到 5 秒**，然后才交给
`Speed` 缩放。重放要传达的东西全都在 5 秒以内——TTFT、增量吐字的节奏、
一条命令的挂钟时间。比这更长的都是人在发呆，而这件事时间戳报得比干等更
清楚。截断放在缩放**之前**，意味着 `--speed 2` 照样能把最坏情况砍一半，
`--speed 0.5` 也照样能替想体会那个停顿的人把它拉长。

## 流式到底让你付出什么

流式不是"同一个响应，慢慢到"。它是另一种数据形状，而旧的那种形状得你自
己拼回来。

**assistant 消息必须由你重新拼装。**历史里要放的，是这次请求换成非流式
时 API **本来会**返回的那条消息。忘了这一步，流式 Agent 就会莫名其妙地
"丢"掉自己的工具调用：增量画得好好的，可什么都没回到 `messages` 里去。

**解析器得能在这个协议真实的样子里活下来。**下面每一条都在
[wire-notes.md](wire-notes.md) §B4–B7 里附了原始证据，每一条都是真踩过
的坑：

| 观察到的 | 后果 |
|---|---|
| 带 usage 的那个 chunk 里 `"choices": []` | `choices[0]` 直接 panic。这是全文件最可能出的 bug。 |
| `id` 和 `function.name` 恰好只在**一个** chunk 里到，后面每个都是 `null` | 第一次见到就锁住；永远不要用 null 覆盖 |
| `arguments` 的碎片**不**按 JSON 边界切（`"{\"command\": "`, `"\""`, `"ls"`, `" -la /srv"`, `"/app"`） | 按 `index` 分桶累积原始字节；永远不要去解析碎片 |
| 每个字段都显式给成 `null`，而不是省略 | "键在"什么都说明不了。要测值 |
| 有一帧在 `data: [DONE]` **之后**才到 | 跳过这个哨兵，继续把流读干到 EOF |
| 这个流里根本没有 `event:` 行 | ……但 `readSSE` 照样支持，因为阶段 03 的第二个协议要用 |

`[DONE]` 这个决定值得单说，因为"见哨兵就停"正是规范写的，而它在这里错在
三处：`[DONE]` 之后那一帧是真数据；响应体里还剩着字节就撒手，HTTP 传输层
就没法复用这条连接，于是每个回合悄悄多一次 TLS 握手；还有，万一哪天
usage 挪到哨兵后面去，提前停下的客户端会报出零 token，而且错得理直气壮。

**TTFT 认的是真负载，不是第一帧。**第一个 chunk 带的是 `content: ""`。
把它算进去，TTFT 就成了到首**字节**的时间，跑在思考模型上的每个请求都会
被它美化一遍。

## 这一章先发出去、后来才修掉的那个集成 bug

留着它，因为它是事件驱动设计的典型故障，而且它长得根本不像崩溃。

第一个能跑的版本，每次调用打**两块面板**——先一块全是零，再一块是真数
字。原因：流解析器发了 `KindResponseEnd`（它知道响应什么时候结束），
而 Agent 主循环**也**发了一份（它知道 usage）。**两个组件都以为同一个事
件归自己所有。**

两处修改，两处都是可以带走的经验：

1. **一个事件只能有一个所有者。** `KindResponseEnd` 留给解析器，因为只
   有它知道响应是不是**干净地**结束了——流中途出错时它故意什么都不发，
   于是 trace 永远不会记下一场根本没发生过的干净收尾。
2. **一个数字是搭哪个事件来的，renderer 不该关心。**它锁住自己见过的最
   后一个 `KindUsage`，就用那个。只从 `KindResponseEnd` 读 usage，就是那
   一堆零底下那个脆弱的假设。

同一次改动还去掉了第二处重复：命令的页脚会打一遍退出码和耗时，而工具结
果的文本末尾本来就有这两样。现在只显示工具结果——**就是喂给模型的那些
字节，一个不多一个不少。**让人看到的摘要比模型收到的更漂亮，而这一阶段
存在的意义，正是消灭这种偏差。

## 练习

1. **把顺序保证弄坏。** 让 `Bus.Emit` 在 goroutine 里分发，然后看着
   trace 和终端在顺序上时不时对不上。看完改回来。
2. **拿 `jq` 翻 trace。**
   `jq -r 'select(.kind=="command_start") | .command'` 会把一次会话跑过
   的所有命令都吐出来。格式故意做得这么无聊，就是为了这个。
3. **打开 `--show-request`，把第一个请求整个读一遍。** 大半"模型为什么
   那么干"的疑问都死在这里：prompt 里根本没有你以为的那些东西。
4. **重放别人的 trace。** 先把环境里的 API key 删掉，好让你自己相信：
   重放什么都不需要。
5. **加一种事件 kind。** 发出它、画出它，确认旧 trace 还能重放。然后试
   着给已有的 kind 改个名，看它对一份录好的会话干了什么——那些常量上为
   什么挂着警告，你就知道了。
6. **把冷启动找出来。** 上面那次运行里，调用 1 的 TTFT 是 13042ms，调用
   2 是 1239ms。把这个差解释清楚，再去看缓存那一列，看它同不同意你的说
   法。
