# 阶段 04：缓存

阶段 03 结尾留了一个没解释的不对称：同样的任务，同样规模的对话，
一边的缓存条是绿的，另一边从头到尾红成一片。

这一章把它修掉，然后拿大半篇幅去讲更要紧的那件事——**prompt 缓存是
一门纪律，不是一项功能。** 代码只有四十行左右，而那四十行外面的
规矩，比这些行本身值钱得多。

---

## 机制，一段话讲完

渲染出来的 prompt 按顺序是三段：`tools`、`system`、`messages`，
先后就是这个。缓存匹配的是**前缀**：`cache_control` 标记的意思是
*到这里为止都算可重用的前缀*。由此立刻得到两条推论，而这一章剩下
的一切都是从它们推出来的：

- 标记只在一种情况下有用：它**前面**的所有内容，下一次逐字节一样。
- 前面动了一个字节，后面所有标记全部作废——所以内容按"稳定的在
  前、易变的在后"排好，比标记本身更要紧。

每个请求最多四个标记。这个适配器放了两个：

```
tools ─────────┐
system ────────┴─▶ [1] 整个会话冻住不动
messages
  回合 1 …
  回合 N ──────────▶ [2] 滚动：一直盖到最新的这个回合
```

第一个请求之后，标记 1 每次都能把自己赚回来。**在 Agent 里真正
要紧的是标记 2**，因为每个回合都要把整段对话重发一遍：少了它，
每个回合都按全价把整段历史重读一遍。这就是阶段 00 量出 4.2 倍、
却没能解释的那个重发比。

---

## 第零课：标记不是机制

这一章的实验，第一次跑出来是这样：

```
  │ in 528    ████████████████████  full 528 · write 0 · read 0
  │ in 647    ████████████████████  full 647 · write 0 · read 0
  │ in 746    ████████████████████  full 746 · write 0 · read 0
```

`cache_control` 是开着的。什么都没缓存上。没有报错，没有警告，
一句抱怨都没有。

**prompt 太短了。** 可缓存前缀有个下限——具体看模型，常见是 1,024
到 4,096 个 token——低于这个数，标记就被默默吞掉。不是被拒绝，是
*被忽略*：`cache_creation_input_tokens: 0`，加上 200 OK。

这里有两件事要记住。短的 Agent 会话根本不走缓存，所以"缓存开了"
这件事，光看配置是看不出来的，只能看用量数字。还有一条：**没报错
不等于成功**，这是贯穿整个仓库的主题。

---

## 实验

同一个任务，三个分支，都跑在同一个 56KB 的文件上（读进上下文之后
大约 10,000 个 token）：

```sh
agent --yolo --max-output 60000                # A：打开 cache_control
agent --yolo --max-output 60000 --no-cache     # B：不打标记（只剩隐式缓存）
agent --yolo --max-output 60000 --break-cache  # C：每个请求换一个新时间戳
```

### 分支 A：显式 `cache_control`

```
  │ in 535    ████████████████████  full 535 · write 0     · read 0
  │ in 10348  █▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓  full 6   · write 10342 · read 0
  │ in 10484  ▓░░░░░░░░░░░░░░░░░░░  full 6   · write 136   · read 10342  99% cached
  │ in 10655  ▓░░░░░░░░░░░░░░░░░░░  full 6   · write 171   · read 10478  98% cached
  │ in 10805  ▓░░░░░░░░░░░░░░░░░░░  full 6   · write 150   · read 10649  99% cached
  │ in 11114  ▓░░░░░░░░░░░░░░░░░░░  full 6   · write 309   · read 10799  97% cached
  │ in 11276  ▓░░░░░░░░░░░░░░░░░░░  full 6   · write 162   · read 11108  99% cached

  prompt tokens billed: 65217  (full 571 · write 11270 · read 53376)
```

看 read 那一列：**10342、10478、10649、10799、11108**——每个数都
正好是上一回合的 prompt。滚动标记在正常干活：每个回合读上一回合
写下的东西，自己只写增量。

### 分支 B：不放标记，只有隐式缓存

```
  │ in 10348  ███░░░░░░░░░░░░░░░░   full 1900 · write 0 · read 8448   82% cached
  │ in 10793  ███░░░░░░░░░░░░░░░░   full 2089 · write 0 · read 8704   81% cached
  │ in 11018  ████░░░░░░░░░░░░░░░   full 2570 · write 0 · read 8448   77% cached
  │ in 11570  ████░░░░░░░░░░░░░░░   full 2866 · write 0 · read 8704   75% cached
  │ in 11671  █░░░░░░░░░░░░░░░░░░   full 791  · write 0 · read 10880  93% cached

  prompt tokens billed: 55935  (full 10751 · write 0 · read 45184)
```

缓存照样发生了——这个网关会隐式缓存。但看 read 列：**8448、8704、
8448、8704、10880。** 每个数都是 64 的倍数（132×64、136×64、
170×64），而且它们**会涨也会跌**，可对话只会变长。

差别一句话就说完了。隐式缓存是按**64 个 token 的块边界**匹配的，
每个请求还要重新决定一次；`cache_control` **把前缀钉死在确切位置**，
命中就变成单调、可预测的了。显式缓存买到的是*确定性*——也就是把
回归和噪声分开的能力。

### 分支 C：系统提示词里塞一个时间戳

```
  │ in 10387  █▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓  full 6 · write 10381 · read 0
  │ in 10497  █▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓  full 6 · write 10491 · read 0
  │ in 16352  █▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓  full 6 · write 16346 · read 0
  │ in 16458  █▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓  full 6 · write 16452 · read 0

  prompt tokens billed: 54267  (full 597 · write 53670 · read 0)
```

**每一次调用都是 `read 0`。** 每个回合都写进一条全新的缓存条目，
而这条永远不会有人来读；为了写它，还要付一笔写入溢价。

按常见的乘数（write ≈1.25x、read ≈0.1x）把三个分支都折算成全价
等效 token：

| 分支 | full | write | read | 折算全价 |
|---|---:|---:|---:|---:|
| A：显式 | 571 | 11,270 | 53,376 | **~20,000** |
| B：只有隐式 | 10,751 | 0 | 45,184 | **~15,300** |
| C：坏掉的 | 597 | 53,670 | 0 | **~67,700** |

**缓存坏掉，比根本没有缓存更糟**——比分支 A 差 3.4 倍，比分支 B
差 4.4 倍——因为每个 token 你都付了写入溢价，却什么都收不回来。
没有任何东西报错。唯一的症状是账单。

### 诚实的那部分：B 赢了 A

在这个只有六次调用的会话上，不放标记的那个分支反而**最便宜**。
这是实测出来的结果，该说出来，不该埋掉。

为什么：滚动标记每回合都要新写一条，而第一次写的是整个 10K token
的前缀，按 1.25 倍收。六次调用换来的读取次数太少，摊不平这笔钱；
对面那个隐式缓存写起来一分不要，命中率本来就有 75–93%。写入溢价
得靠量才划得来——换到长 Agent 会话上，同一个前缀要被读几十遍，
账就翻过来了。

有三条限定条件必须一起记住，因为它们就是"实测"和"口号"之间的
分界线：

- **乘数是假设。** 这个网关每个响应都报 `cost: "0"`（wire-notes
  §C10），所以美元那一列是拿业界常见比率算出来的，不是这家供应商
  的真实账单。token 数是量出来的，钱是推出来的。
- **分支之间不是严格受控的。** 模型每次跑出来的回答都略有不同，
  总数因此对不齐。真正的发现是*比例*，不是绝对数字。
- **收支平衡点取决于你的会话有多长、你的供应商用什么乘数。** 自己
  去量。这一章的重点不是让你把缓存打开，而是让你*分得清*。

## 第二课：值在哪儿算出来的，决定它疼不疼

`--break-cache` 第一次写出来根本不生效。时间戳**只在启动时注进去
一次**，缓存照样好得很——因为在一次会话里恒定的值，对这次会话来说
就是恒定的前缀。

真正会被发布出去的 bug 长这样：`datetime.now()` 待在 prompt 构建器
里，而这个构建器**每次调用都跑一遍**。同一行代码，同一个变量，在
调用图上只隔三十行，成本差 3.4 倍。

所以要审的问题不是"我的 prompt 里有没有时间戳"，而是**"我的前缀里
有没有哪个值，在两次连续请求之间可能不一样"**——这问的是
*代码在哪儿跑*，不是代码写了什么。

## 五条纪律

代码做的事都很小。真正要记住的是这一节。

**1. 一次会话之内，把系统提示词冻死。** 任何会动的东西——日期、
用户 id、模式开关、特性开关——都该待在最后一个断点*之后*，放进
消息流里，绝不能摆在前缀最前面。回合 5 追加的一条消息，废不掉
回合 5 之前的任何东西。

**2. 把工具列表冻死。** 工具渲染在位置零，所以加一个、删一个、
换个顺序，废掉的是*所有东西*，标记也一起废。序列化的方式必须
确定。真需要"模式"，就把模式放进消息里传；别去换工具集。

**3. 只追加，永不重写历史。** 改一条旧消息，它后面每个字节都会
挪位。上下文压缩——阶段 05——贵也贵在这里，而这笔账在它自己的
token 数字里根本看不见：它重写了前缀，所以压缩之后的那个回合，
铁定是一次全价未命中。

**4. 序列化要保持字节稳定。** Go 会给 map 的键排序，模型不会。把
工具调用的参数解出来再编回去，字节就挪了位——所以从阶段 03 起，
`Block.Args` 一路都是原始字符串。`TestToolArgumentKeyOrderSurvives`
存在的意义就是让这类回归吵得足够响；对它做变异测试，吐出来的警告
一字不差是这样：

```
tool arguments were re-serialised: keys came back sorted, so the prompt prefix
moved and every cached turn is now a miss
```

**5. 盯 read 列，别盯配置。** 缓存没有成功信号。想知道它在干活，
唯一的办法是看 `cache_read` 又大又单调地往上涨。阶段 02 那块仪表
盘就是为这个存在的。

## 两个从头到尾不报错的陷阱

**最小前缀。** 低于大约 1K–4K 个 token（看模型），标记直接被忽略。
你精心摆好的位置一点用都没有，而且没人来告诉你。

**20 个块的回看窗口。** 断点会往回找有限个内容块，看有没有现成
的条目。Agent 要是在一个回合里并行开了很多工具，一次就能塞进比这
更多的块——之后下一个标记什么也找不到，你就一声不响地付了全价。
每回合只开一个工具，稳稳待在窗口以内。扇出型 Agent 得在中间再放
一个标记——四个槽位里还空着两个，就是留给它的。

## 关于那根缓存条的一点说明

这三段拆分画出来用的是三种不同的**字形**，不只是三种颜色：

```
████▓▓░░░░░░░░░░░░░░   █ 全价   ▓ 缓存写   ░ 缓存读
```

最初不是这么设计的。第一版用同一个字形配三种颜色，在终端里看着
挺好，可输出一旦过一道 `grep`、写进文件、或者落进 CI 日志，就变成
一整块看不出层次的东西——而出了问题的时候，人看 Agent 输出恰恰
就是这么看的。**只在彩色终端里成立的图表，偏偏会在有人想给你指出
问题的那一刻变成空白。**

## 练习

1. **三个分支自己跑一遍**，把 read 列拿来对比。然后把分支 A 跑到
   两倍长，看交叉点会不会出现。
2. **加第五个标记。** 看 API 怎么把它顶回来，再想清楚：手上这
   四个，你愿意让出哪一个。
3. **把滚动标记挪到固定位置**——比如永远钉在消息 3——然后看着
   对话越过它以后，命中率一回合一回合往下掉。
4. **故意破一次纪律 4**：把工具参数解出来再编回去。字节在你眼里
   一模一样，read 列直接塌掉。
5. **找到你自己的收支平衡点。** 同一个任务，分别跑 5、20、50 个
   回合，有标记和没标记各来一遍，看在你的供应商这边，会话长到
   多少显式缓存才开始占优。那个数字，比这一章的任何建议都值钱。
