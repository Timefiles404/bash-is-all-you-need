# 阶段 07：乘法

两个功能，哪个都算不上子系统。

```
子 Agent    换一份 []Msg，换一份系统提示词，其余一切照旧——而回来的只有
            文字，别的什么都没有。
技能        一个装 Markdown 文件的目录，外加一段话说明它们存在。
```

没有调度器，没有消息队列，没有 Agent 注册表，Agent 之间也没有协议。
子 Agent 就是一次函数调用，返回值是一段话。

还有一句得摆在最前面，因为它跟所有人的直觉正好相反：

> **子 Agent 不省 token，它省的是上下文。**

下面有实测：委托那一路**多花了 20% 的 token**，收工时父 Agent 的上下文
**小 9.6 倍**。两个数字往相反的方向走，而"什么时候该委托"这件事，从头到尾
就是搞清楚你眼下缺的是哪一个。

## 子 Agent 就是同一个主循环，再调一次

```go
func (a *agent) spawn(callID, description, prompt string) (string, Usage, error) {
    child := a.newChild(agentID, func() string { return subagentSystem + para + a.stable })
    msgs := child.runTurn([]Msg{TextMsg(RoleUser, prompt)})
    return lastAssistantText(msgs), child.spent, nil
}
```

功能就这么多。父 Agent 手上早就有主循环、总线、压缩器和权限闸了；子 Agent
就是同一个主循环，换一个消息数组。真正有意思的设计问题到头来只剩一个——
哪些东西共享，哪些不共享：

| 共享 | 不共享 |
|---|---|
| 供应商、HTTP client | 消息数组 |
| 权限闸 | 系统提示词 |
| shell 配置和工作目录 | 压缩器 |
| **总线内核**——整棵树共用一条有序 trace | 回合预算 |

让这件事值得做的，是 `lastAssistantText` 这一句。子 Agent 干过的其他一切——
每一次工具调用、每一坨 40kB 的命令输出、每一条走错又退回来的岔路——都活在
一个消息数组里，而那个数组随后就被丢掉。父 Agent 的上下文只涨那份报告的
长度，别的一个字节都不涨。

这件事是在系统提示词里明说给子 Agent 的，没留给它自己去猜：

> 你在这里做的一切，做完之后全部丢弃，**只有你最后那条消息例外**。
> 调用你的人永远看不到你的命令、你的推理、你的工具输出——只看得到你
> 说的最后一句话。

少了这一段，子 Agent 交上来的是**过程**总结——"我看了几个文件，发现了
一些东西"——因为聊天回合本来就长这样。把"最后那条消息是唯一活下来的
东西"这句话对它说清楚，它就写报告了。

## 真实运行：委托到底花了多少

三个 Markdown 文件，一共 63kB。任务只有一个：每个都通读一遍，各写三句话
的总结。两路对照，同一批文件，同一个模型：

```sh
agent --yolo --max-output 60000              # delegate：每个文件一个子 Agent
agent --yolo --max-output 60000 --max-depth 0  # inline：没有 task 工具
```

```
  ╭─ subagent · Summarize wire-notes.md
  ╭─ subagent · Summarize 02-see-everything.md
  ╭─ subagent · Summarize 03-babel.md
  │ $ cat .../wire-notes.md
  │ $ cat .../02-see-everything.md
  │ $ cat .../03-babel.md
  ╰─ 2 turns ·  5133 prompt +  204 output tokens ·  6327ms →  707B returned
  ╰─ 2 turns · 11952 prompt +  237 output tokens · 12441ms →  827B returned
  ╰─ 2 turns ·  4696 prompt +  380 output tokens · 13519ms →  950B returned
```

| | 委托 | 内联 |
|---|---:|---:|
| 模型调用 | 9（父 Agent 3，子 Agent 6） | 3 |
| prompt token | 25,782 | 19,715 |
| 按 0.1x 缓存读折算 | **22,038** | **18,390** |
| output token | 1,635 | 571 |
| 实际耗时 | 39s | 18s |
| **收工时父 Agent 的上下文** | **1,893** | **18,160** |

按全价当量算，委托多花了 20% 的 token、2.9 倍的 output token、2.2 倍的
耗时。它同时也让父 Agent 收工时整个上下文只有 1,893 个 token——因为那
63kB 的 Markdown 被读了三遍，三个 Agent 各读一遍，而它们没有一个还端着
这段对话。

再看那三行 `╰─`。**进去 21,781 个 prompt token，回来 2,484 字节。**这个
比值就是你买到的东西，其余全是为它付的开销。

所以判断标准不是"这个任务够不够大，值不值得委托"，而是：

> 该委托的活是**读得多、结论少**的那一种，而且读进去的东西你之后不会
> 再用。如果你需要中间输出，子 Agent 严格劣于内联做完——token 你付了
> 两遍，结果还是扔了。

这也是 `task` 工具的描述为什么写的是经济账而不是机制。只讲工具**干什么**
的描述，对"什么时候该伸手拿它"一个字都没说。

## 并发，和一张提前三章到期的账单

三个子 Agent 同时在跑。注意 trace 依然是单独一条、全序的流——每个事件
都带一个 `Seq`，它给这个事件和树里任何一个别的事件定下先后，跨 Agent
也算。

这不是新写的东西。阶段 02 挑了同步总线、一把锁，为的就是顺序——那会儿
正好只有一个生产者，看不出有什么明显的理由去在乎：

```go
type busCore struct {
    mu   sync.Mutex
    seq  int
    subs []Subscriber
}

func (b *Bus) Fork(agent string) *Bus {
    return &Bus{core: b.core, depth: b.depth + 1, agent: agent}
}
```

`Fork` 什么都不复制。一个计数器，一把锁，N 个生产者。要是当初选了按订阅者
分开的异步总线——也就是那个"扩展性更好"的设计——每个订阅者拿到的就是
同一个并发会话的不同版本，而并发会话恰恰是没有统一版本就没法推理的那种
会话。

另一个常见选择是每个 Agent 一份 trace。它的后果是，你真正想问的那唯一一个
问题——**子 Agent 在跑的时候，父 Agent 在干什么？**——只能靠按时间戳合并
文件来回答，而按时间戳对齐正好是时间戳最不擅长的事。

### 渲染器降级，而不是撒谎

三个子 Agent 把 token 流往同一个终端光标里灌，出来的是一段由三句不同的
话拼起来的文字。这不只是丑；它读起来像一个 Agent 在自己跟自己矛盾。

所以朴素渲染器只显示子 Agent 的**结构**——跑了什么、花了多少、返回了
什么——正文一概不显示。什么都没丢，因为每一个 delta 都在 trace 里；而
阶段 06 的 composer 存在的理由正是：线性终端对一棵树来说形状不对。

> **渲染器显示不了某样东西，就该用少显示来说明这件事，绝不能靠显示错的。**

### 并发执行，确定的历史

`dispatch` 并发跑子 Agent，但返回结果的顺序**是模型要求它们的那个顺序**。
要是改成谁先完成就先 append，同一个会话重放两遍会得到两个不同的消息
数组、两个不同的 prompt 前缀，以及——照阶段 04 的说法——一个永远不命中
的缓存。

> 并发可以改变事情要花多久。它不可以改变这段对话说了什么。

权限闸加 mutex 是同一个理由，而这个理由比看上去更锋利。两个 goroutine
同时往一个终端写 prompt，屏幕上是一行交错的字，然后一个答案被当成两个
问题的回答读走：**用户批的是一条命令，跑起来的是另一条。**这是穿着 UI
bug 外衣的安全 bug。`dispatch` 在任何并发开始之前，就在同一个 goroutine
上把所有问题都问完了，所以那把锁本来永远不该有竞争——它在那儿，是因为
"本来永远不该"不是你愿意让权限闸靠着的性质。

## 深度保险丝，以及工具为什么会消失

到了深度上限，`task` 工具是**从工具列表里拿掉**的，不是等它调用时再拒绝。

运行时拒绝要赔一整个往返——模型写一次调用，宿主驳回，模型读完驳回再换
别的招——而且每一个根本用不上它的请求，都要为那份工具定义付 token。更糟
的是，这是一条模型看得出来很随意的规则，而模型跟随意的规则争论的方式，
就是换个说法再来一遍。

不在列表里的工具不是规则。没有东西可争，也没有东西可绕，模型就在自己
手上有的工具里做计划。

## 技能就是一个目录加一段话

```
skills/
  mutation-test/SKILL.md    ---  name: … / description: … ---  然后是正文
  new-stage/SKILL.md
  wire-probe/SKILL.md
```

系统提示词里放的是名字和一行描述。正文留在磁盘上。模型觉得某个技能用得
上，就 `cat` 一下读它。没有技能工具，没有检索环节，没有运行时——这就是
阶段 05 关于记忆的那个观察，从另一条路走到了同一个地方：Agent 一旦有了
shell，"相关的时候加载这份文档"就不是什么要你去实现的功能，它就是个
文件名。

承重的是形状。**渐进式披露**：索引永远在，正文按需取。

```
  ≡ skills: 3 skills · index 738B in every request · 6.1kB of bodies left on disk
```

这个数字是故意打出来的，因为索引**不是免费的**，而这笔算术就是整个设计
决策本身。738 字节会在会话活着的每一刻，坐在每一个请求的前缀里——阶段
04 之后它能按十分之一的价格缓存，但永远不是零。四十个技能就是两千来个
token 的永久开销。技能目录要是没人修剪、只管往下长，那就是一笔税，对
Agent 此后的每一次调用征收；而唯一能让人察觉到它的办法，是有东西把这个
数字打出来。

索引里有三条指令，每一条都对着一种出错的方式：

- **"动手前先读正文"**——否则模型就照着描述动手，而那描述只有一行，
  是为了让人能**挑得出来**才写的，不是为了够用。
- **"最多一个"**——给模型五个看着都像的技能，它会把五个全读完，于是省
  token 变成了费 token 外加五个往返。
- **"都不适用就忽略这个列表"**——少了这句，技能列表读起来就像一份菜单，
  模型觉得自己有义务点一个，于是总能找出一个差不多能凑上的。

frontmatter 的解析器是二十行，而不是 YAML 依赖。接口的两头都在你手里，
解析器就可以小到跟接口一样大。

## PTC 到底是什么

程序化工具调用（PTC）的卖点只有一条：模型写代码去调工具，代码在别处跑，
**中间结果永远不进上下文**。

shell 管道早就把这件事做了。同一个任务，三种做法——**在 `src/` 下面找出
最大的五个 Go 文件**——跑在 21 个文件上：

| | 模型调用 | 命令 | prompt token | 按 0.1x 读折算 | 进上下文的工具输出 | 耗时 |
|---|---:|---:|---:|---:|---:|---:|
| 每个文件一次调用 | 25 | 23 | 51,937 | 8,161 | 1,255 B | 80s |
| `wc -l src/*.go` | 2 | 1 | 2,097 | 1,175 | 509 B | 12s |
| `find … \| sort -rn \| head -6` | 2 | 1 | **1,608** | **686** | **157 B** | **8s** |

**答案一模一样。prompt token 32 倍，耗时 10 倍。**

要读的是"进上下文的工具输出"这一列，因为那才是机制，别的都只是症状。
管道里的 `sort | head` 是**在 shell 内部**过滤完的，所以越境进上下文的
是 157 字节，不是 1,255。中间数据是存在的，它只是从来没变成 token。

这张表里有两件事值得带走。

**中间那一行是个意外，而它恰好把话说明白了。**那一路本来该是慢的那个——
指令写的是不许用管道、不许串联、不许 `xargs`、不许 `find`。模型交上来的是
`wc -l src/*.go`，一条规矩都没破，还把整件事在一次调用里做完了，因为
**glob 本身就是批量操作**，我禁掉的运算符一个也没用上。不用开口要就白拿
到扇出，正是这个仓库从开篇那一节起就一直在替 shell 主张的性质，而它偏偏
要靠一次失败的实验才现形。

**那 PTC 比管道多给了什么？**反正不是那条卖点——那条卖点就是一个 `|`。
它多给的是一门真正的编程语言，而 shell 在这个位置上只有组合：有类型的
工具 API 而不是文本流，能对结构化结果做条件和循环，错误处理不靠 `$?`，
工具也不必是 PATH 上的程序。如果你的工具是 CLI 程序，控制流就是"过滤、
排序、取前几个"，那管道就是 PTC，你从 1973 年起就已经有它了。如果你的
工具是带 schema 的 HTTP API，控制流还带分支，那就不是了——这个差别值得
专门配一个运行时。

## 完全不要 `task` 工具的那个版本

能跑 bash 的 Agent，就能跑**那个 Agent 自己**：

```sh
agent --subagent "survey every provider adapter and report the disagreements"
```

一个 prompt 进去，一份报告出来，没有 REPL。这就是一套完整的子 Agent
机制，用的全是 Agent 手上已经有的那个工具；值得亲眼看看它有多单薄——
递归不需要编排层，它需要的是一个进程。

代价是仪表盘上的一切。单独的进程有自己的总线，于是它的事件不在你的
trace 里；它的 token 不在你的账本里；它的权限 prompt 会跟你的抢终端；它的
失败是退出码，不是停止原因。这些你全都得重造一遍——架在一根管道上，用
一种此后还得由你自己做版本管理的格式。

这就是"进程内还是进程外"这整个选择的老实总结：**shell 是个相当好的
编排器，一直好到你想知道它到底花了多少为止。**

## 练习

1. **把两路都跑一遍**，比一比各自最后那个 `context` 数字。那个比值就是
   你花钱买的东西。
2. **委托一件你需要中间输出的事**——"找到 bug，把 diff 给我看"——然后
   看那份报告怎么变得毫无用处。子 Agent 的失败模式不是它答错了，而是
   **它丢信息的方向不由你选**。
3. **把 `subagentSystem` 里"一切都会被丢弃"那一段删掉**，然后读三份报告，
   数数有几份写的是过程而不是发现。
4. **让 `dispatch` 改成谁先完成就先 append 结果**，而不是按下标。同一个
   会话跑两遍，把两份 trace 的请求体 diff 一下。
5. **设 `--max-depth 3`**，给 Agent 一个大到会递归的任务。然后算出你最坏
   情况下的账单是多少，再看代码里有没有哪个保险丝真拦得住它。
6. **加第四个技能，再量一次索引。**外推到四十个。在你真的需要修剪策略
   **之前**，先把它定下来。
7. **自己把 PTC 那张表跑一遍**，挑一个大到有意义的目录，找出单命令版本
   的输出装不进 `--max-output` 的那个点。那个数字就是 shell 不再够用、
   真正的沙箱开始成为答案的地方——那就是阶段 08。
